## 01. 프로젝트 소개와 본인 역할

### Q001. OnFilm을 30초 안에 사용자·문제·핵심 기능 중심으로 소개해 주세요.

OnFilm은 배우 등 작품 참여자가 프로필과 필모그래피, 스토리보드를 관리하고 영상을 외부에 보여주는 서비스입니다. 저는 백엔드와 비동기 영상 처리 흐름을 구현하고, 중복 요청·작업 누락·조회 성능을 개선했습니다.

### Q002. 어떤 사용자를 위해 만들었고, 그 사람이 기존에 겪던 불편은 무엇이었나요?

작품과 경력을 보여주려는 지인을 대상으로 시작했습니다. 단순한 영상 목록보다 참여 작품·역할·프로필을 함께 보여주고, 제출 목적에 맞게 영상을 제공하는 것이 중요했습니다. 아직 대규모 사용자 조사 결과로 일반화할 단계는 아닙니다.

### Q003. 프로필·필모그래피·스토리보드·영상 제공 기능은 하나의 사용자 흐름에서 어떻게 이어지나요?

사용자는 프로필을 만들고 작품과 역할을 필모그래피에 연결합니다. 영상은 업로드 후 별도 Worker가 변환하고, 스토리보드는 Project·Scene·Card로 구성합니다. 방문자는 공개 범위에 맞춰 경력과 영상을 확인합니다.

### Q004. 프로젝트에서 직접 맡은 범위와 외부 도구·라이브러리·AI의 도움을 받은 범위는 어디까지인가요?

도메인 정책 결정, 백엔드 기능과 테스트 검토, AWS 설정 및 전체 흐름 검증을 맡았습니다. 코드 작성과 대안 정리에 AI를 활용했고 Spring·Kafka·FFmpeg 등을 사용했습니다. 모든 코드를 혼자 처음부터 작성했다고 표현하지는 않습니다.

### Q005. 초기 개발과 이후 리팩토링을 구분하면 각 시기의 목표는 무엇이었나요?

초기에는 사용자에게 필요한 프로필·필모그래피·영상 기능을 만드는 것이 목표였습니다. 이후에는 엔티티와 서비스 책임, 오류·트랜잭션 정책을 정리하고 DB·메시지 처리의 실패 상황을 검증하는 데 집중했습니다.

### Q006. 실제 사용자 이용, AWS 기능 검증, 인위적인 부하 실험을 구분해서 설명할 수 있나요?

현재 목표는 지인 1~2명이 사용하는 MVP입니다. AWS에서 영상 업로드부터 DONE까지 확인한 것은 실제 환경의 기능 검증이고, k6 실험은 인위적인 부하 측정입니다. 이를 다수 고객의 지속적인 운영 실적으로 말하지 않습니다.

### Q007. 가장 자신 있는 개선 사례 하나를 문제·원인·선택·검증·한계 순서로 설명해 주세요.

대표 사례는 Job 저장 후 Kafka 발행 전에 종료되면 작업이 누락될 수 있는 문제입니다. Job과 Outbox를 함께 저장해 재발행할 근거를 남기고, Worker의 Inbox로 중복에 대응했습니다. DB·상태 테스트와 AWS 흐름을 확인했지만 외부 작업의 정확히 한 번 실행을 보장하지는 않습니다.

### Q008. 프로젝트에서 가장 어려웠던 결정은 무엇이고, 왜 어려웠나요?

DB와 Kafka 사이의 실패를 어디까지 자동 복구할지 정하는 일이 어려웠습니다. Outbox는 누락 위험을 줄이지만 중복과 운영 상태를 추가합니다. 실패 지점을 나누어 학습하고 재시도 한도·최종 상태·수동 복구 정책을 정했습니다.

### Q009. 개발 기간에 비해 기능과 구조가 복잡해진 이유를 어떻게 설명하겠나요?

기능 제공뿐 아니라 실패 처리와 기술 선택을 학습·검증하는 목적이 함께 있었습니다. 다만 학습 가치가 곧 MVP의 필수 복잡성을 뜻하지는 않습니다. 지금 다시 시작한다면 사용자 기능과 안정성 실험의 작업 범위를 더 명확히 나누겠습니다.

### Q010. 이 프로젝트 경험 중 지원 직무에 직접 연결되는 부분과 아직 경험하지 못한 부분은 무엇인가요?

연동 직무에는 중복·누락·Callback 실패를 다룬 경험, 일반 백엔드 직무에는 모델링·트랜잭션·SQL 검증을 연결할 수 있습니다. 대규모 실서비스 운영이나 여러 외부 공급사의 데이터 통합을 수행한 경험은 없다고 구분하겠습니다.

## 02. 사용자 요구사항·MVP·비즈니스 정책

### Q011. 왜 유튜브 링크만 연결하지 않고 직접 영상을 제공하는 방향을 선택했나요?

저는 비용 절감을 위해 유튜브 링크 방식을 제안했지만, 사용자는 오래된 업로드 날짜가 제출 자료의 인상에 영향을 줄 수 있다고 설명했습니다. 서비스의 목적이 경력을 보여주는 것임을 고려해 직접 제공하는 방향을 유지했습니다.

### Q012. 사용자가 업로드 날짜 표시를 우려했을 때 본인의 비용 중심 제안을 어떻게 수정했나요?

사용자의 반대 이유를 듣고 영상 재생 자체보다 제출 상황에서 어떻게 보이는지가 중요하다는 점을 이해했습니다. 비용만으로 판단하지 않고 직접 제공 방식을 유지했습니다. 업로드 날짜가 실제 평가에 미친 효과를 측정한 것은 아닙니다.

### Q013. 사용자의 요청을 모두 구현하지 않고 우선순위를 정한 기준은 무엇인가요?

핵심 사용자 흐름에 필요한지, 실패 시 피해가 큰지, 지금 운영 규모에 맞는지를 기준으로 나눴습니다. 역할 모델과 파일 권한 확인은 정리하되 전자서명 같은 큰 기능은 보류했습니다. 우선순위 결정과 학습용 실험도 구분하려 했습니다.

### Q014. 초기 1~2명 사용을 위한 필수 기능과 공개 서비스 전환 전 필요한 기능은 어떻게 다른가요?

MVP는 확인된 사용자, 프로필·필모그래피, 영상 업로드·재생과 기본 복구가 우선입니다. 공개 전에는 가입·업로드 제한, 권리 확인 자동화, 보안 점검, 비용 통제와 운영 담당 체계를 보강해야 합니다. 이를 모두 이미 구축한 것은 아닙니다.

### Q015. 같은 영화에 여러 사람이 참여하면 Movie와 개인 필모그래피를 어떻게 구분하나요?

정책상 Movie는 공유 작품이고 MoviePerson은 개인의 참여 관계입니다. 역할은 MoviePersonRole에 둡니다. 같은 작품을 재사용하는 모델과 정책을 선택했지만, 이름이나 영상 해시로 모든 중복 작품을 자동 병합하는 기능은 없습니다.

### Q016. 사용자가 탈퇴했을 때 참여 관계·공유 Movie·영상 파일 중 무엇이 삭제돼야 하나요?

정책상 탈퇴한 사용자의 Person과 참여 관계는 제거하되 공유 Movie와 다른 사람의 이력은 유지합니다. Movie 자체 삭제는 별도 관리 행위로 보고 소유 자식과 파일을 정리합니다. 정책 문서와 모든 탈퇴 실행 경로의 구현 여부는 구분해 확인해야 합니다.

### Q017. 영상 업로더·작품 참여자·영상 이용 권한 보유자는 왜 같은 개념이 아닌가요?

참여 이력은 작품에서 맡은 역할을 뜻하고, 업로더는 실제 파일을 올리는 사람입니다. 서비스에서 저장·변환·공개하도록 허락할 수 있는지는 별도의 조건입니다. 프로젝트에서는 참여 사실만으로 영상 공개 권한을 자동 인정하지 않는 정책을 정했습니다.

### Q018. 현재 수동 권리 확인 정책은 무엇을 기록하며, 사용자 수가 늘면 어떤 한계가 있나요?

운영자가 이용허락 주체, 저장·변환·공개 범위, 기간과 철회 조건을 확인하는 정책입니다. 증빙은 Git이 아닌 제한된 보관소에서 관리하도록 했습니다. 현재 애플리케이션이 승인·만료 이력을 자동 추적하는 것은 아니어서 규모가 커지면 누락 위험이 있습니다.

### Q019. 권리가 확인되지 않은 작품도 영상 없이 필모그래피로 등록할 수 있나요?

정책상 영상 권리가 불명확하면 파일을 받지 않고 작품명과 역할 등 텍스트 필모그래피만 제공할 수 있습니다. 작품 참여 정보를 등록하는 것과 영상을 공개하는 조건을 구분한 것입니다.

### Q020. 전자서명·공유 영상 권한·자동 승인 같은 기능을 지금 보류한 이유는 무엇인가요?

확인된 소수 사용자를 위한 단계에서 권리자 인증·서명·분쟁 처리를 모두 만들면 범위가 너무 커집니다. 현재는 수동 확인과 이용자 제한을 선택하고 공개 서비스 전환 전에 재설계하기로 했습니다. 수작업 의존성은 감수한 한계입니다.

## 03. 전체 아키텍처와 데이터 흐름

### Q021. 업로드 요청부터 영상 재생 가능 상태까지 시스템 흐름을 종이에 설명해 주세요.

권한 확인 후 requestId와 Presigned URL을 발급하고 브라우저가 S3에 업로드합니다. 완료 API는 Job과 Outbox를 저장합니다. Publisher가 Kafka로 보내면 Worker가 변환·업로드하고, 인증된 Callback으로 API의 결과와 DONE을 반영합니다.

### Q022. API·Worker·Kafka·S3·DB 각각의 책임과 실패 시 영향 범위는 무엇인가요?

API는 권한·메타데이터·Job 상태, Worker는 영상 처리, Kafka는 요청 전달, S3는 파일, 각 DB는 담당 서비스의 상태를 보관합니다. Kafka 장애는 발행 적체로, API 장애는 접수·Callback 실패로 이어질 수 있어 단계별로 조사합니다.

### Q023. API와 Worker를 분리한 이유는 무엇이며, 단순한 프로세스 분리와 MSA를 어떻게 구분하나요?

CPU를 많이 쓰는 긴 인코딩이 사용자 API의 자원을 직접 소모하지 않도록 분리했습니다. 독립 배포·자원 조정이 가능하지만 이것만으로 완성된 MSA라고 보지는 않습니다. 데이터 소유권·통신 계약·복구 비용까지 함께 관리해야 합니다.

### Q024. 영상 업로드 자체와 인코딩 요청 발행은 각각 어느 경로를 통과하나요?

파일 바이트는 브라우저에서 S3로 직접 보냅니다. Kafka에는 파일 자체가 아니라 jobId·requestId·스토리지 위치·변환 설정 등 작업 정보를 보냅니다. 따라서 업로드 성공과 인코딩 접수·완료는 다른 단계입니다.

### Q025. API와 Worker가 같은 MySQL 서버를 사용하면서 논리 DB와 계정을 분리한 이유는 무엇인가요?

현재 규모에서 물리 DB 두 대의 비용은 피하면서 스키마 변경과 데이터 접근 책임을 분리하려 했습니다. API는 onfilm_api, Worker는 onfilm_worker만 접근합니다. 직접 조회 대신 Kafka·Callback으로 연결하는 비용은 추가됩니다.

### Q026. 논리 DB를 나눠도 같은 물리 서버의 장애와 자원 경합은 공유하지 않나요?

네, 논리 DB와 계정 분리는 접근 권한과 소유권을 나누는 것이지 물리 장애 격리가 아닙니다. CPU·스토리지·연결 용량을 공유합니다. 실제 경합이나 가용성 요구가 커지면 물리 분리와 복제 구성을 검토하겠습니다.

### Q027. API·Worker 사이에서 직접 DB JOIN을 금지한 이유와 그 때문에 생긴 비용은 무엇인가요?

다른 서비스의 테이블 구조에 직접 의존하면 변경과 배포가 강하게 결합됩니다. 각 서비스가 자신의 DB만 변경하고 메시지·API 계약으로 연결하도록 했습니다. 대신 즉시 JOIN이 어렵고 최종 상태를 맞추는 재시도와 관측이 필요합니다.

### Q028. HTTP 202 응답 시점에 보장된 사실과 아직 완료되지 않은 일은 무엇인가요?

202 시점에는 해당 완료 요청에 대한 Job·발행 요청이 저장됐다는 것을 의미합니다. Kafka 소비, 인코딩, 출력 업로드와 최종 Callback은 아직 끝나지 않았습니다. 클라이언트는 Job 조회로 최종 상태를 확인해야 합니다.

### Q029. 사용자에게 결과를 알릴 때 polling을 선택한 이유와 SSE·WebSocket 대안은 무엇인가요?

초기 규모에서는 Job 상태를 주기적으로 조회하는 방식이 단순하고 재연결 처리가 쉽습니다. 대신 반복 요청과 갱신 지연이 있습니다. 작업 수·조회 부하·실시간 요구가 커지면 SSE 등을 검토하되 현재 도입했다고 말하지 않습니다.

### Q030. API 인스턴스를 두 대로 늘리면 기존 설계에서 먼저 점검할 공유 상태는 무엇인가요?

Outbox 선점·공유 DB 외에 메모리 nonce 저장소, 스케줄러 중복 실행, 로컬 파일 의존성을 먼저 확인합니다. Callback replay를 전역으로 막으려면 공유 nonce 저장소가 필요합니다. API 수를 늘리는 것만으로 모든 상태가 공유되는 것은 아닙니다.

## 04. 도메인 모델·소유권·관계

### Q031. MoviePerson에서 MoviePersonRole을 분리한 이유를 실제 사용자 사례로 설명해 주세요.

한 참여자가 같은 작품에서 여러 역할을 맡는데, 역할마다 참여 행을 만들면 공개 여부와 순서가 중복됩니다. 참여는 MoviePerson 하나로 두고 역할을 자식으로 분리했습니다. 참여 중복과 역할 중복을 각각 명확한 UNIQUE로 제한할 수 있습니다.

### Q032. User와 Person은 왜 별도 엔티티이며, 두 객체의 생명주기는 어떻게 다른가요?

User는 로그인 정보와 인증 정책, Person은 공개 프로필과 경력 정보를 담당합니다. 변경 이유를 분리하려는 선택입니다. 다만 서로 독립적으로 영원히 존재하는 모델이라고 단정하지 않고 생성·탈퇴 시 연결된 생명주기도 함께 관리합니다.

### Q033. 한 사람이 같은 작품에서 배우·감독·작가를 맡으면 어떤 행들이 저장되나요?

해당 Movie와 Person 사이에 MoviePerson 한 행을 만들고, ACTOR·DIRECTOR·WRITER의 MoviePersonRole 세 행을 연결합니다. 배우 전용 정보는 ACTOR 역할에만 둬 참여 자체의 공개 여부·순서를 중복 저장하지 않습니다.

### Q034. MoviePerson과 MoviePersonRole의 UNIQUE 기준은 각각 무엇인가요?

MoviePerson은 movie_id와 person_id 조합을 유일하게 둡니다. MoviePersonRole은 movie_person_id와 role 조합을 유일하게 둡니다. 한 사람의 같은 작품 참여는 하나이면서 그 안에 서로 다른 역할은 여러 개 허용하는 기준입니다.

### Q035. 작품의 개인 공개 여부와 정렬 순서는 왜 역할이 아니라 참여 관계에 속하나요?

필모그래피에서는 같은 작품을 한 항목으로 보여주므로 공개 여부와 순서도 참여 항목의 속성이라고 봤습니다. 역할마다 저장하면 한 작품 안에서 서로 다른 공개 상태가 생길 수 있습니다. 역할별 공개 요구가 생기면 별도 정책 검토가 필요합니다.

### Q036. 배우 역할에는 필요한데 감독 역할에는 없어야 하는 필드는 어떻게 검증하나요?

ACTOR에는 castType을 요구하고 DIRECTOR·WRITER에는 배우 전용 필드를 허용하지 않습니다. 객체 생성·변경 시 검증하고 실제 DB의 CHECK도 함께 둡니다. 애플리케이션 외의 저장 경로에서도 잘못된 조합을 막으려는 목적입니다.

### Q037. 마지막 역할을 제거하면 참여 관계가 어떻게 돼야 하며 그 규칙은 어디서 지키나요?

참여에 역할이 하나 이상 있어야 한다는 규칙을 두었습니다. 마지막 역할만 제거해 빈 참여를 남기기보다 제거를 거절하고 참여 자체를 삭제하는 행위와 구분합니다. 최소 역할 수는 부모 컬렉션을 관리하는 도메인에서 지킵니다.

### Q038. 표준 Genre와 사용자 입력 Genre를 한 모델에서 표현한 이유와 대안은 무엇인가요?

표준 장르를 선택할 수도 있고 사용자가 직접 장르를 입력할 수도 있어 MovieGenre에서 두 경우를 표현했습니다. 표준 ID가 없는 경우도 정규화된 텍스트로 중복을 검사합니다. 모델 분리가 더 명확할 수 있지만 조회·수정 경로가 늘어나는 비용이 있습니다.

### Q039. JPA 연관관계를 사용한 참조와 ID 값만 보관한 참조를 어떤 기준으로 나눴나요?

객체 탐색과 생명주기 관리가 필요한 관계는 연관관계를 쓰고, 비동기 작업의 식별·스냅샷 중심 정보는 ID 값으로 보관했습니다. Java의 ID 참조와 DB FK 존재 여부는 별개입니다. 특히 서비스 간 DB FK는 두지 않는 정책입니다.

### Q040. UUID publicId를 노출하면 접근 권한 검증은 생략해도 되나요?

아닙니다. UUID는 순차 PK 추측을 어렵게 하고 내부 식별자 노출을 줄이지만 권한을 증명하지 않습니다. 해당 프로필·Movie를 요청자가 조회·수정할 수 있는지 별도로 확인해야 합니다.

## 05. 엔티티 캡슐화·JPA 설계

### Q041. Aggregate Root가 자식 생성·연결·삭제를 책임지도록 한 이유는 무엇인가요?

외부 서비스가 컬렉션을 직접 수정하면 중복 검사와 양방향 연결 순서가 흩어집니다. 부모의 add·remove·reorder 메서드에 묶어 유효한 상태를 유지하도록 했습니다. 자식의 모든 업무를 부모가 알아야 한다는 뜻은 아닙니다.

### Q042. protected 기본 생성자와 정적 팩토리가 각각 필요한 이유는 무엇인가요?

JPA가 엔티티를 복원할 기본 생성자는 허용하되 외부에서 검증 없이 생성하지 못하도록 제한했습니다. 정적 팩토리는 생성 의도를 드러내고 필수값·정규화를 적용합니다. JPA 복원 경로는 팩토리를 거치지 않으므로 DB 제약도 필요합니다.

### Q043. Builder를 모든 엔티티에 적용하지 않은 이유와 적용해도 되는 경우는 무엇인가요?

Builder는 선택값이 많은 객체를 읽기 쉽게 만들지만 엔티티의 필수값과 연결 규칙을 자동 보장하지 않습니다. OnFilm은 유효한 생성 경로를 명시하는 팩토리를 우선했습니다. 검증을 유지할 수 있는 복잡한 DTO 등에는 선택적으로 쓸 수 있습니다.

### Q044. change·update·apply 메서드 이름을 어떤 기준으로 구분했나요?

change는 제목·파일 키처럼 구체적 속성을 바꾸는 행위, update는 관련 정보를 묶어 수정하는 행위로 구분했습니다. apply는 검증된 결과를 내부 모델에 반영하는 문맥에 사용했습니다. 이름보다 실제 책임과 검증 경계가 일치하는지 확인했습니다.

### Q045. 양방향 연관관계의 주인과 도메인 생명주기의 주인은 항상 같은가요?

같지 않습니다. JPA의 주인은 FK 값을 쓰는 쪽이고 Aggregate Root는 업무 불변식과 생명주기를 관리하는 쪽입니다. 예를 들어 자식이 FK를 관리하더라도 부모가 생성·추가·삭제 편의 메서드를 제공할 수 있습니다.

### Q046. add·remove 편의 메서드가 중간에 실패하면 객체 관계를 어떻게 유지하나요?

null·중복·다른 부모 소속 같은 검증을 가능하면 변경 전에 끝내고 양쪽 관계를 함께 맞춥니다. 여러 요소를 교체할 때는 전체 요청 검증 후 반영합니다. DB 롤백이 이미 수정한 Java 객체 상태까지 되돌리는 것은 아니라 객체를 재사용할 때도 주의합니다.

### Q047. 읽기 전용 컬렉션을 반환하면 내부 엔티티의 변경까지 막히나요?

아닙니다. 읽기 전용 리스트는 add·remove 같은 컬렉션 구조 변경을 막습니다. 안에 들어 있는 엔티티가 변경 메서드를 제공하면 그 객체는 바뀔 수 있습니다. 객체의 상태 변경도 도메인 규칙을 거치게 해야 합니다.

### Q048. cascade와 orphanRemoval을 적용한 관계·적용하지 않은 관계를 각각 설명해 주세요.

StoryboardProject의 Scene처럼 부모가 소유한 자식에는 cascade와 orphanRemoval을 사용했습니다. 참여 관계를 삭제했다고 공유 Movie나 다른 Person까지 지워서는 안 됩니다. 저장 전파와 고아 삭제를 공유 객체 전체로 확대하지 않는 것이 기준입니다.

### Q049. Scene 재정렬 요청이 정확한 순열인지 검사해야 하는 이유는 무엇인가요?

전체 순서를 전달하는 API라면 누락·중복·다른 Project ID를 조용히 보정하는 것은 클라이언트 오류를 숨깁니다. 기존 ID의 정확한 순열인지 먼저 검사하고 순서만 바꿉니다. 부분 이동 API가 필요하면 별도 계약으로 만드는 편이 명확합니다.

### Q050. @OrderColumn과 자바 리스트 순서, DB 제약의 중간 저장 상태는 어떻게 연결되나요?

@OrderColumn은 리스트 위치를 DB 순서 컬럼으로 관리합니다. Hibernate가 INSERT 뒤 위치를 UPDATE하는 등 중간 상태를 거칠 수 있어 무조건 NOT NULL·UNIQUE를 붙이면 정상 저장도 실패할 수 있습니다. 실제 MySQL 저장·재정렬 SQL로 제약을 검증했습니다.

근거·상세: [관련 설명·답변](08-java-spring-jpa-interview-qa.md)

## 06. Service 책임·DTO·검증 위치

### Q051. PersonReadService를 어떻게 나눴고 각 서비스는 무엇 때문에 변경되는 클래스인가요?

PersonReadService에 조회·변경·파일 처리가 함께 있어 이름만으로 책임을 알기 어려웠습니다. Storyboard·Gallery·Filmography 등의 Query·Command와 미디어 처리 서비스로 나눴습니다. 업무 상태 변경, 조회 응답 조립, 외부 파일 처리라는 변경 이유를 구분한 것입니다.

### Q052. Command·Query 분리와 별도 읽기 DB를 갖는 CQRS는 무엇이 다른가요?

현재 분리는 같은 모델과 DB에서 읽기·쓰기 책임을 나누는 수준입니다. 별도 읽기 모델과 DB를 비동기로 동기화하는 전체 CQRS를 도입한 것은 아닙니다. 클래스 이름이 Command·Query라는 이유로 더 큰 아키텍처를 구현했다고 표현하지 않습니다.

### Q053. 서비스를 여러 클래스로 나누면서 호출 관계가 더 복잡해진 비용은 없나요?

서비스 수가 늘어 호출 경로를 따라가는 비용이 생겼습니다. 대신 외부 작업과 DB 변경 위치가 드러났습니다. 책임 설명 문서와 경계 테스트로 보완했고, 단순한 기능까지 같은 방식으로 계속 쪼개야 한다고 보지는 않습니다.

### Q054. 오케스트레이션 서비스와 Transaction Service의 역할 차이는 무엇인가요?

오케스트레이터는 권한 확인·파일 작업·DB 반영·실패 보상의 순서를 조율합니다. Transaction Service는 짧은 조회·잠금·상태 변경을 담당합니다. 외부 호출을 기다리는 동안 DB 트랜잭션을 유지하지 않으려는 분리입니다.

### Q055. DTO·Entity·Service·DB에서 같은 값을 검증하는 것이 무조건 중복인가요?

무조건 중복은 아닙니다. DTO는 입력 형식, 엔티티는 생성·변경 규칙, 서비스는 권한·업무 조건, DB는 동시 요청까지 포함한 저장 무결성을 지킵니다. 같은 숫자가 반복되는 경우에는 상수와 정책을 공유하되 각 경계의 검증 목적은 유지합니다.

### Q056. 형식 검증·불변식·소유권 검사·동시성 제약을 실제 필드로 구분해 주세요.

제목의 필수·길이 형식은 DTO에서 확인하고, 엔티티에서도 유효한 제목만 저장하도록 합니다. 특정 Project를 수정할 권한은 서비스가 확인합니다. 이메일이나 참여 관계의 동시 중복은 DB UNIQUE가 막습니다.

### Q057. DTO를 record로 통일한 이유와 record만으로 깊은 불변성이 보장되지 않는 이유는 무엇인가요?

불필요한 setter를 줄이고 데이터 전달 목적을 드러내기 위해 record를 기본으로 했습니다. 필드 참조가 final이어도 내부 List나 객체는 바뀔 수 있어 방어적 복사와 요소의 변경 가능성을 함께 봐야 합니다.

### Q058. 전체 수정과 부분 수정에서 null·누락·빈 문자열을 어떻게 구분하나요?

전체 수정이라면 필수 필드 누락을 오류로 처리하고, 부분 수정은 미전달과 명시적 삭제를 구분하는 계약이 필요합니다. 일반 record의 null만으로 이 구분이 항상 가능하지는 않습니다. 현재 모든 API가 삼상태 PATCH를 구현했다고 주장하지 않습니다.

### Q059. 제목 trim과 길이 검증 순서가 DTO와 Entity에서 다르면 어떤 문제가 생기나요?

DTO가 원문 길이를 제한하고 엔티티가 trim 후 검사하면 공백이 포함된 값의 허용 여부가 달라질 수 있습니다. 정규화 시점과 길이 기준을 먼저 정하고 경계 테스트를 맞춰야 합니다. 엔티티 검증과 동일한 제목 정책이라는 이유만으로 완전히 같은 결과라고 가정하지 않습니다.

### Q060. 새 기능을 추가할 때 기존 서비스에 넣을지 분리할지 판단하는 기준은 무엇인가요?

새 기능의 변경 이유가 기존 책임과 같으면 기존 서비스에 둡니다. 권한 규칙·외부 I/O·트랜잭션 경계가 달라지면 분리를 검토합니다. 메서드 수나 줄 수 하나보다 호출 흐름과 테스트의 독립성을 기준으로 판단합니다.

근거·상세: [관련 설명·답변](../review/service/service-responsibility-map.md)

## 07. 트랜잭션 경계·외부 I/O

### Q061. S3·FFmpeg·Kafka·BCrypt를 DB 트랜잭션 밖으로 옮긴 이유는 무엇인가요?

외부 호출이 느리거나 실패하면 DB 연결과 잠금을 오래 유지할 위험이 있습니다. 외부 처리와 짧은 DB 반영을 나눠 이 위험을 줄였습니다. 대신 두 단계 사이 상태 변화와 실패 보상은 별도로 처리해야 합니다.

### Q062. 메서드에 @Transactional이 붙었다고 시작부터 항상 DB 연결을 점유하나요?

항상 그렇지는 않습니다. Connection 획득 시점은 JPA·트랜잭션 관리자와 실제 DB 접근에 따라 달라집니다. 다만 첫 DB 접근 후 외부 작업을 오래 수행하면 연결·잠금을 길게 유지할 수 있어 트랜잭션 범위를 짧게 설계했습니다.

### Q063. 외부 작업을 분리하기 전후의 Connection 점유·Lock 유지 시간을 어떻게 확인할 수 있나요?

동일한 외부 지연을 주입하고 트랜잭션 경계 테스트, Hikari active·pending, DB 잠금 시간과 요청 지연을 비교하겠습니다. 코드 분리만으로 점유 시간이 몇 퍼센트 감소했다고 주장할 수는 없습니다. 현재 근거가 경계 테스트인지 직접 측정인지 구분합니다.

### Q064. 외부에서 파일 존재를 확인한 뒤 저장하기 전까지 상태가 바뀌면 어떻게 처리하나요?

쓰기 트랜잭션에서 Job의 상태와 예상 출력 정보를 다시 확인합니다. 그러나 DB 잠금이 S3 객체를 잠그는 것은 아닙니다. 확인 직후 파일 삭제·교체 가능성까지 통제하려면 파일 키 불변성, 삭제 정책, 필요시 버전 식별을 추가 검토해야 합니다.

### Q065. 읽기 단계의 스냅샷에서 어떤 정보를 넘기며, 쓰기 단계에서 무엇을 재검증하나요?

작업 ID·소유권 판단에 필요한 값·기대 출력 키·현재 상태 등 후속 판단에 필요한 값을 전달합니다. 쓰기 단계에서는 대상을 다시 읽고 권한이나 상태를 재확인합니다. 관리 엔티티를 트랜잭션 밖으로 들고 다니며 그대로 신뢰하는 방식은 피했습니다.

### Q066. 같은 Bean 내부에서 @Transactional 메서드를 호출하면 어떤 문제가 있나요?

같은 객체 내부 호출은 보통 Spring 프록시를 통과하지 않아 기대한 전파 속성이 적용되지 않습니다. 외부 오케스트레이터가 별도 Transaction Service Bean을 호출하도록 했습니다. 테스트에서도 메서드 이름이 아니라 실제 트랜잭션 유무를 확인합니다.

### Q067. REQUIRES_NEW는 어디에 사용했고, 외부 롤백과 무관하게 무엇을 보존하나요?

만료 Refresh Token 접근 기록과 재사용 시 전체 Refresh Token 삭제에 사용했습니다. 이 보안 처리는 커밋한 뒤 외부 요청에 401을 반환해야 합니다. 외부 회전 트랜잭션의 예외로 보안 기록까지 사라지지 않도록 한 선택입니다.

### Q068. 별도 트랜잭션을 열면 추가 Connection과 잠금 측면에서 어떤 위험이 있나요?

외부 트랜잭션의 자원을 유지한 채 내부 연결을 추가로 요구할 수 있어 Pool 고갈 위험이 있습니다. 외부가 잠근 행을 내부가 갱신하면 대기도 생길 수 있습니다. 필요한 보안 처리에만 제한하고 잠금 순서와 연결 용량을 점검해야 합니다.

### Q069. BCrypt 연산 중 계정이나 비밀번호 상태가 바뀌면 로그인 후속 단계는 무엇을 검사하나요?

현재 로그인 코드는 DB에서 비밀번호 스냅샷을 읽고 트랜잭션 밖에서 BCrypt를 비교한 뒤 토큰을 발급합니다. 비교 후 비밀번호 변경·잠금 상태를 다시 확인하는 로직은 없습니다. 그런 요구가 생기면 인증 버전이나 후속 재검증을 추가해야 하며 완료된 기능처럼 말하지 않습니다.

### Q070. DB commit 응답을 못 받았을 때 성공·실패를 어떻게 판단하고 재요청하나요?

응답을 못 받았다는 사실만으로 롤백됐다고 판단하지 않습니다. 같은 requestId로 결과를 조회하거나 멱등 재요청해 기존 커밋 결과를 확인합니다. 새 ID로 무조건 다시 생성하면 이미 성공한 업무가 중복될 수 있습니다.

근거·상세: [관련 설명·답변](../review/transaction/transaction-boundary-guide.md)

## 08. 예외·ErrorCode·API 계약

### Q071. DomainException과 ErrorCode를 도입하기 전에는 어떤 문제가 있었나요?

예외 종류와 HTTP 응답이 흩어져 있고 일부는 메시지 문자열로 분기해 문구 변경에 취약했습니다. DomainException이 ErrorCode를 전달하고 공통 처리기가 일관된 응답을 만들도록 정리했습니다.

### Q072. ErrorCode를 단일 정책원으로 삼았을 때 얻은 점과 결합도가 늘어난 부분은 무엇인가요?

오류 코드·HTTP 상태·공개 메시지를 한곳에서 관리해 응답 정책의 중복을 줄였습니다. 대신 중앙 enum이 커지고 도메인과 전송 정책이 결합될 수 있습니다. 규모가 커지면 도메인별 코드와 웹 경계의 매핑 분리를 검토할 수 있습니다.

### Q073. 도메인 오류가 HTTP 상태를 알게 되는 설계에 대한 반론에는 어떻게 답하나요?

도메인을 HTTP에서 독립시키려면 도메인 오류와 웹 매핑을 분리하는 것이 대안입니다. 현재는 HTTP 중심의 작은 서비스에서 일관성을 쉽게 관리하려고 ErrorCode에 상태를 모았습니다. 계층 독립성보다 정책 관리의 단순함을 택한 절충입니다.

### Q074. 전용 예외 클래스와 ErrorCode만 받는 공통 예외를 각각 언제 사용하나요?

호출부에서 의미를 명확히 드러내거나 별도 처리가 필요한 오류는 전용 예외로 표현합니다. 공통 예외도 가능하지만 아무 ErrorCode나 전달하면 잘못된 조합이 생길 수 있습니다. 전용 타입을 유지하면서 공통 응답 경로를 재사용하는 방향을 택했습니다.

### Q075. 문자열 메시지 비교를 타입 기반 분기로 바꾸면 어떤 회귀 위험이 줄어드나요?

예외 문구를 바꾸거나 번역해도 처리 분기가 바뀌지 않습니다. 미디어 상태 충돌은 정해진 예외·코드로 구분합니다. 대신 코드 변경 자체는 클라이언트 계약 변경일 수 있어 테스트와 호환성 검토가 필요합니다.

### Q076. 400·401·403·404·409·422·500을 프로젝트에서 어떻게 구분했나요?

형식이 깨진 요청은 400, 인증 필요는 401, 권한 부족은 403, 대상 없음은 404로 구분합니다. 동시 변경·상태 충돌은 409, 프로젝트의 입력 검증 정책은 422를 사용합니다. 예상하지 못한 서버 오류는 500이며 정확한 매핑은 ErrorCode를 기준으로 확인합니다.

### Q077. Security Filter의 예외를 ControllerAdvice만으로 처리할 수 없는 이유는 무엇인가요?

보안 필터는 DispatcherServlet과 Controller보다 앞에서 동작할 수 있어 ControllerAdvice에 도달하지 않는 오류가 있습니다. EntryPoint·AccessDeniedHandler와 공통 응답 작성기를 사용해 이 경로의 401·403도 같은 형식으로 맞췄습니다.

### Q078. DB 무결성 오류가 발생하면 모두 중복 값 오류로 응답해도 되나요?

아닙니다. FK·NOT NULL·CHECK 위반도 같은 계열 예외가 될 수 있습니다. 회원가입에서는 확인 가능한 UNIQUE 제약 이름을 이메일·사용자명 중복으로 바꾸고, 알 수 없는 무결성 오류는 임의로 특정 중복 원인으로 단정하지 않습니다.

### Q079. 클라이언트 공개 오류와 서버의 상세 원인을 어떻게 분리했나요?

클라이언트에는 안정적인 코드와 공개 가능한 메시지를 반환하고 내부 예외·SQL·스택은 노출하지 않습니다. 상세 원인은 서버 로그로 추적합니다. 로그에도 토큰·서명·민감한 파일 정보가 섞이지 않도록 별도 주의가 필요합니다.

### Q080. 비즈니스 성공 응답·검증 실패·보안 실패의 형식 일관성을 어떤 테스트로 확인했나요?

Controller 검증·도메인 오류와 보안 필터의 상태 코드·응답 필드를 테스트했습니다. 성공 응답은 각 API의 정상 계약을 확인합니다. 모든 성공·실패를 똑같은 모양으로 만든 것이 아니라, 오류끼리 일관된 해석이 가능하도록 정리했습니다.

근거·상세: [관련 설명·답변](../convention/exception-and-error-code-convention.md)

## 09. 로그인·토큰·브라우저 보안

### Q081. Access Token과 Refresh Token을 왜 나누고 각각 어디에서 검증하나요?

Access Token은 일반 API 인증, Refresh Token은 재발급에 사용합니다. JWT 서명·만료와 DB의 Refresh Token 해시·폐기·만료 상태를 각각 확인합니다. 짧은 Access Token 수명과 로그인 편의를 함께 얻기 위한 분리입니다.

### Q082. Refresh Token은 왜 원문 대신 해시로 저장하며 비밀번호 해싱과 무엇이 다른가요?

DB 유출 시 원문 Refresh Token을 바로 사용하는 위험을 줄이기 위해 SHA-256 해시로 조회합니다. Refresh Token은 안전한 난수인 반면 비밀번호는 사람이 정해 추측 가능성이 높으므로 BCrypt 같은 비용 있는 해싱이 필요합니다.

### Q083. Rotation 성공 후 응답이 유실되어 이전 토큰을 다시 보내면 어떻게 되나요?

서버에서 회전이 커밋됐으면 이전 토큰은 폐기 상태입니다. 정상 사용자의 재전송이어도 현재 정책은 재사용으로 판단해 전체 Refresh Token을 삭제할 수 있습니다. 응답 유실과 탈취를 완전히 구분하는 복구 기능은 없다는 한계를 설명합니다.

### Q084. 재사용 감지 시 한 세션이 아니라 사용자의 모든 Refresh Token을 폐기한 이유는 무엇인가요?

초기에는 여러 기기의 세션을 독립적으로 관리할 요구가 작아 단순한 사용자 단위 차단을 택했습니다. 정상 기기의 재발급도 막히는 비용이 있습니다. 기기별 운영이 필요해지면 sessionId·familyId 기반의 제한적 폐기로 확장할 수 있습니다.

### Q085. Refresh Token 삭제가 이미 발급한 Access Token의 즉시 차단을 보장하나요?

아닙니다. Refresh Token 삭제는 추가 재발급을 막지만 이미 발급된 JWT는 만료 전까지 유효할 수 있습니다. 즉시 차단이 필요하면 세션·인증 버전 검사나 차단 목록이 추가로 필요합니다.

### Q086. 여러 탭에서 동시에 재발급하면 DB와 클라이언트가 각각 무엇을 책임져야 하나요?

DB는 @Version 등으로 같은 토큰이 두 번 정상 회전되는 것을 막습니다. 클라이언트는 갱신 요청 하나를 공유하고 여러 탭 간에도 조율해야 합니다. 정상 동시 요청이 재사용 감지를 유발할 수 있어 서버 정책과 클라이언트 동작을 함께 봐야 합니다.

### Q087. HttpOnly·Secure·SameSite가 방어하는 범위와 막지 못하는 공격은 무엇인가요?

HttpOnly는 JavaScript의 쿠키 값 접근, Secure는 평문 전송, SameSite는 교차 사이트 쿠키 전송을 제한합니다. 세 속성 모두 중요하지만 XSS 자체나 모든 CSRF를 없애지는 않습니다. 실제 배포의 Set-Cookie와 HTTPS도 확인해야 합니다.

### Q088. 쿠키 인증과 Authorization 헤더 인증을 함께 지원하면 우선순위와 CSRF 정책은 어떻게 되나요?

현재 Bearer 헤더를 쿠키보다 우선하는 경로가 있습니다. 명시적 헤더 토큰과 자동 전송 쿠키는 CSRF 위험이 다르지만, 현재 필터가 인증 수단별 예외까지 완성했다고 말하지 않습니다. 혼합 지원 시 두 자격 증명이 다른 사용자일 때의 계약도 확인해야 합니다.

### Q089. 현재 CSRF 제외 경로와 출처 비교 방식에서 추가 검토가 필요한 부분은 무엇인가요?

현재 로그인·가입·refresh·logout 및 내부 API 경로가 CSRF 필터에서 제외됩니다. 출처 비교도 스킴과 포트를 엄격하게 검사하는 구현은 아닙니다. 내부 HMAC 분리와 별개로 인증 경로·출처 비교·서명형 CSRF 토큰은 추가 보안 검토 대상입니다.

### Q090. 비밀번호 변경·회원 탈퇴·계정 잠금 시 기존 인증 정보는 어디까지 무효화돼야 하나요?

계정의 민감한 상태 변경 후에는 재발급뿐 아니라 기존 접근 권한을 어디까지 차단할지 정책이 필요합니다. 현재 모든 변경에 대한 즉시 Access Token 폐기가 구현된 것은 아닙니다. 비밀번호·계정 상태 버전을 인증 검증에 연결하는 방안을 검토하겠습니다.

근거·상세: [관련 설명·답변](10-auth-security-interview-qa.md)

## 10. 내부 Callback 인증·보안 경계

### Q091. 내부 Callback에는 왜 브라우저 CSRF 대신 HMAC 인증을 적용했나요?

Worker는 브라우저의 자동 쿠키 전송이 아니라 서버 간 요청을 보냅니다. 호출 주체와 본문을 HMAC으로 검증하되 브라우저용 CSRF 검사는 제외했습니다. 실제 장애도 이 두 인증 경로를 혼동해 정상 Callback을 403으로 차단한 문제였습니다.

### Q092. HMAC 입력에 timestamp·nonce·HTTP method·path·body hash를 포함한 이유는 무엇인가요?

Timestamp는 시간 범위, nonce는 반복 전송, method·path는 다른 API로의 전용, body hash는 내용 변경을 확인하기 위한 값입니다. 이들을 같은 규칙으로 연결해 서명해야 API와 Worker가 같은 요청으로 검증합니다.

### Q093. 본문을 의미상 같은 JSON으로 재직렬화하면 서명 검증에 영향이 있나요?

네, 같은 의미라도 공백·필드 순서가 바뀌면 원문 바이트의 해시가 달라질 수 있습니다. 실제 전송할 본문과 서명 계산에 쓰는 본문을 일치시켜야 합니다. 객체를 다시 직렬화해도 항상 같은 서명이 나온다고 가정하지 않습니다.

### Q094. Timestamp 허용 범위와 서버 시간 동기화는 왜 함께 봐야 하나요?

시간 오차가 크면 정상 Callback도 허용 시간을 벗어나 거절될 수 있습니다. 현재 정책은 5분 범위이며 서버 시간 동기화를 함께 확인해야 합니다. 허용 시간을 늘리는 것만으로 원인을 덮으면 replay 허용 범위도 커집니다.

### Q095. Nonce를 확인하면 동일 작업의 정상 Callback 재시도도 막히지 않나요?

같은 jobId의 업무 재시도와 동일 nonce의 인증 replay는 다릅니다. 재시도할 때 새 timestamp·nonce·서명을 만들고, API 업무 로직은 같은 결과를 멱등 처리합니다. 이전 요청의 인증 헤더를 그대로 재사용하면 거절될 수 있습니다.

### Q096. 메모리 nonce 저장소는 재시작·다중 API 인스턴스에서 어떤 한계가 있나요?

프로세스가 재시작하면 메모리 기록이 사라지고 다른 API 인스턴스와도 공유되지 않습니다. 단일 프로세스의 검사 범위를 넘어 전역 replay를 막으려면 TTL이 있는 공유 저장소나 DB 유일성 검사가 필요합니다. Sticky routing만으로 완전한 전역 방어가 되지는 않습니다.

### Q097. 내부 경로가 private network에 있으면 서명 검증을 생략해도 되나요?

생략하지 않겠습니다. Private network는 접근 범위를 줄이지만 내부 오설정이나 다른 호스트의 접근까지 업무 권한으로 인정해 주지는 않습니다. 네트워크 제한과 Callback의 인증·본문 검증을 함께 사용합니다.

### Q098. HMAC이 제공하는 인증·무결성과 HTTPS의 역할은 어떻게 다른가요?

HMAC은 공유 비밀키를 가진 주체가 해당 내용을 만들었는지 확인하고 변조를 탐지합니다. 본문을 숨기는 암호화는 아닙니다. HTTPS는 전송 구간의 기밀성과 상대 서버 확인을 제공하므로 함께 필요합니다.

### Q099. Callback 비밀키를 교체할 때 API와 Worker의 배포 순서를 어떻게 정하나요?

현재 자동 키 순환 기능을 구축한 것은 아닙니다. 확장한다면 검증 측이 일정 기간 이전·신규 키를 구분해 수용하도록 먼저 배포하고, Worker를 신규 키로 전환한 후 구키를 제거하겠습니다. 키 ID·유예 기간·재시도 메시지를 함께 검토해야 합니다.

### Q100. Callback 인증 성공과 해당 Job의 출력 파일을 변경할 권한 검증은 어떻게 다른가요?

서명이 맞아도 다른 Job의 출력 키를 반영하면 안 됩니다. API는 jobId에 저장된 예상 bucket·key·content type과 현재 상태를 확인합니다. 호출자 인증과 해당 업무 결과의 정합성 검증을 분리한 것입니다.

근거·상세: [관련 설명·답변](../problem-solving/12-production-callback-csrf-conflict.md)

## 11. Presigned URL·업로드 검증·스토리지 키

### Q101. 파일을 API 서버를 거치지 않고 S3에 직접 올리게 한 이유는 무엇인가요?

큰 파일이 API를 통과하면 네트워크와 메모리·연결 사용량이 늘어납니다. API는 업로드 권한과 목적을 확인해 URL을 발급하고 브라우저가 S3에 직접 전송하게 했습니다. API 부하는 줄지만 완료 후 실제 객체 검증은 여전히 필요합니다.

### Q102. Presign 발급과 업로드 완료 API를 분리한 이유는 무엇인가요?

권한을 부여한 것과 파일이 실제로 저장된 것은 다른 사건이기 때문입니다. Presign 단계에는 requestId와 예상 파일 위치를 남기고 완료 API에서 해당 요청과 객체를 확인한 뒤 Job을 생성합니다.

### Q103. requestId는 누가 발급하며 sourceKey·movieId와 어떻게 연결되나요?

서버가 업로드 요청을 만들면서 requestId를 발급합니다. sourceKey에 movieId·작업 종류·requestId를 포함하고 완료 요청도 저장된 요청과 대조합니다. 클라이언트가 아무 작업 ID나 파일 위치를 조합하는 것을 막는 기준입니다.

### Q104. 클라이언트가 다른 사용자의 sourceKey를 완료 요청에 넣으면 어디서 거절하나요?

현재 사용자의 Movie 편집 권한과 업로드 요청의 소유 정보를 확인하고, StorageKeyPolicy가 Movie·requestId·작업 종류에 맞는 경로인지 검사합니다. 접두사 검사만으로 사용자 권한 검증을 대신하지 않습니다.

### Q105. 파일 존재 확인만으로 실제 파일 유형·크기·내용까지 신뢰할 수 있나요?

아닙니다. 존재는 객체가 있다는 뜻이고 metadata도 실제 바이트 내용의 안전성을 보장하지 않습니다. Worker에서 크기·content type·미디어 분석을 추가합니다. 악성 파일의 모든 위험을 이 검사로 제거했다고 주장하지 않습니다.

### Q106. Content-Type 헤더와 실제 영상 형식이 다르면 어디에서 검증하나요?

Worker가 저장소 metadata와 메시지의 타입을 비교하고 FFprobe로 실제 미디어를 분석합니다. 변환 결과도 검사합니다. 브라우저가 보낸 Content-Type을 그대로 믿고 처리하지 않는다는 의미이지 모든 코덱·취약점 검사를 완료했다는 뜻은 아닙니다.

### Q107. URL 대신 storageKey를 DB에 저장하면 CDN 변경·파일 삭제·권한 검증에 어떤 이점이 있나요?

DB 값이 CDN 도메인이나 배포 주소와 결합되지 않고 삭제 대상과 소유 경로를 일관되게 표현할 수 있습니다. 응답에서 URL로 변환하는 비용이 생기고 외부 유튜브 URL은 별도 모델이 필요합니다. 키 정책과 권한 검증은 함께 사용합니다.

### Q108. Presigned URL은 만료 전 재사용되거나 공유될 수 있는데 어떤 위험이 있나요?

Presigned URL은 접근 능력을 가진 비밀 URL이므로 노출되면 유효 기간 안에 다른 주체가 사용할 수 있습니다. URL 자체가 일회용은 아닙니다. 짧은 만료·고유 키·로그 노출 제한과 완료 후 객체 변경 가능성을 검토해야 합니다.

### Q109. 완료 API에 같은 requestId지만 다른 파일 정보가 오면 어떻게 처리하나요?

같은 requestId에 다른 sourceKey·contentType 등이 오면 정상 중복으로 취급하지 않고 거절합니다. 같은 요청 내용이면 기존 Job을 반환합니다. 요청 ID만 같다고 무조건 성공시키면 잘못된 파일 연결을 숨길 수 있습니다.

### Q110. 경로 탐색·절대 경로·외부 URL·타 사용자 키를 어떤 규칙으로 거부하나요?

서버가 만든 경로 형식과 대상 ID를 검사하고 URL·절대 경로·역슬래시·상위 경로 탐색 같은 입력을 거부합니다. 로컬 저장소에서도 정규화된 경로가 허용 루트 안에 남는지 확인해야 합니다. 문자열 필터 한 번으로 모든 저장소 권한을 대신하지는 않습니다.

근거·상세: [관련 설명·답변](../decisions/trailer-storage-key-policy.md)

## 12. 파일 생명주기·삭제·보상

### Q111. 파일 삭제를 DB commit 이후로 옮긴 이유를 롤백 상황으로 설명해 주세요.

DB 반영 전에 파일을 지우면 후속 DB 롤백 시 데이터는 파일을 참조하지만 실제 파일은 사라집니다. DB에서 참조 제거가 커밋된 뒤 파일을 지우게 바꿨습니다. 대신 커밋 후 삭제 실패로 남는 고아 파일을 관리해야 합니다.

### Q112. AFTER_COMMIT 이벤트가 실행되기 전에 프로세스가 죽으면 파일 삭제는 어떻게 되나요?

삭제 이벤트가 프로세스 메모리에만 있으면 유실되어 파일이 남을 수 있습니다. AFTER_COMMIT은 실행 시점을 정하지 영속적인 전달을 보장하지 않습니다. 삭제 작업 테이블이나 정합성 점검·재시도는 향후 보완 방향입니다.

### Q113. 일반 애플리케이션 이벤트와 Outbox의 내구성은 무엇이 다른가요?

일반 이벤트는 프로세스 종료 후 다시 전달할 기록이 없을 수 있습니다. Outbox는 업무 변경과 함께 DB에 발행할 내용을 남겨 재조회할 수 있습니다. 파일 삭제에도 같은 내구성이 필요해지면 별도 삭제 Outbox를 검토하겠습니다.

### Q114. 파일 삭제 실패 로그가 남았다고 복구까지 완료된 것인가요?

아닙니다. 현재 리스너는 삭제 실패를 ERROR 로그로 남기고 다음 파일 처리를 이어갑니다. 자동 재시도 큐나 완료 추적까지 제공하지는 않습니다. 기록은 탐지 근거이며 잔여 파일 확인과 복구는 별도로 필요합니다.

### Q115. 여러 파일 중 하나의 삭제가 실패하면 나머지 파일 처리는 어떻게 하나요?

파일별로 예외를 처리해 하나의 실패가 나머지 삭제를 막지 않도록 했습니다. 다만 실패한 파일은 남기 때문에 로그와 대상 키를 기준으로 후속 확인해야 합니다. 전체 삭제의 원자성을 보장하는 방식은 아닙니다.

### Q116. 새 파일 업로드 성공 후 DB 저장이 실패하면 무엇을 보상하며, 보상도 실패하면 어떻게 하나요?

새 파일 저장 후 DB 연결·반영이 실패하면 새 파일을 최선 노력으로 삭제합니다. 보상 삭제도 실패할 수 있으므로 완전한 원자성을 제공하지는 않습니다. 그 경우 고아 파일로 남아 별도 정리 대상이 됩니다.

### Q117. 하나의 파일을 여러 Card나 참여자가 참조한다면 삭제 가능 여부를 어떻게 판단하나요?

삭제할 참조를 제거하는 것과 실제 파일을 지우는 것은 구분해야 합니다. 남은 참조가 있는지 확인하거나 파일 소유·공유 정책을 명시해야 합니다. Card 교체의 사용 키 비교를 서비스 전체의 공유 파일 참조 카운팅으로 일반화하지 않습니다.

### Q118. HLS 재생목록만 삭제하면 Segment 파일과 썸네일도 정리되나요?

아닙니다. 현재 S3StorageService.delete는 전달받은 key의 객체 한 개를 삭제합니다. index.m3u8만 전달하면 Segment가 자동으로 지워지지 않습니다. HLS 출력 묶음의 manifest나 검증된 전용 prefix를 기준으로 정리하는 보완이 필요합니다.

### Q119. DB에는 참조가 없지만 S3에는 남은 고아 파일을 어떻게 탐지하고 안전하게 정리할 건가요?

추가 설계라면 저장 객체와 DB 참조를 비교하되 진행 중 업로드·Job의 객체를 제외하고 충분한 유예 시간을 두겠습니다. 바로 삭제하지 않고 후보 기록과 재확인 단계를 두는 것이 안전합니다. 현재 자동 전수 정리 기능을 구현한 것은 아닙니다.

### Q120. 회원 탈퇴·Movie 삭제·영상 교체 시 파일 수명주기의 책임이 어떻게 다른가요?

탈퇴는 개인 프로필·참여 이력의 생명주기, Movie 삭제는 공유 작품의 별도 관리 행위입니다. 영상 교체는 새 참조 커밋 후 이전 파일을 정리합니다. 세 작업을 같은 cascade나 일괄 파일 삭제로 처리하면 다른 사용자의 자료를 지울 수 있습니다.

근거·상세: [관련 설명·답변](../problem-solving/02-storage-key-and-file-lifecycle.md)

<a id="section-13"></a>

## 13. 영상 인코딩·HLS·Worker 자원

### Q121. MP4 원본을 그대로 제공하지 않고 HLS로 변환한 이유와 비용은 무엇인가요?

HLS는 영상을 재생목록과 작은 구간 파일로 제공해 스트리밍 처리에 활용할 수 있습니다. 대신 변환 CPU, 추가 객체, 관리와 요청 비용이 생깁니다. 현재 단일 720p preset을 여러 화질의 적응형 스트리밍까지 구현한 것으로 설명하지 않습니다.

### Q122. HLS 재생목록과 Segment는 각각 무엇이며 모두 업로드되기 전에 공개하면 어떤 문제가 있나요?

재생목록은 재생할 Segment 위치와 순서를 안내하고 Segment는 실제 영상 구간입니다. 필요한 파일이 빠진 채 공개되면 재생 중 오류가 날 수 있습니다. Worker는 출력 검증·업로드 뒤 Callback으로 공개 결과를 반영하는 흐름입니다.

### Q123. 720p·비트레이트·오디오 설정 등 preset은 어떤 요구사항으로 선택했나요?

현재 preset은 일관된 출력 형식으로 영상 처리 흐름을 검증하기 위한 초기 선택입니다. 여러 화질·비트레이트의 화질과 비용을 비교해 최적값을 찾았다는 근거는 없습니다. 실제 사용자 환경과 비용 데이터를 모아 조정할 대상으로 봅니다.

### Q124. FFprobe와 FFmpeg의 역할은 어떻게 다르며 사전 검사가 필요한 이유는 무엇인가요?

FFprobe는 길이·스트림·코덱 같은 미디어 정보를 읽고, FFmpeg는 실제 변환을 수행합니다. 변환 전에 크기·시간·형식을 검사하면 처리할 수 없는 파일에 많은 자원을 쓰는 것을 줄일 수 있습니다.

### Q125. 손상된 파일·지나치게 긴 영상·지원하지 않는 코덱은 어떻게 처리하나요?

metadata·미디어 분석·출력 검증에서 정책 위반을 구분하고, 같은 입력을 반복해도 해결되지 않는 오류는 영구 오류로 처리합니다. 변환 프로세스 실패나 timeout도 기록합니다. 모든 미디어 오류를 네트워크 재시도처럼 처리하지 않습니다.

### Q126. 인코딩 과정에서 CPU·메모리·디스크 중 무엇이 먼저 병목인지 어떻게 확인하나요?

단계별 소요 시간과 실패 코드, CPU·메모리·디스크 여유를 같은 시각에 봅니다. transcode만 길면 CPU·코덱을, download·upload가 길면 저장소와 네트워크를 봅니다. 병목을 확인하기 전에 Worker 수만 늘리지 않습니다.

### Q127. 한 Worker에서 FFmpeg가 여러 개 실행되면 어떤 자원 제한이 필요하나요?

전체 FFmpeg 동시 실행 수와 프로세스별 스레드, 작업 파일 크기·디스크 한도를 함께 제한해야 합니다. Listener concurrency 1만으로 Retry Consumer와 복구 스케줄러까지 포함한 전역 실행 제한이 되지는 않습니다. 별도 실행 용량 제어는 점검 대상입니다.

### Q128. 작업 디렉터리는 어떻게 나누며 실패·강제 종료 후 임시 파일은 어떻게 관리하나요?

Job별 작업 디렉터리를 사용하고 정상 예외 흐름의 finally에서 정리합니다. OS 강제 종료나 정리 실패 시에는 남을 수 있습니다. 시작 시 또는 별도 주기로 활성 lease와 충돌하지 않는 잔여 파일을 정리하는 정책은 추가 검토가 필요합니다.

### Q129. FFmpeg 실행 인자에 사용자 입력을 넣을 때 명령 삽입을 어떻게 방지하나요?

현재 FFmpeg는 정해진 preset의 인자 리스트를 ProcessBuilder에 전달하며 셸 명령 문자열로 조합하지 않습니다. 파일 경로와 입력 형식도 검증합니다. 셸을 쓰지 않아도 임의 옵션·경로·미디어 처리 취약점 위험까지 없어지는 것은 아닙니다.

### Q130. 관리형 영상 변환 서비스 대신 직접 Worker를 운영한 이유와 전환 기준은 무엇인가요?

변환 과정·장애·자원 사용을 직접 제어하고 학습하려고 Worker를 선택했습니다. 관리형 서비스와의 비용·운영 시간을 정량 비교한 것은 아닙니다. 사용자 규모와 운영 부담이 늘면 작업당 비용·품질·복구 기능을 기준으로 전환을 검토하겠습니다.

근거·상세: [관련 설명·답변](../problem-solving/05-media-encode-outbox-and-worker.md)

## 14. Kafka·Outbox·전달 보장

### Q131. DB 저장과 Kafka 발행 사이에서 어떤 장애가 가능하며 Outbox가 어떻게 대응하나요?

DB 저장과 메시지 전송은 다른 시스템이므로 한쪽만 성공할 수 있습니다. 작업과 발행 요청을 같은 DB 트랜잭션으로 저장해 커밋 후 서버가 종료돼도 발행할 근거를 남겼습니다. 전송 결과 저장 사이의 중복은 Inbox로 대응합니다.

### Q132. Job과 Outbox를 같은 트랜잭션에서 저장하지 않으면 어떤 불일치가 생기나요?

Job만 저장되면 Worker에 전달되지 않는 작업이 남고, 메시지만 전달되면 Worker가 API에서 찾을 수 없는 작업을 실행할 수 있습니다. 두 DB 레코드를 함께 저장해 발행 대상의 근거와 업무 상태가 함께 생기도록 했습니다.

### Q133. Kafka 발행 성공 후 PUBLISHED 저장이 실패하면 어떻게 되나요?

Kafka에는 메시지가 있지만 Outbox는 완료되지 않아 lease 만료 후 재발행될 수 있습니다. 이를 실패가 전혀 없었던 것으로 처리하지 않고 중복 가능성을 인정했습니다. 같은 jobId를 Worker가 다시 확인해 결과 중복을 줄입니다.

### Q134. KafkaTemplate.send의 Future 성공과 Worker 작업 성공은 어떻게 다른가요?

Future 성공은 설정된 Broker 확인 수준에서 발행 결과를 받은 것입니다. Worker가 받았는지, 파일 변환과 Callback이 성공했는지는 알 수 없습니다. 업무 완료는 Job의 최종 상태와 Worker·Callback 기록으로 확인합니다.

### Q135. Publisher에서 기다리다 timeout이 나면 Kafka 발행 실패를 확정할 수 있나요?

확정할 수 없습니다. 기다리는 쪽이 timeout이 났어도 비동기 전송이 나중에 성공할 수 있습니다. 실패 상태를 기록해 재시도하되 중복이 발생할 수 있다는 전제로 처리합니다. timeout과 외부 작업 취소는 같은 의미가 아닙니다.

### Q136. At-least-once와 업무 결과의 멱등성은 어떻게 다른가요?

At-least-once는 전달이 반복될 수 있는 성질이고 멱등성은 반복된 요청이 업무 결과를 중복 변경하지 않는 성질입니다. 전달 자체를 한 번으로 만들었다고 말하지 않고, DB와 상태 검증으로 결과를 보호했다고 설명합니다.

### Q137. Topic·Partition·Key·Consumer Group을 현재 인코딩 흐름에 대입해 설명해 주세요.

요청 Topic의 데이터를 Partition으로 나누고 jobId를 Key로 보냅니다. 같은 Worker group의 Consumer들이 Partition을 분담합니다. Offset은 레코드 위치이며 업무 식별자인 jobId와 다릅니다. Retry·DLT는 별도의 처리 경로입니다.

### Q138. acks·복제 수·최소 ISR 설정은 각각 무엇을 보장하고 무엇을 보장하지 않나요?

acks는 어떤 Broker 확인을 기다릴지, 복제 수는 복사본 개수, 최소 ISR은 쓰기를 허용할 동기화 상태의 기준입니다. 단일 Broker에서 acks를 강화해도 다중 Broker 내구성이 생기지는 않습니다. 현재 직접 만든 Producer 설정과 실제 기본값을 함께 확인해야 합니다.

### Q139. Outbox Polling 대신 CDC를 선택할 조건과 추가 운영 비용은 무엇인가요?

Polling 부하와 전달 지연이 실제 병목으로 드러나면 CDC를 검토할 수 있습니다. 대신 Connector, 변경 로그 보존·권한·장애 복구를 관리해야 합니다. 현재는 스케줄 기반 Polling이고 CDC 도입 성과가 있는 것은 아닙니다.

### Q140. 여러 Publisher가 동시에 실행되거나 한 배치의 발행 시간이 길어지면 lease는 안전한가요?

행 잠금으로 선점하고 lease를 기록해 중복 점유를 제한합니다. 하지만 배치를 먼저 잡고 순차 전송하면 뒤쪽 항목의 lease가 실행 전에 소진될 수 있습니다. 배치 크기·발행 시간·권한 재검증을 함께 검토해야 하며 lease만으로 항상 안전하다고 말하지 않습니다.

## 15. Inbox·Callback·최종 상태

### Q141. 같은 jobId가 여러 번 들어와도 안전하도록 Inbox가 어떤 정보를 보관하나요?

Inbox는 jobId와 요청 내용, 처리 상태·lease·시도·실패 정보를 저장합니다. 다시 받은 작업은 신규 실행·처리 중·Callback-only·종료를 구분합니다. 메모리만이 아니라 DB 기록을 사용해 재시작과 여러 Worker에서도 판단할 근거를 남겼습니다.

### Q142. 처음 도착한 두 메시지가 동시에 Inbox를 만들려고 하면 어떻게 처리하나요?

존재 여부 조회만으로는 둘 다 새 작업이라고 판단할 수 있습니다. DB의 jobId 기본 키가 중복 INSERT를 막고, 충돌한 경로는 별도 트랜잭션에서 기존 기록을 다시 확인합니다. 같은 트랜잭션에서 실패한 상태를 계속 재사용하지 않습니다.

### Q143. 같은 jobId에 다른 payload가 들어오면 왜 정상 중복으로 취급하면 안 되나요?

같은 작업 번호로 다른 입력을 처리하면 기존 결과를 잘못 재사용하거나 덮어쓸 수 있습니다. 현재는 Kafka key와 저장 payload의 일치도 확인합니다. 직렬화 변화가 정상 재전달을 다르게 보이게 할 수 있는 한계도 있습니다.

### Q144. PROCESSING·OUTPUT_UPLOADED·FAILURE_PENDING·DONE·FAILED는 각각 어떤 복구 지점을 뜻하나요?

PROCESSING은 처리 중, OUTPUT_UPLOADED는 출력 저장 후 통지 단계, FAILURE_PENDING은 실패 보고 대기입니다. DONE·FAILED는 최종 상태입니다. 체크포인트가 있어야 재실행할 일과 이미 끝난 일을 구분할 수 있습니다.

### Q145. 출력 업로드 성공 후 Callback만 실패하면 왜 재인코딩하지 않아도 되나요?

출력 업로드 완료를 Inbox에 기록했으면 남은 업무는 API에 결과를 알리는 것입니다. 이 경우 Callback-only로 이어가 불필요한 CPU·업로드 비용을 피합니다. 업로드 직후 체크포인트 저장 전에 종료되면 같은 보장이 성립하지 않을 수 있습니다.

### Q146. 동일 DONE Callback 반복과 동시에 도착한 DONE 요청 둘은 처리 결과가 항상 같나요?

순차 중복은 기존 DONE과 출력 정보를 확인하고 결과를 유지할 수 있습니다. 동시 요청은 둘 다 미완료를 읽어 경쟁하므로 @Version 충돌로 한 요청이 409를 받을 수 있습니다. 멱등 결과 유지와 모든 요청의 즉시 성공 응답은 다릅니다.

### Q147. DONE 뒤 FAILED와 FAILED 뒤 DONE을 거부한 이유와 그 정책의 비용은 무엇인가요?

이미 확정한 최종 결과를 늦은 반대 통지가 뒤집지 못하게 하려는 정책입니다. 대신 timeout으로 실패한 뒤 실제 출력이 늦게 완성돼도 같은 Job을 DONE으로 바꾸지 못합니다. 새 요청이나 별도 정리·복구 절차가 필요합니다.

### Q148. REQUESTED에서 PROCESSING을 거치지 않고 DONE으로 바뀌는 것은 왜 허용하나요?

시작 통지를 놓쳐도 실제 완료 결과가 유효하면 반영할 수 있어야 하기 때문입니다. Job과 예상 출력·타임스탬프를 검증한 뒤 REQUESTED에서 바로 DONE을 허용합니다. 모든 중간 상태 통지가 반드시 전달된다는 가정은 두지 않았습니다.

### Q149. 같은 Movie에 서로 다른 두 Job의 Callback이 역순으로 오면 현재 Job별 검증만으로 충분한가요?

충분하다고 볼 수 없습니다. 서로 다른 Job은 각자의 상태 검사에 통과해 같은 Movie 결과를 순서와 다르게 바꿀 수 있습니다. 현재 검사만으로 최신 Job 우선 정책을 보장한다고 말하지 않고, 활성 Job·세대 번호 같은 추가 조건을 검토해야 합니다.

### Q150. Inbox를 정리한 뒤 오래된 메시지가 다시 오면 어떤 검증 기록이 남아 있나요?

Inbox 삭제 후에는 Worker의 이전 처리 기록이 없어질 수 있습니다. API Job이나 Outbox도 보존 기간에 따라 남지 않을 수 있어 오래된 재생을 무조건 안전하다고 볼 수 없습니다. Kafka 보존·수동 재처리 범위와 멱등 기록 보존을 함께 정해야 합니다.

근거·상세: [관련 설명·답변](11-kafka-operations-interview-qa.md)

## 16. Retry·Timeout·Lease·장애 복구

### Q151. 재시도해도 되는 오류와 재시도하면 안 되는 오류를 어떻게 구분했나요?

일시적인 통신 장애나 외부 서비스의 5xx처럼 시간이 지나면 회복될 가능성이 있는 오류는 재시도 대상으로 봤습니다. 잘못된 메시지 형식, 지원하지 않는 작업, 복구할 수 없는 입력 오류는 같은 요청을 반복해도 해결되지 않으므로 영구 실패로 분류했습니다. 인증·권한 오류도 무조건 재시도하지 않고 설정 문제인지 먼저 확인해야 합니다.

### Q152. Outbox 총 8회와 Worker 총 5회는 각각 어디서 적용되며 최초 시도를 포함하나요?

Outbox의 8회는 API에서 Kafka로 메시지를 발행하는 단계이고, Worker의 5회는 메시지를 받아 처리하는 Retry Topic 경로에 적용됩니다. 둘 다 최초 시도를 포함합니다. 별도 복구 스케줄러까지 포함해 작업 전체가 반드시 5회 이하라고 보장하는 것은 아닙니다.

### Q153. 정책 문서의 단계별 긴 재시도 일정 중 현재 구현된 부분과 미구현 부분은 무엇인가요?

현재 Worker Retry Topic은 최초 처리 후 1초·2초·4초·8초 간격으로 재시도합니다. Outbox는 별도의 지수 백오프를 사용합니다. 문서에 적은 외부 호출 10초·30초·2분·10분, Callback 전용 추가 30분, 인코딩 1분 후 한 번 재실행은 목표 정책이므로 모두 구현된 것으로 설명하지 않겠습니다.

### Q154. 재시도 대기 중 DB Connection과 스레드를 점유하는지 구현 경로별로 설명해 주세요.

Outbox는 다음 시도 시각을 DB에 저장하므로 그 시각까지 DB 연결을 잡고 기다리지 않습니다. Kafka 발행 결과를 기다리는 동안에는 발행 스레드는 점유하지만 DB 트랜잭션 밖입니다. Retry Topic도 긴 DB 트랜잭션을 유지하는 방식은 아니지만, 실제 외부 호출과 FFmpeg 실행 중에는 해당 처리 스레드가 사용됩니다.

### Q155. FFmpeg timeout·Inbox lease·poll interval·Job timeout의 관계를 어떻게 정했나요?

FFmpeg 자체 실행 제한은 2시간, Inbox 처리 권한의 유효 시간은 3시간, API Job 만료는 4시간 30분으로 두었습니다. 다만 현재 max.poll.interval은 3시간이고 문서의 목표인 4시간과 차이가 있습니다. 다운로드·업로드·재시도까지 포함한 최대 처리 시간을 다시 계산해야 하므로, 모든 제한 시간이 충분히 정렬됐다고 말하지 않겠습니다.

### Q156. Retry Topic·복구 스케줄러·라이브러리 재시도가 겹치면 전체 시도 수를 어떻게 제한하나요?

현재는 발행 시도, Retry Topic 처리, 만료 작업 복구가 각각 관리되므로 하나의 전체 시도 한도로 합쳐져 있지 않습니다. 라이브러리 내부 재시도까지 겹치면 실제 호출은 더 많아질 수 있습니다. 보완한다면 작업별 누적 시도 수와 전체 마감 시각을 저장하고, 모든 진입 경로에서 같은 기준을 확인하겠습니다.

### Q157. lease 만료 후 이전 Worker가 계속 실행하면 어떤 문제가 있고 Fencing은 무엇을 해결하나요?

처리 권한이 만료돼 다른 Worker가 작업을 가져가도 이전 Worker의 프로세스가 자동으로 멈추는 것은 아닙니다. Fencing은 새 작업자에게 더 큰 번호를 부여하고 저장 대상이 오래된 번호의 쓰기를 거부하는 방식입니다. 현재 lease와 버전 검사만으로 DB와 S3의 모든 오래된 쓰기를 차단한다고 보장하지는 않습니다.

### Q158. Worker 강제 종료를 어느 지점에 주입했으며 자동으로 복구되지 않는 구간은 어디인가요?

테스트에서는 처리 중 상태나 결과 업로드 후 상태를 남기고, 시간이 지난 뒤 복구 경로가 이어지는 상황을 재현했습니다. 실제 EC2 프로세스를 모든 단계에서 강제 종료한 실험까지 완료한 것은 아닙니다. 메모리에만 있던 이벤트, 남은 임시 파일, 이미 종료된 API Job과 충돌하는 복구는 별도로 확인할 구간입니다.

### Q159. DLT나 Outbox DEAD를 다시 처리하기 전에 확인해야 할 조건은 무엇인가요?

실패 원인이 해결됐는지, 원본 파일이 남아 있는지, 같은 작업이 아직 실행 중인지, API Job의 현재 상태가 무엇인지부터 확인합니다. 이미 종료된 작업의 결과를 임의로 되돌리거나 전체 DLT를 무조건 재전송하지 않습니다. 재처리가 기존 정책과 충돌하면 새 작업으로 요청하고 기존 실패 기록과 연결해 추적하는 편이 안전합니다.

### Q160. Circuit Breaker·Backoff·Timeout·동시 실행 제한은 각각 어떤 문제를 해결하나요?

Timeout은 한 번의 호출을 언제 포기할지, Backoff는 실패 후 다음 시도까지 얼마나 기다릴지를 정합니다. Circuit Breaker는 계속 실패하는 대상에 대한 호출을 잠시 막고, 동시 실행 제한은 한꺼번에 쓰는 자원을 제한합니다. 역할이 서로 다르며, 현재 프로젝트에 Circuit Breaker까지 적용한 것은 아닙니다.

## 17. Flyway·DB 소유권·Constraint

### Q161. Hibernate 자동 생성 대신 Flyway와 validate를 선택한 이유는 무엇인가요?

Hibernate 자동 생성만 사용하면 스키마가 언제 어떤 이유로 바뀌었는지 관리하기 어렵습니다. Flyway SQL로 변경 순서와 이력을 남기고 Hibernate는 매핑이 맞는지 확인하도록 역할을 나눴습니다. 직접 SQL을 관리하는 비용이 늘지만 변경을 검토하고 같은 순서로 재현할 수 있다는 장점을 선택했습니다.

### Q162. 보존할 운영 데이터가 없는 상태와 이미 운영 중인 상태의 초기 Migration 전략은 어떻게 다른가요?

보존할 운영 데이터가 없었기 때문에 빈 DB에 V1부터 적용하는 방식을 선택했습니다. 이미 운영 중인 DB라면 실제 스키마와 데이터를 조사하고 백업·호환성·기존 버전 등록 전략을 정해야 합니다. 단순히 초기 SQL을 기존 DB에 다시 실행하거나 데이터를 지우는 방식으로 접근하면 안 됩니다.

### Q163. 적용된 Migration을 고치면 안 되는 이유와 잘못된 Migration을 수정하는 방법은 무엇인가요?

적용된 파일을 수정하면 DB에 기록된 체크섬과 달라지고 환경별로 같은 버전이 다른 의미를 갖게 됩니다. 이미 배포한 변경을 바로잡을 때는 후속 Migration을 추가합니다. 실패한 DDL이 일부 남았을 가능성도 확인해야 하며, repair만 실행해서 실제 스키마까지 복구됐다고 생각하면 안 됩니다.

### Q164. validate가 UNIQUE·CHECK·Index까지 모든 스키마 정책을 완전히 검증하나요?

아닙니다. Hibernate validate는 주로 엔티티가 기대하는 테이블·컬럼·타입 등의 매핑을 확인하지만, 모든 UNIQUE·CHECK·인덱스 정책을 완전히 비교하는 도구는 아닙니다. 따라서 Migration 결과를 조회하고 실제로 잘못된 데이터를 넣었을 때 DB가 거부하는지도 테스트했습니다.

### Q165. Reference Data와 개발 Fixture를 분리한 이유와 각 실행 환경의 차이는 무엇인가요?

장르처럼 서비스 실행에 필요한 기준 데이터와 개발 편의를 위한 가짜 사용자·영화 데이터를 구분했습니다. 운영 기준 데이터는 변경 이력과 함께 관리하고 개발 Fixture는 명시한 개발·테스트 환경에서만 사용하도록 했습니다. 운영에서 임의의 테스트 데이터가 자동 생성되지 않게 하는 것이 목적입니다.

### Q166. MySQL에서 확인한 UUID·TEXT 매핑 문제는 무엇이었고 H2에서는 왜 놓칠 수 있었나요?

MySQL 검증 과정에서 UUID의 BINARY(36) 표현과 VARCHAR(36) 매핑을 맞추고, 메시지 payload가 TINYTEXT가 아닌 필요한 TEXT 타입으로 생성되도록 정리했습니다. H2는 타입 처리와 길이 제한, 방언이 MySQL과 같지 않아 이런 차이를 놓칠 수 있습니다. 정확한 재현 조건은 당시 Migration과 테스트 기록을 함께 제시하겠습니다.

### Q167. Nullable 컬럼이 포함된 UNIQUE에서 어떤 중복이 허용될 수 있나요?

MySQL UNIQUE에는 NULL을 포함한 행이 여러 개 들어갈 수 있습니다. 예를 들어 두 컬럼의 조합이 유일해야 해도 한 컬럼이 NULL이면 기대한 중복 방지가 되지 않을 수 있습니다. NULL이 실제로 필요한지부터 정하고, 필요한 경우 별도 모델링이나 조건을 표현하는 제약을 검토해야 합니다.

### Q168. FK의 ON DELETE와 JPA cascade·orphanRemoval은 왜 별도로 검토해야 하나요?

JPA cascade와 orphanRemoval은 엔티티를 통해 삭제할 때의 동작이고, FK의 ON DELETE는 DB가 관계를 처리하는 규칙입니다. 직접 SQL이나 벌크 삭제는 JPA의 연관관계 삭제 과정을 거치지 않을 수 있습니다. 따라서 영화와 참여 이력처럼 함께 삭제할 데이터와 독립적으로 남길 데이터를 먼저 정하고 두 계층을 함께 검토했습니다.

### Q169. 모든 컬럼에 NOT NULL과 모든 관계에 FK를 추가하지 않은 이유는 무엇인가요?

아직 값이 정해지지 않은 상태를 표현해야 하는 컬럼에는 NULL이 필요하고, 다른 서비스 DB의 식별자는 서비스 간 FK로 묶지 않는 정책을 선택했습니다. 또 정렬 컬럼처럼 JPA가 저장 과정에서 나중에 채우는 값은 중간 SQL까지 확인해야 합니다. 제약은 많을수록 좋은 것이 아니라 실제 불변 규칙을 표현해야 합니다.

### Q170. API와 Worker Migration의 버전·이력·권한을 왜 독립적으로 관리하나요?

API와 Worker는 같은 MySQL 서버를 사용해도 서로 다른 논리 DB와 계정으로 분리했습니다. 각 서비스가 자기 테이블과 Flyway 이력만 관리하게 해 한쪽의 변경이 다른 쪽 스키마를 직접 바꾸지 않도록 했습니다. 버전 번호도 독립적이며 DB 간 직접 조회 대신 API와 메시지 계약으로 연결합니다.

## 18. DB 동시성·잠금·트랜잭션 실험

### Q171. 중복 확인을 통과한 두 요청이 동시에 INSERT하면 마지막 방어선은 무엇인가요?

DB UNIQUE 제약이 마지막 방어선입니다. 애플리케이션의 사전 조회와 INSERT 사이에는 다른 요청이 들어올 수 있으므로 조회만으로 중복을 막을 수 없습니다. 충돌은 해당 제약의 의미에 맞는 예외로 변환하되, 모든 DB 오류를 중복 오류로 처리하지 않도록 구분했습니다.

### Q172. 낙관적 락과 비관적 락을 각각 어느 기능에 적용했고 왜 그렇게 선택했나요?

RefreshToken과 MediaEncodeJob 등에는 버전 검사를 사용해 동시에 수정한 요청의 충돌을 탐지하도록 했습니다. Outbox나 Inbox의 작업 선점처럼 같은 대상을 한 처리자에게 배정해야 하는 구간에서는 잠금 조회와 짧은 트랜잭션을 활용했습니다. 버전 검사와 선점 잠금은 목적이 다르므로 함께 사용하는 엔티티도 있습니다.

### Q173. @Version이 있으면 관련된 모든 엔티티와 외부 파일의 경쟁도 막히나요?

아닙니다. @Version은 해당 엔티티의 갱신 충돌을 탐지하는 장치이며 다른 행이나 S3 파일까지 함께 보호하지 않습니다. 특히 외부 작업 후 최신 엔티티를 다시 읽으면 오래된 작업인지 별도로 판단해야 합니다. 관련 요청 번호, 현재 상태, 파일 소유 관계와 같은 업무 조건도 확인해야 합니다.

### Q174. 낙관적 락 재시도를 실패한 기존 트랜잭션에서 하면 안 되는 이유는 무엇인가요?

충돌한 트랜잭션은 롤백이 필요하고 영속성 컨텍스트에도 오래된 상태가 남아 있을 수 있습니다. 새 트랜잭션에서 최신 데이터를 다시 읽고 업무 조건부터 판단해야 합니다. 사용자의 의도가 여전히 유효한 경우에만 제한적으로 재시도하며, 외부 부수 효과도 중복되지 않는지 확인해야 합니다.

### Q175. 같은 DB를 갱신하는 벌크 쿼리와 JPA 변경 감지는 어떻게 충돌할 수 있나요?

벌크 쿼리는 DB를 직접 바꾸기 때문에 이미 조회한 엔티티가 변경 사실을 모를 수 있습니다. 이후 오래된 객체를 사용하거나 flush하면 기대하지 않은 갱신이 발생할 수 있고, 벌크 쿼리가 버전을 어떻게 처리하는지도 별도 문제입니다. 실행 전 flush와 실행 후 clear 또는 재조회 시점을 명시해야 합니다.

### Q176. REPEATABLE READ에서 일반 조회·잠금 조회·UPDATE의 관측 결과는 어떻게 다를 수 있나요?

InnoDB의 REPEATABLE READ에서 일반 SELECT는 일관된 스냅샷을 읽지만, 잠금 조회와 UPDATE는 같은 방식의 과거 스냅샷 조회가 아닙니다. 따라서 같은 트랜잭션 안에서도 일반 조회에서 본 값과 잠금 후 확인한 값이 달라질 수 있습니다. 이 차이를 이해하고 상태 변경 직전의 조건을 확인해야 합니다. [MySQL 공식 설명](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

### Q177. Index가 잠금 범위에 영향을 주는 이유와 Gap Lock 때문에 생길 수 있는 문제는 무엇인가요?

InnoDB는 인덱스 레코드와 범위를 기준으로 잠금을 잡기 때문에 탐색에 사용한 인덱스가 잠금 범위에도 영향을 줍니다. 범위 조회의 Gap Lock은 조건 사이에 새 행을 넣는 요청을 기다리게 할 수 있습니다. 검색이 느린 문제뿐 아니라 잠금 대기까지 고려해 실제 실행 계획과 격리 수준을 함께 확인합니다.

### Q178. Deadlock과 Lock Timeout을 어떻게 구분하고 어떤 범위를 재시도하나요?

Deadlock은 트랜잭션들이 서로 가진 잠금을 기다리는 순환이고, Lock Timeout은 잠금을 정해진 시간 안에 얻지 못한 상황입니다. MySQL에서 두 오류의 롤백 범위가 항상 같다고 가정하면 안 됩니다. 애플리케이션에서는 실패한 작업을 종료하고, 멱등성이 확보된 업무 단위만 새 트랜잭션에서 제한적으로 재시도하는 방향으로 다룹니다.

### Q179. REQUIRES_NEW 테스트에서 외부 롤백 후 내부 기록이 남았음을 어떻게 확인했나요?

외부 트랜잭션 안에서 별도 빈의 REQUIRES_NEW 메서드를 호출해 만료·폐기 기록을 저장한 뒤 외부 작업에 실패를 발생시켰습니다. 이후 독립된 조회로 외부 변경은 되돌아갔지만 내부 기록은 남았는지 확인했습니다. 같은 클래스 내부 호출만 사용하면 프록시를 거치지 않을 수 있어 빈 경계도 중요합니다.

### Q180. 동시성 테스트가 실제로 겹쳐 실행됐고 단순 순차 실행이 아님을 어떻게 증명했나요?

여러 스레드를 시작했다는 사실만으로는 부족하므로 시작 지점을 맞추는 동기화 장치와 스레드별 트랜잭션을 사용합니다. 각 요청의 성공·충돌 결과뿐 아니라 최종 행 수와 상태도 확인했습니다. 테스트마다 동시 구간을 어떻게 만들었는지 코드를 보여주며, 모든 실제 스케줄링 경우를 다 검증했다고 주장하지는 않겠습니다.

## 19. API 성능·N+1·k6 측정 신뢰성

### Q181. Storyboard SQL 24회가 어떻게 발생했고 3회로 줄어든 이유를 실제 조회 흐름으로 설명해 주세요.

초기 기록에서는 소유자 확인에 Person과 User 조회 2회, 본문 Person 조회 1회, Project 목록 조회 1회, 20개 Project의 Scene 조회 20회로 총 24회였습니다. Fetch Join으로 본문 Person·Project·Scene을 한 번에 가져와 소유자 확인 2회와 합쳐 3회로 줄였습니다. 로그인 요청의 SQL까지 포함한 숫자는 아닙니다.

### Q182. SQL 개수는 어떤 도구로 측정했으며 로그인·권한 검사 쿼리도 포함했나요?

SQL 로그와 P6Spy 기반 확인으로 해당 조회 요청 중 발생한 쿼리를 세었습니다. 기존 측정 기록의 24회와 3회에는 소유자 확인 쿼리가 포함되고 별도 로그인 요청은 포함되지 않습니다. 현재 코드에서도 같은 수치라고 말하려면 같은 요청 경로로 다시 측정해야 하므로 당시 기록과 현재 측정을 구분하겠습니다.

### Q183. Fetch Join 외에 DTO Projection·Batch Fetch·IN 조회를 비교했나요?

여러 번 왕복하는 문제를 줄이는 방법으로 Fetch Join, Batch Fetch, ID 목록을 이용한 IN 조회, 응답 전용 DTO 조회를 비교할 수 있습니다. 이 기능에서는 필요한 연관 데이터를 함께 가져오는 Fetch Join을 적용했습니다. 네 가지 방법을 같은 환경에서 모두 성능 비교한 것은 아니며, 목록 규모가 커지면 DTO 조회를 다시 검토할 수 있습니다.

### Q184. 컬렉션 Fetch Join의 중복 행과 페이징 문제는 어떻게 피했나요?

이 조회는 특정 사용자의 Project 목록을 반환하는 경로로 컬렉션 Fetch Join에 페이지 제한을 함께 적용하지 않았습니다. 루트 중복은 DISTINCT 등을 고려하지만 DB에서 전달되는 결합 행 자체가 없어지는 것은 아닙니다. Project 수가 커져 페이징이 필요하면 먼저 ID 페이지를 구한 뒤 연관 데이터를 조회하는 방식으로 바꾸겠습니다.

### Q185. README의 초기 수치와 이후 AWS 재측정 수치가 다른 이유를 조건별로 설명할 수 있나요?

초기 문서는 2026년 3월의 t2.micro 환경과 단계별 VU 부하를 기록했고, 9월 AWS 재측정은 조정한 인스턴스에서 초당 50회·2분 조건으로 실행했습니다. 초기 p95 55.02→32.7ms와 재측정 77.67→21.31ms를 같은 실험처럼 섞지 않겠습니다. 재측정 수치는 대화에 공유한 결과이며 원본 결과 파일도 함께 보관해야 합니다.

### Q186. VU 수·초당 요청 수·iteration 수·실제 요청 수는 어떻게 다른가요?

VU는 가상 사용자 실행 단위이고 iteration은 스크립트 한 순회입니다. 한 순회에 여러 HTTP 요청이나 대기가 있으면 iteration 수와 요청 수는 달라집니다. 초당 요청 수도 전체 평균과 유지 구간이 다를 수 있으며, 로그인 같은 준비 요청이 총 HTTP 수에 포함되는지도 확인했습니다.

### Q187. 일정 VU 방식과 일정 도착률 방식은 각각 어떤 부하를 재현하나요?

일정 VU 방식은 정해진 수의 사용자가 응답을 받은 뒤 다음 동작을 하는 상황을 재현합니다. 일정 도착률 방식은 응답 속도와 별개로 정해진 속도로 iteration을 시작하려고 합니다. 후자도 필요한 VU가 부족하면 실행하지 못한 iteration이 생기므로 목표 요청률과 실제 실행률을 함께 봐야 합니다. [k6 도착률 실행 방식](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/), [VU 부족과 누락](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/arrival-rate-vu-allocation/)

### Q188. 워밍업·JIT·캐시·측정 순서·EC2 CPU credit이 비교 결과에 미친 영향을 어떻게 통제했나요?

현재 기록만으로 모든 영향을 완전히 통제했다고 말하기는 어렵습니다. 재시작 뒤 워밍업을 맞추고 두 버전을 번갈아 반복 측정하며 동일한 데이터·부하·DB 조건을 유지하는 보완이 필요합니다. 특히 버스트형 EC2의 CPU credit과 DB 캐시, 동시간대 부하를 기록해야 개선 폭의 신뢰도를 높일 수 있습니다.

### Q189. 단일 사용자·한 Job·20개 Project를 반복 조회한 실험으로 주장할 수 있는 범위는 어디까지인가요?

해당 데이터와 요청 패턴에서 조회가 정상 동작했고 응답 시간과 자원 사용을 관측했다는 범위까지 설명할 수 있습니다. 다양한 사용자·큰 목록·동시 쓰기·영상 처리까지 섞인 전체 서비스의 최대 처리량을 입증한 것은 아닙니다. 같은 Job이나 Person을 반복 조회하면 캐시가 유리하게 작용할 수 있다는 한계도 있습니다.

### Q190. p95 개선·실패율·dropped_iterations·DB Pool·CPU를 함께 보면 어떤 결론과 한계가 있나요?

9월 기록에서는 N+1 버전의 p95 77.67ms가 Fetch Join에서 21.31ms로 낮아졌고 둘 다 HTTP 실패는 없었습니다. N+1에는 dropped_iterations 11건이 있어 목표 부하를 전부 실행하지 못한 점도 포함해야 합니다. CPU와 DB 활성 연결의 관측 최대값도 낮아졌지만, 반복 실험과 동일한 관측 구간을 확인한 뒤 인과와 개선 폭을 판단하겠습니다.

## 20. SQL·Index·EXPLAIN 성능 근거

### Q191. 완료 Job 조회의 123ms→3.40ms는 어떤 SQL과 데이터 조건에서 측정한 값인가요?

20만 건의 media_encode_jobs에서 상태가 DONE 또는 FAILED이고 completed_at이 기준 시각보다 이전인 행의 ID를 찾는 SQL입니다. 같은 MySQL 8.4.11 컨테이너와 데이터에서 인덱스 가시성만 바꾸고 워밍업 후 3회 측정한 중앙값을 비교했습니다. 상세 SQL과 분포는 인덱스 비교 문서에 남겼습니다.

### Q192. 이 수치는 API 전체 응답 시간인가요, SELECT 실행 시간인가요, 실제 DELETE 완료 시간인가요?

EXPLAIN ANALYZE로 확인한 SELECT 실행 시간입니다. API 인증·응답 직렬화·네트워크 시간을 포함하지 않으며, 실제 DELETE와 연관 데이터 정리 완료 시간도 아닙니다. 따라서 ‘API 응답이 123ms에서 3.40ms로 개선됐다’거나 ‘삭제 전체가 그 시간에 끝났다’고 표현하지 않겠습니다.

### Q193. (status, completed_at) 순서의 Index를 선택한 이유와 반대 순서의 차이는 무엇인가요?

실제 조건이 상태 값을 지정하고 그 안에서 완료 시각 범위를 찾는 형태여서 status와 completed_at을 묶었습니다. 반대 순서는 시각 범위를 먼저 읽은 뒤 상태를 거르는 비용이 달라질 수 있습니다. 항상 한 순서가 정답인 것은 아니며 실제 데이터 분포와 다른 조회에서의 활용도까지 확인해야 합니다.

### Q194. 선택도가 낮은 status를 선두에 둬도 유효한 이유를 실제 조건과 함께 설명해 주세요.

상태 종류가 적더라도 특정 상태 안에서 시간 범위를 좁히는 복합 조건에는 도움이 될 수 있습니다. 이번에는 단일 status 인덱스의 효율만 주장한 것이 아니라 completed_at과 함께 검색 범위를 줄인 결과를 확인했습니다. 반환할 ID까지 인덱스에서 읽을 수 있었던 점도 영향을 줬습니다.

### Q195. Covering Index가 적용되면 테이블 접근과 읽는 행 수가 어떻게 달라지나요?

조회에 필요한 값을 인덱스에서 모두 구하면 각 결과의 원본 행을 다시 읽는 접근을 줄일 수 있습니다. 이번 Job 조회는 전체 20만 행 스캔에서 7,056행의 커버링 범위 조회로 바뀐 기록이 있습니다. 커버링은 추가 테이블 접근을 줄이는 개념이며 읽는 인덱스 행 수 자체를 자동으로 줄이는 것은 아닙니다.

### Q196. INVISIBLE Index를 사용한 실험이 Index를 물리적으로 삭제한 실험과 다른 점은 무엇인가요?

INVISIBLE 인덱스는 기본 설정에서 실행 계획 선택 대상에서 제외되지만 저장 공간을 차지하고 쓰기 때도 유지됩니다. 따라서 같은 데이터에서 읽기 계획을 비교하는 데 유용하지만, 인덱스가 실제로 없는 상태의 INSERT 비용을 재현하지는 않습니다. 이 실험으로 쓰기 비용까지 입증하지 않겠습니다. [MySQL 공식 설명](https://dev.mysql.com/doc/refman/8.0/en/invisible-indexes.html)

### Q197. 같은 데이터 분포·cutoff·통계·워밍업 조건을 어떻게 맞췄나요?

같은 컨테이너의 같은 데이터와 cutoff를 사용하고 ANALYZE TABLE로 통계를 정리했습니다. 인덱스 가시성을 전환해 비교하며 워밍업 1회 후 3회 결과의 중앙값을 기록했습니다. 데이터 분포가 바뀌거나 콜드 캐시인 상황까지 대표하는 실험은 아니므로 조건을 결과와 함께 남겼습니다.

### Q198. EXPLAIN의 예상 rows와 EXPLAIN ANALYZE의 실제 rows·loops·시간은 어떻게 읽나요?

예상 rows는 옵티마이저의 추정치이고 실제 rows와 loops는 실행에서 반복된 처리량을 보여줍니다. 반복 노드의 행 수는 loops와 함께 읽고, 시간은 첫 행과 전체 반환 시점을 구분합니다. 부모 시간이 자식 실행을 포함할 수 있으므로 각 노드 시간을 단순 합산하지 않으며 추정과 실제 차이가 큰 지점을 찾습니다.

### Q199. Outbox claim처럼 개선되지 않은 SQL은 왜 Index를 추가하지 않았나요?

Outbox claim은 상태별 조건과 OR, 정렬이 함께 있어 후보 인덱스를 추가해도 기대한 실행 계획이 선택되지 않았습니다. 근거 없이 인덱스를 늘리면 쓰기·공간 비용만 생길 수 있어 개선되지 않은 결과도 남겼습니다. 필요하면 조건 분리나 선점 쿼리 구조 변경을 별도 실험으로 검토하겠습니다.

### Q200. 조회 개선에 따른 Index 공간·쓰기 비용·대량 삭제 Lock·undo 비용은 어디까지 측정했나요?

추가 인덱스 3개의 공간 약 34.72MiB와 주요 SELECT 실행 계획·시간을 기록했습니다. INSERT·UPDATE 처리량 감소나 실제 대량 DELETE의 잠금·undo·복제 지연까지 정량 측정한 것은 아닙니다. 운영 적용을 확대하려면 삭제 배치 크기와 쓰기 부하를 함께 측정해야 합니다.

## 21. 테스트 전략·증거·회귀 방지

### Q201. 단위 테스트·H2 통합 테스트·MySQL 통합 테스트·AWS 전체 흐름 검증을 어떻게 나눴나요?

엔티티 규칙과 분기 처리는 빠른 단위 테스트로, Spring 연결과 일반 저장 흐름은 H2 통합 테스트로 확인했습니다. MySQL Testcontainers에서는 Migration·제약·잠금·실제 SQL 동작을 확인하고, AWS에서는 보안 설정과 Kafka·S3·Callback을 포함한 전체 흐름을 확인했습니다. 각 검증이 다른 검증을 완전히 대체하지는 않습니다.

### Q202. Mock 기반 테스트가 통과해도 실제 트랜잭션이나 보안 필터에서 실패할 수 있는 이유는 무엇인가요?

Mock은 정해 둔 반환값과 예외만 흉내 내므로 실제 커밋 시점, DB 잠금, Spring 프록시와 보안 필터 순서를 그대로 검증하지 못합니다. 메서드 자체가 통과해도 외부 요청이 그 메서드에 도달하지 못할 수 있습니다. 실제 Callback의 CSRF 충돌이 이런 경계를 확인해야 한다는 사례였습니다.

### Q203. Testcontainers로 컨테이너를 띄우는 것과 실제 운영과 같은 조건을 검증하는 것은 어떻게 다른가요?

MySQL 컨테이너를 띄우면 H2와 다른 DB 엔진 동작을 확인할 수 있지만 운영의 모든 조건이 같아지지는 않습니다. 버전·문자 정렬 규칙·격리 수준·권한·데이터 분포를 맞춰야 하고 RDS 네트워크나 장애 전환까지 재현되는 것은 아닙니다. 엔진 일치와 운영 환경 재현을 구분하겠습니다.

### Q204. Migration 빈 DB 적용·Hibernate validate·Constraint 위반은 각각 어떻게 테스트했나요?

빈 MySQL에 Migration을 순서대로 적용하고 Hibernate validate로 애플리케이션 매핑이 맞는지 확인했습니다. UNIQUE·FK·CHECK 등은 실제 위반 데이터를 저장해 DB가 거부하는지 별도로 확인했습니다. 애플리케이션이 시작된다는 사실만으로 모든 제약이 의도대로 작동한다고 판단하지 않았습니다.

### Q205. Clock을 주입한 테스트가 sleep으로 기다리는 테스트보다 유리한 이유는 무엇인가요?

만료 기준에 Clock을 주입하면 실제로 오래 기다리지 않고 특정 시각 전후를 정확하게 재현할 수 있습니다. 실행 속도가 빠르고 시간 경계 테스트가 흔들리는 문제도 줄어듭니다. 다만 실제 스케줄러 실행이나 네트워크 지연까지 검증한 것은 아니므로 시간 계산 테스트와 실행 환경 검증은 구분합니다.

### Q206. DB commit·rollback·AFTER_COMMIT을 테스트할 때 테스트 자체의 롤백은 어떤 영향을 주나요?

테스트가 기본적으로 롤백되면 실제 커밋 뒤에 실행되는 AFTER_COMMIT 리스너가 호출되지 않을 수 있습니다. 따라서 커밋·롤백을 명시적으로 나누고, 이후 새로운 조회로 저장 결과와 부수 효과를 확인해야 합니다. 같은 영속성 컨텍스트의 객체만 확인하면 실제 DB 상태를 검증했다고 보기 어렵습니다.

### Q207. Kafka·S3 장애를 Mock 예외로 재현한 것과 실제 네트워크를 끊은 실험의 차이는 무엇인가요?

Mock 예외는 실패 분기와 재시도 정책을 빠르고 일정하게 검증하는 데 유용합니다. 실제 네트워크 단절은 연결 timeout, 클라이언트 내부 재시도, 스레드 점유, 부분 성공처럼 더 넓은 문제를 드러냅니다. Mock 기반 장애 주입 결과를 모든 실제 네트워크 장애를 검증한 것처럼 설명하지 않겠습니다.

### Q208. 보안 필터를 직접 호출하는 테스트와 전체 Filter Chain 통합 테스트는 무엇이 다른가요?

필터 직접 호출 테스트는 그 필터의 입력과 응답 동작을 좁게 검증합니다. 전체 Filter Chain 테스트는 CSRF·인증·예외 응답 필터가 어떤 순서와 경로 조건으로 작동하는지도 확인합니다. 특히 운영 프로필의 내부 Callback은 전체 체인을 통해 허용·거부 조건을 확인해야 합니다.

### Q209. 269개 같은 테스트 통과 수치는 어느 커밋·단계의 결과이며 현재 전체 수와 구분할 수 있나요?

269개는 예외 표준화와 트랜잭션 경계 개선 사례 문서에 남은 당시 전체 테스트 결과이며 현재 저장소의 최신 테스트 수를 뜻하지 않습니다. 정확한 커밋은 각 문서의 작업 이력과 실행 결과를 대조해 제시하겠습니다. 이번에는 테스트를 다시 실행하지 않았으므로 과거 수치를 현재 결과로 말하지 않겠습니다. [예외 표준화 기록](../problem-solving/08-domain-exception-and-api-error-standardization.md), [트랜잭션 경계 기록](../problem-solving/09-transaction-boundary-and-external-io.md)

### Q210. 테스트가 실패하거나 Docker를 쓸 수 없을 때 완료 보고와 CI 기준은 어떻게 유지했나요?

Docker를 사용할 수 없으면 MySQL 통합 검증을 못 했다는 사실을 명시하고, 실행한 테스트와 미실행 테스트를 나눠 보고했습니다. 코드 작성 완료와 검증 완료를 같은 의미로 쓰지 않는 것이 기준입니다. 필수 MySQL 검증은 Docker가 가능한 CI에서 통과한 뒤 반영 여부를 판단해야 합니다.

## 22. 관측성·실제 장애·Runbook

### Q211. REQUESTED에 멈춘 실제 사례에서 처음 확인한 증거와 원인을 좁힌 순서를 설명해 주세요.

API Job이 REQUESTED에 머문 것을 확인한 뒤 Kafka의 발행 위치와 Consumer offset, retry·DLT 기록을 차례로 확인했습니다. 원본 메시지의 Lag은 0이었지만 DLT에 메시지가 남아 있어 처리 성공은 아니라는 점을 알았습니다. 이후 내부 Callback이 운영 보안 필터에서 거부되는 원인을 수정하고 새 영상 작업이 DONE까지 가는지 확인했습니다.

### Q212. Consumer Lag 0인데도 영상 처리가 실패할 수 있음을 어떤 기록으로 확인했나요?

원본 토픽의 마지막 위치와 Consumer의 커밋 위치가 모두 1이어서 Lag은 0이었지만, DLT에는 메시지 1건이 있었습니다. 원본 메시지를 넘긴 뒤 실패 처리 경로로 이동해도 Lag은 줄어들 수 있습니다. 따라서 Lag만 보지 않고 Job·Inbox 상태와 DLT, Callback 결과까지 함께 확인해야 합니다.

### Q213. 개발 프로필에서는 정상인데 운영 프로필에서 Callback이 막힌 원인은 무엇이었나요?

개발 환경에서는 내부 Callback 경로가 CSRF 검사에서 제외됐지만 운영 환경에서는 같은 예외가 적용되지 않았습니다. 이 때문에 HMAC 인증을 검사할 내부 처리 경로에 도달하기 전에 요청이 거부됐습니다. 내부 경로의 CSRF 예외를 일관되게 적용하면서 HMAC 검증은 유지하는 방향으로 수정했습니다.

### Q214. correlationId·requestId·jobId는 각각 어떤 범위를 연결하고 어디에서 전파되나요?

requestId는 요청을 구분하지만 HTTP 요청 ID와 업로드 요청 식별자가 같은 의미인지 문맥을 먼저 구분해야 합니다. jobId는 한 인코딩 작업, correlationId는 API·메시지·Worker·Callback의 연관 흐름을 찾는 데 사용합니다. 메시지와 내부 요청에 추적 문맥을 전달해 서로 다른 프로세스의 로그를 연결하도록 했습니다.

### Q215. 로그 추적 ID와 완전한 분산 Trace의 Span·전파 체계는 무엇이 다른가요?

현재 추적 ID는 여러 로그가 같은 작업에서 나왔는지 검색하기 위한 연결 정보입니다. 완전한 분산 Trace는 각 호출의 Span, 부모·자식 관계, 시작·종료 시간과 전파 규약을 함께 관리합니다. correlationId가 있다고 OpenTelemetry 기반 분산 추적 전체를 구축했다고 표현하지는 않겠습니다.

### Q216. 어떤 값은 Metric Tag로 두고 어떤 값은 로그에만 남겼나요?

서비스·환경·상태·결과처럼 종류가 제한된 값은 Metric Tag로 사용합니다. jobId·movieId·userId·requestId처럼 계속 늘어나는 값은 주로 로그에 남깁니다. ID별로 시계열을 만들면 메트릭 저장량과 조회 비용이 커지기 때문에 집계와 개별 추적의 역할을 나눴습니다.

### Q217. 상태 Gauge의 스냅샷 지연과 Counter의 재시작·커밋 시점 차이는 어떻게 해석하나요?

상태 Gauge는 주기적으로 읽은 DB 스냅샷이라 실제 변경을 즉시 반영하지 않을 수 있습니다. Counter는 프로세스 재시작과 증가 시점의 영향을 받으며, 커밋 전에 증가했다면 롤백과도 차이가 생길 수 있습니다. 메트릭은 추세와 이상 감지에 사용하고 개별 작업의 최종 사실은 DB와 로그로 확인합니다.

### Q218. Alert Rule 작성·대시보드 구성·실제 알림 수신 연결 중 어디까지 완료됐나요?

Prometheus 수집과 Grafana 구성, Alert Rule 및 관련 대응 문서를 준비했습니다. AWS에서는 API·Worker의 수집 상태와 대시보드 연결을 확인했습니다. Slack·이메일 같은 실제 수신 채널까지 연결해 알림을 받았다는 검증은 별도이므로 완료 범위를 구분하겠습니다.

### Q219. 장애 복구를 선언할 때 health UP 외에 어떤 업무 지표와 잔여 작업을 확인하나요?

health UP 외에 새 요청이 접수되고 Worker 처리와 Callback을 거쳐 최종 결과가 저장되는지 확인합니다. 오래 남은 Job, Outbox DEAD, DLT와 처리 중 Inbox도 확인해 복구 뒤 잔여 실패가 없는지 봐야 합니다. 영상이라면 최종 파일의 존재와 재생까지 확인하는 것이 업무 복구 기준입니다.

### Q220. Runbook이 실제 대응 시간을 줄였다는 근거가 있나요, 아니면 다음 대응을 위한 준비인가요?

현재는 실제 장애에서 확인한 순서와 복구 절차를 다음 대응에 활용하도록 정리한 단계입니다. Runbook 도입 전후 평균 복구 시간을 비교한 수치는 없습니다. 따라서 ‘대응 시간을 몇 퍼센트 줄였다’고 말하기보다 다음 장애에서 확인할 로그·지표·복구 조건을 명확히 했다고 설명하겠습니다.

근거·상세: [관련 설명·답변](../operations/media-incident-runbook.md)

## 23. AWS·네트워크·권한·비용

### Q221. 실제 성능 측정 환경과 장기 운영용 아키텍처를 구분해서 설명해 주세요.

실험 환경은 API·Worker·Kafka·부하 발생용 EC2와 RDS·S3를 중심으로 단순하게 구성했습니다. 서비스 전체 흐름과 성능을 짧게 확인하는 목적이었습니다. 장기 운영이라면 다중 장애 구역, 접근 통제, 백업 복구, 배포 가용성 등을 별도 설계해야 하므로 실험 구성을 고가용성 운영 환경으로 소개하지 않겠습니다.

### Q222. Default VPC를 사용한 것과 VPC 없이 구성한 것은 왜 다른가요?

Default VPC도 AWS가 제공하는 VPC이므로 VPC를 사용하지 않은 것이 아닙니다. 직접 복잡한 네트워크 구성을 만들지 않고 기존 VPC의 서브넷과 보안 그룹을 활용한 것입니다. 라우팅과 접근 제어가 필요 없어진다는 의미도 아닙니다.

### Q223. 사설 IP·공인 IP·Elastic IP를 API↔Worker와 Mac·CI 접속에서 어떻게 구분했나요?

API·Worker·Kafka 사이의 내부 통신에는 사설 IP를 사용했습니다. Mac이나 외부 GitHub Actions에서 SSH로 접속할 때는 접근 가능한 공인 주소를 사용했고 주소 고정을 위해 Elastic IP를 사용했습니다. hostname -I에 보이는 사설 IP를 외부 SSH 주소로 혼동했던 부분도 구분해 정리했습니다.

### Q224. 보안 그룹의 인바운드를 열어도 통신이 실패했던 사례에서 아웃바운드는 어떤 역할을 했나요?

목적지의 인바운드가 허용돼도 출발지에서 나가는 요청을 아웃바운드 규칙이 막으면 연결되지 않습니다. 실제 k6 인스턴스에 아웃바운드 규칙이 없어 API·Worker 연결이 timeout됐습니다. 출발지와 목적지 양쪽의 규칙을 확인한 뒤 통신이 성공했습니다.

### Q225. RDS 마스터 계정을 애플리케이션에 사용하지 않고 서비스별 계정을 만든 이유는 무엇인가요?

마스터 계정은 관리 권한이 넓으므로 애플리케이션에 사용하면 설정 실수나 침해의 영향이 커집니다. API·Worker별 계정을 만들고 각자 소유한 논리 DB에만 접근하도록 했습니다. Worker URL을 API DB로 잘못 지정했을 때 접근이 거부된 사례도 있어 URL을 고쳤고 권한을 넓히지는 않았습니다.

### Q226. Access Key 대신 EC2 IAM Role을 사용한 이유와 S3 최소 권한 범위는 무엇인가요?

EC2 IAM Role을 사용하면 장기 Access Key를 환경 파일에 직접 보관하지 않고 임시 자격 증명을 받아 사용할 수 있습니다. S3 권한은 필요한 버킷·경로의 조회·업로드·삭제 동작에 맞춰 제한하는 것이 기준입니다. 실제 실행 계정에서 접근을 확인했고 모든 AWS 리소스에 광범위한 권한이 필요한 것은 아닙니다.

### Q227. 단일 Kafka Broker와 단일 MySQL 서버가 갖는 장애 위험을 현재 규모에서 어떻게 판단했나요?

단일 Broker가 중단되면 Kafka 사용이 멈추고, 복제본이 없으면 디스크 손실에도 취약합니다. API와 Worker의 논리 DB를 분리해도 같은 MySQL 서버 장애는 함께 영향을 줍니다. 초기 소규모 실험에서는 비용과 단순성을 선택했지만 이 구성을 장애 무중단 구조로 설명하지 않겠습니다.

### Q228. Actuator·Prometheus·Grafana·Kafka 포트를 어디까지 공개하며 관리 화면은 어떻게 보호하나요?

Kafka와 Actuator는 필요한 내부 인스턴스에서만 접근하도록 하고, 관리용 Prometheus·Grafana는 허용한 관리 경로로 제한하는 방향입니다. 컨테이너 포트가 0.0.0.0에 바인딩됐다는 사실과 인터넷 접근 가능 여부는 보안 그룹까지 함께 봐야 합니다. Grafana 인증과 관리 화면 공개 범위도 별도로 확인해야 합니다.

### Q229. 짧은 실험을 위해 허용한 SSH 접근 정책을 실제 운영에 그대로 쓰면 어떤 문제가 있나요?

외부 CI의 접속을 쉽게 하려고 SSH 접근 범위를 넓히면 키 인증만 사용하더라도 불필요한 공격 노출이 늘어납니다. 짧은 실험에서 허용한 설정을 운영의 권장 구성으로 보지는 않습니다. 운영 전에는 SSM이나 통제된 배포 실행 환경 등으로 접근 경로를 줄이고 권한과 접속 이력도 관리하겠습니다.

### Q230. 실험 종료 후 EC2 외에 EBS·RDS·Snapshot·Elastic IP·S3 비용을 어떻게 정리하나요?

인스턴스를 멈추는 것만으로 모든 비용이 사라지지는 않으므로 연결된 볼륨, RDS, 스냅샷, Elastic IP와 S3 데이터까지 목록으로 확인하겠습니다. 재현에 필요한 결과와 설정을 보관한 뒤 삭제 대상과 보존 대상을 나눕니다. 실제 사용자 데이터나 필요한 백업은 확인 없이 지우지 않고, 정리 후 남은 리소스와 청구 내역도 점검하겠습니다.

## 24. CI/CD·릴리스·롤백·환경 재현

### Q231. 커밋부터 테스트·빌드·배포·health 확인·롤백까지 현재 Workflow를 설명해 주세요.

현재 성능 실험용 배포는 테스트와 빌드를 거쳐 커밋별 JAR를 SSH·SCP로 EC2에 전달하는 흐름입니다. 새 JAR로 current.jar 링크를 바꾸고 서비스를 재시작한 뒤 health를 확인합니다. 실패하면 이전 릴리스가 있는 경우 되돌리지만, 코드 복구와 업무 정상화 확인은 별도로 구분합니다.

### Q232. 과거 CodeDeploy 구성과 현재 SCP 배포 중 지금 설명하는 환경은 어느 것인가요?

지금 설명하는 AWS 성능 실험 환경은 GitHub Actions의 SSH·SCP 배포입니다. 과거에 다룬 S3·CodeDeploy 구성이나 README의 다른 시점 설명과 혼동하지 않겠습니다. 실제 증거는 해당 시점 Workflow와 서버의 릴리스 경로로 보여드리겠습니다.

### Q233. 커밋별 JAR와 current.jar 심볼릭 링크로 릴리스를 관리한 이유는 무엇인가요?

JAR 이름에 커밋을 남기면 어떤 코드가 실행 중인지 확인하고 이전 파일을 보존하기 쉽습니다. 서비스는 current.jar라는 고정 경로를 바라보므로 실행 설정을 매번 바꾸지 않고 릴리스를 전환할 수 있습니다. 링크를 바꾸는 것만으로 실행 중인 JVM이 바뀌는 것은 아니어서 서비스 재시작도 필요합니다.

### Q234. 배포 health 확인이 실패하면 어디까지 자동으로 되돌리고 무엇은 직접 확인해야 하나요?

health 확인이 실패하면 로그를 출력하고 유효한 이전 릴리스가 있을 때 링크를 되돌려 재시작합니다. 다만 스크립트의 롤백이 DB·환경변수·외부 작업까지 복원하는 것은 아닙니다. 이전 버전의 health와 실제 요청 처리, 남은 작업 상태까지 정상인지 직접 확인해야 합니다.

### Q235. 이전 정상 릴리스가 없는 첫 배포 실패와 재배포 실패를 어떻게 구분하나요?

첫 배포에는 돌아갈 정상 JAR가 없을 수 있으므로 이전 릴리스가 있는 경우와 같은 롤백을 기대하면 안 됩니다. Worker 배포는 이전 경로가 유효한지 확인하고 돌아갈 대상이 없으면 중지하는 흐름을 구분합니다. 서비스별 스크립트 조건을 확인해 실패 시 무엇이 남고 무엇이 실행되는지 설명하겠습니다.

### Q236. 코드 롤백으로 되돌아가지 않는 환경변수·DB Migration·Kafka 메시지는 어떻게 처리하나요?

코드 링크를 되돌려도 적용된 Migration, 변경한 환경 파일, 이미 보낸 Kafka 메시지는 그대로 남습니다. 따라서 DB 변경은 이전 코드와도 호환되는 순서로 진행하고, 설정과 메시지 버전도 함께 검토해야 합니다. 복구 SQL이나 재처리는 영향 범위를 확인한 별도 절차이지 JAR 롤백의 자동 효과가 아닙니다.

### Q237. API·Worker가 다른 버전으로 잠시 실행될 때 메시지·Callback 호환성을 어떻게 검증하나요?

메시지에 규격 버전을 두고 지원 여부와 필수 데이터를 검사하는 장치를 적용했습니다. 그러나 버전 검사만으로 구버전 API와 신버전 Worker의 모든 조합이 검증되는 것은 아닙니다. 실제 배포 전에는 이전 메시지 샘플과 Callback 계약을 함께 테스트하고, 호환되는 변경부터 적용하는 순서를 정해야 합니다.

### Q238. 로그인 비밀키·DB 비밀번호·Callback secret을 저장소와 배포 로그에서 어떻게 보호하나요?

비밀번호와 서명용 비밀값은 저장소의 설정 예시와 분리하고 GitHub Secrets나 서버의 제한된 환경 파일로 관리합니다. 원문 토큰·토큰 해시·비밀번호를 로그나 실패 메시지에 남기지 않는 기준을 두었습니다. 노출이 발생하면 파일에서 지우는 것만으로 끝내지 않고 해당 자격 증명 교체까지 필요합니다.

### Q239. SSH known_hosts 검증과 사용자 인증용 개인키의 역할은 무엇이 다른가요?

known_hosts는 접속 대상 서버의 공개키를 확인해 예상한 서버가 맞는지 검증하는 용도입니다. 개인키는 그 서버에 접속하는 사용자가 인증받는 데 사용합니다. 서버 지문 비교 없이 얻은 키를 그대로 신뢰하는 것과, 사용자 개인키를 안전하게 보관하는 문제는 서로 다른 확인 사항입니다.

### Q240. 다른 사람이 같은 커밋으로 환경을 재현할 때 이미지·JDK·DB 버전과 설정 차이를 어떻게 줄이나요?

커밋과 Migration, 필요한 환경변수와 실행 절차를 문서로 남기고 JDK·MySQL·컨테이너 이미지 버전도 함께 고정하는 것이 기준입니다. 다만 실험에서 latest 이미지를 사용한 부분은 완전한 재현성의 한계입니다. 재실험에는 실제 사용 이미지 버전이나 digest와 시스템 설정을 기록해 차이를 줄이겠습니다.

## 25. AI 활용·본인 기여·학습·협업

### Q241. AI가 제안한 작업 중 본인이 직접 내린 기술·정책 결정 하나를 근거와 함께 설명해 주세요.

만료된 Refresh Token에 접근했을 때 폐기 기록은 남기고 요청에는 401을 반환하는 정책을 선택했습니다. 예외와 함께 전체 트랜잭션이 롤백되면 기록도 없어질 수 있어 별도 REQUIRES_NEW 저장으로 분리했습니다. 추가 트랜잭션 비용이 들더라도 보안 상태를 남겨야 한다는 판단이었습니다.

### Q242. AI가 코드를 작성했더라도 설계를 이해하고 검증했다는 것을 어떻게 보여줄 수 있나요?

핵심 요청이 어떤 메서드를 거쳐 DB·Kafka·Worker·Callback으로 이어지는지 코드로 설명하고, 실패 지점별 테스트를 보여주겠습니다. 기술을 왜 선택했는지와 보장하지 못하는 구간도 함께 설명할 수 있어야 합니다. AI가 만든 코드의 양이나 테스트 개수만으로 제 이해도를 증명하려고 하지는 않겠습니다.

### Q243. AI 제안이 잘못됐거나 과도해서 수정·보류한 실제 사례는 무엇인가요?

스토리보드 스크립트의 검증 정책은 제안이 있었지만 요구사항이 정해지지 않아 구현을 보류했습니다. 영상 이용 권한도 처음부터 전자서명과 자동 승인까지 만들지 않고 소규모 이용에 맞춘 수동 확인을 선택했습니다. 이를 AI의 오류를 발견한 사례로 과장하기보다 제안을 범위와 정책에 맞게 조정한 사례로 설명하겠습니다.

### Q244. 정책이 정해지지 않은 스크립트·권리 관리 등을 보류한 기준은 무엇이었나요?

실제 사용 규칙이 정해지지 않은 상태에서 코드로 제한하면 나중에 잘못된 제약을 풀어야 할 수 있다고 봤습니다. 당장 필요한 기능과 사용자 수를 기준으로 우선순위를 정하고, 보류 이유와 확장 방향을 기록했습니다. 다만 보류가 보안·권한 확인 자체를 생략한다는 의미는 아닙니다.

### Q245. 작업을 작은 단위로 나누고 커밋·테스트·문서를 관리한 이유는 무엇인가요?

수정 범위가 커지면 어떤 변경이 문제를 만들었는지 확인하기 어려워 엔티티·DTO·서비스·예외·트랜잭션 등으로 나눴습니다. 작은 단위로 검토와 테스트를 하고 결정 이유를 문서로 남겨 다음 작업에서도 기준을 유지했습니다. 커밋도 가능하면 한 가지 목적과 검증 결과를 설명할 수 있는 단위로 만들려고 했습니다.

### Q246. AI가 만든 테스트도 같은 오해를 검증할 수 있는데 이를 어떻게 보완했나요?

구현과 테스트가 같은 잘못된 가정을 공유할 수 있어 통과 개수만으로 안심하지 않겠습니다. 실제 사용자 요구, DB 제약과 SQL, 공식 문서, MySQL 통합 테스트와 AWS 전체 흐름을 서로 다른 확인 근거로 활용했습니다. 모든 테스트를 독립적으로 재검토한 것은 아니며 핵심 실패 조건은 사람이 기대 결과를 먼저 정하는 보완이 필요합니다.

### Q247. 비밀번호·토큰·실제 사용자 파일이 AI 입력이나 로그에 노출되지 않도록 어떤 기준을 사용했나요?

비밀값은 예시값이나 마스킹된 값으로 대체하고 실제 인증 정보와 사용자 파일을 그대로 붙여 넣지 않는 기준이 필요합니다. 프로젝트에서도 환경변수 분리와 민감한 토큰 로그 제외 정책을 사용했습니다. 과거의 모든 입력과 로그에 노출이 없었다고 단정하지 않으며, 발견하면 자격 증명 교체와 공유 범위 확인까지 하겠습니다.

### Q248. 개인 프로젝트에서 사용자와 의견을 조율한 경험과 개발팀 협업 경험을 어떻게 구분하나요?

이 프로젝트에서는 실제 사용자의 요구를 듣고 구현 방향을 조정한 경험이 있습니다. 영상 비용을 줄이려던 유튜브 링크 제안을, 업로드 시점 노출을 우려한 사용자 의견을 듣고 바꾼 사례입니다. 이를 여러 개발자와 코드 리뷰·일정을 조율한 팀 개발 경험으로 바꿔 말하지는 않겠습니다.

### Q249. 새로운 Outbox·Flyway·Testcontainers 개념을 학습하고 구현까지 연결한 과정을 설명해 주세요.

먼저 기존 방식에서 누락이나 환경 차이가 생기는 지점을 확인하고 새 기술이 무엇을 보장하는지 학습했습니다. Outbox는 저장과 전송의 부분 실패, Flyway는 스키마 변경 이력, Testcontainers는 실제 MySQL 동작 검증에 연결했습니다. 정상 사용법뿐 아니라 재시도·기존 데이터·실행 환경 등 추가 관리 비용도 함께 정리했습니다.

### Q250. AI 없이 핵심 흐름을 다시 설명하거나 작은 버전으로 구현하라고 하면 어디부터 시작하겠나요?

먼저 작업 접수와 상태 변경 규칙을 작은 엔티티와 테스트로 표현하겠습니다. 다음으로 작업과 발행 대기 기록을 같은 트랜잭션에 저장하고, 별도 발행과 중복 수신 처리를 붙이겠습니다. 프레임워크 설정을 전부 외우기보다 각 단계의 입력·저장 결과·실패 시 남는 데이터를 설명하는 데서 시작하겠습니다.

## 26. 반론·한계·재설계·확장 시나리오

### Q251. 사용자 1~2명인 프로젝트에 Kafka·Outbox·여러 서비스가 과한 설계라는 의견에 어떻게 답하나요?

실제 사용자 수만 보면 더 단순한 구조로 시작할 수 있다는 의견에 동의합니다. 이 프로젝트는 기능 제공과 함께 비동기 처리의 실패·중복·DB 신뢰성을 학습하고 검증하려는 목적도 있었습니다. 학습 목적의 선택을 사업 규모상 필수였다고 주장하지 않고, 운영 비용에 맞춰 단순화할 가능성을 열어두겠습니다.

### Q252. 지금 다시 만든다면 유지할 선택 세 가지와 단순화할 선택 세 가지는 무엇인가요?

유지할 것은 엔티티의 상태 변경 규칙, Migration과 실제 DB 테스트, 요청 추적과 오류 계약입니다. 단순화 후보는 작은 규모의 배포 단위, 세분화가 과한 서비스 클래스, 중복된 재시도·복구 경로입니다. 다만 비동기 발행을 유지한다면 저장과 발행 사이의 누락 방지는 계속 필요하므로 Outbox를 이유 없이 제거하지는 않겠습니다.

### Q253. 리팩토링이 클래스 수와 문서만 늘린 것이 아니라 실제 문제를 줄였다는 근거는 무엇인가요?

컬렉션 직접 수정과 잘못된 상태 전이를 제한하고, 실제 MySQL에서 제약과 저장 동작을 확인한 테스트를 근거로 들겠습니다. Storyboard 조회의 SQL 24→3회와 인덱스 실험처럼 측정한 개선도 있습니다. 반면 클래스 분리 자체가 성능이나 안정성을 자동으로 높였다고 말하지는 않겠습니다.

### Q254. 가장 안전하다고 설명한 기능에서 아직 실패할 수 있는 구간 세 가지를 꼽아 주세요.

커밋 이후 메모리 이벤트만으로 삭제하는 파일은 프로세스 종료 시 정리가 누락될 수 있습니다. lease가 만료된 이전 Worker의 외부 쓰기는 완전한 Fencing이 없어 별도 검토가 필요합니다. 또 오래된 Job의 결과가 Movie의 최신 영상 변경과 충돌하지 않는지 작업 간 정책까지 확인해야 합니다.

### Q255. 사용자가 10배·100배 늘면 어떤 지표를 근거로 어느 부분부터 확장하겠나요?

단순히 사용자 수 배수만 보고 인스턴스를 늘리지 않고 지연 시간·오류율·DB 대기·Consumer Lag·인코딩 처리 시간을 보겠습니다. 읽기 병목이면 쿼리와 인덱스, 인코딩 병목이면 동시 처리 한도와 Worker 확장을 먼저 검토합니다. 이후 실제 분포에 맞는 부하로 확장 효과와 새로운 병목을 다시 확인하겠습니다.

### Q256. Redis·Kubernetes·CDC·멀티 AZ를 지금 도입하지 않은 이유와 도입 기준은 무엇인가요?

현재는 실제 필요와 운영 부담에 비해 추가 기술이 많아질 수 있어 모두 도입하지 않았습니다. Redis는 공유 상태나 반복 조회 병목, Kubernetes는 배포·확장 운영 부담, CDC는 발행 방식의 병목, 멀티 AZ는 요구 가용성과 복구 목표가 도입 판단 기준입니다. 기술 이름을 늘리기보다 관측한 문제와 비용으로 결정하겠습니다.

### Q257. 스토리지 비용이 예산을 넘으면 화질·보존·직접 제공 범위를 어떤 순서로 조정하겠나요?

먼저 원본·변환본 저장량과 전송량 중 무엇이 비용을 만드는지 측정하겠습니다. 남은 임시 파일과 불필요한 보존 데이터를 정리하고, 사용자에게 필요한 화질·보존 기간·직접 제공 범위를 차례로 협의하겠습니다. 제출 목적이 있는 영상이므로 비용만 보고 품질을 낮추거나 파일을 임의로 삭제하지는 않겠습니다.

### Q258. 중복 처리 방지 경험을 결제·재고·예약에 적용할 때 그대로 가져가면 안 되는 정책은 무엇인가요?

요청 식별자와 중복 방지 원리는 가져갈 수 있지만, 인코딩의 종료 상태 정책을 그대로 적용하면 안 됩니다. 결제·예약은 취소·환불·재고 복구와 외부 시스템의 실제 성공 여부를 따로 다뤄야 합니다. timeout을 실패로 단정하지 않고 업무별 보상과 대사, 중복 판단 기간을 새로 설계해야 합니다.

### Q259. 포트폴리오에서 측정 완료·코드 구현·문서상 설계·향후 계획이 섞인 표현을 스스로 찾아 설명할 수 있나요?

SQL 123→3.40ms는 특정 SELECT 측정이고, 24→3회는 특정 Storyboard 조회 기록입니다. 긴 단계별 재시도 일정과 Circuit Breaker는 구현 사실과 구분해야 하며, Runbook 작성은 복구 시간 단축을 측정했다는 의미가 아닙니다. 포트폴리오에서도 각 문장을 코드·테스트·실험·계획 중 무엇으로 뒷받침하는지 확인하겠습니다.

### Q260. 면접관이 지금 코드와 테스트 하나를 열어 근거를 보여 달라고 하면 어떤 파일부터 보여주겠나요?

Outbox 사례라면 발행 상태와 선점·재시도를 관리하는 MediaEncodeOutboxTransactionService, 실제 발행을 수행하는 MediaEncodeOutboxPublisher를 먼저 열겠습니다. 이어 MediaEncodeOutboxFailureInjectionIntegrationTest에서 실패를 어떻게 재현하고 무엇을 검증했는지 보여주겠습니다. 이 테스트가 Worker와 S3까지 모든 장애를 검증하는 것은 아니라는 범위도 함께 설명하겠습니다.
