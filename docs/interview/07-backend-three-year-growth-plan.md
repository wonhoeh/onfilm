# 3년차 백엔드 개발자 역량 진단 및 보완 계획

## 1. 문서 목적

이 문서는 Onfilm 프로젝트의 코드와 문제 해결 과정을 기준으로, 3년차에 준하는 백엔드 개발자로 평가받기 위해 현재 갖춘 강점과 보완해야 할 역량을 정리한다.

이 평가는 실제 업무 전체를 관찰한 결과가 아니라, 현재 확인할 수 있는 프로젝트와 대화 과정을 기준으로 한 진단이다.

작성 기준일: 2026-08-17

## 2. 현재 수준에 대한 요약

현재 모습은 “구현력이 부족한 신입”과는 거리가 멀다. Spring Boot와 JPA를 활용해 기능을 구현하고, 엔티티의 불변식과 연관관계를 개선하려는 설계 감각도 가지고 있다.

다만 채용 담당자가 바로 3년차 수준이라고 판단하기에는 다음 증거가 부족하다.

- 요구사항과 도메인 정책을 먼저 정의하고 스스로 설계한 증거
- 변경을 작은 단위로 검증하고 안전하게 전달하는 작업 완결성
- 운영 장애, 동시성, 데이터 무결성을 다룬 경험
- 설계 선택의 트레이드오프를 논리적으로 설명하는 능력

보수적으로 표현하면 다음과 같다.

| 영역 | 현재 평가 |
|---|---|
| 구현 및 학습 능력 | 주니어 상위 |
| Spring/JPA 활용 | 2년차 이상의 잠재력 |
| 도메인 설계 감각 | 좋은 편 |
| 작업 완결성과 운영 안정성 | 보완 필요 |
| 독립적인 기술 의사결정 | 성장 중 |
| 종합 | 3년차 가능성은 보이지만 운영·소유권의 증거가 더 필요 |

## 3. 현재의 강점

### 3-1. 구조와 이유를 질문하는 태도

단순히 동작하는 코드를 만드는 것에 그치지 않고, 다음과 같은 선택의 이유를 질문하고 있다.

- Builder와 생성자의 선택 기준
- `change`, `update`, `apply`의 의미
- `add`와 `attach`의 책임
- 연관관계 편의 메서드의 위치
- null과 중복 입력을 처리하는 정책

이는 단순 문법보다 설계 원칙을 학습하려는 태도로, 성장에 유리한 강점이다.

### 3-2. 엔티티 불변식과 연관관계에 대한 관심

`Movie`, `MoviePerson`, `MovieGenre`를 단순한 데이터 보관 객체가 아니라 스스로 상태를 보호하는 객체로 만들려는 방향은 좋다.

예:

- 필수 값과 허용 범위 검증
- 역할에 따른 배역 정보 정규화
- 중복 참여자와 장르 방지
- `create → add → attach`를 통한 양방향 관계 일관성 보장
- Entity 검증과 DB 유니크 제약의 병행

### 3-3. 실제 오류를 기반으로 문제를 해결하는 태도

테스트 실패, Spring Context 로딩 오류, H2 PK 충돌 등을 숨기지 않고 스택 트레이스와 실행 결과를 기준으로 원인을 좁혀갔다.

이는 현실적인 개발 업무에서 필요한 역량이며, 각 문제의 원인과 재발 방지 방법을 정리하면 좋은 면접 사례가 될 수 있다.

### 3-4. 넓은 기술 경험

Onfilm 프로젝트에서 다음 영역을 다루고 있다.

- Spring Boot, Spring Security, JPA
- JWT access/refresh token과 rotation
- Kafka 기반 미디어 인코딩 흐름
- S3 및 presigned URL
- H2, MySQL, Redis
- k6 성능 테스트

기술 스택의 넓이는 이미 충분하다. 이제는 새 기술을 더 추가하기보다 현재 사용하는 기술의 실패 조건과 운영 방법을 깊게 다루는 것이 효과적이다.

## 4. 주요 보완 영역

### 4-1. 정책을 코드보다 먼저 결정하는 습관

구현 후에 `sortOrder`, `isPrivate` 등의 의미나 중복 정책을 확인하는 경우가 있었다. 3년차에게는 다음 순서로 작업하는 능력이 기대된다.

```text
요구사항 확인
→ 도메인 정책 결정
→ 실패 조건 정의
→ DB 제약과 트랜잭션 설계
→ 코드 구현
→ 테스트
```

기능 구현 전에 최소한 다음 질문에 답한다.

- 필수 값과 선택 값은 무엇인가?
- 중복은 허용하는가?
- 수정과 삭제 정책은 무엇인가?
- 동시 요청이 들어오면 어떻게 되는가?
- Entity와 DB에서 각각 무엇을 보장할 것인가?
- 실패하면 호출자에게 어떤 결과를 전달할 것인가?

### 4-2. 테스트와 Git 작업의 완결성

큰 변경 후 여러 기존 테스트가 한꺼번에 깨졌고, 작업 트리에 코드·테스트·문서·정적 파일과 `.DS_Store`가 섞여 있었다.

3년차 수준의 신뢰를 주는 작업 방식은 다음과 같다.

- 변경을 작은 단위로 나눈다.
- 변경 직후 관련 단위 테스트를 실행한다.
- 작업 완료 전에 전체 테스트를 실행한다.
- 한 커밋에는 하나의 논리적 목적만 담는다.
- 로컬 생성 파일을 `.gitignore`로 차단한다.
- CI에서 빌드와 테스트를 자동으로 실행한다.

이는 코드 스타일보다 동료의 신뢰에 더 직접적인 영향을 준다.

### 4-3. JPA와 DB에 대한 운영 수준의 이해

현재 경험한 H2 ID 충돌, nullable 컬럼이 포함된 유니크 제약, 양방향 연관관계 문제는 좋은 학습 소재다. 다음 단계에서는 해결 방법뿐 아니라 동작 원리까지 설명할 수 있어야 한다.

핵심 학습 주제:

- 영속성 컨텍스트와 dirty checking
- flush 시점과 트랜잭션 경계
- 연관관계의 주인과 `mappedBy`
- cascade와 `orphanRemoval`
- LAZY 로딩, N+1, fetch join, batch fetch
- 복합 유니크 제약과 `NULL`
- Entity의 중복 검사만으로 동시 요청을 막을 수 없는 이유
- 인덱스 선택도와 컬럼 순서
- `EXPLAIN` 실행 계획 분석
- H2와 MySQL의 SQL·제약·ID 생성 차이

보완 방법:

- Flyway로 스키마 변경 이력 관리
- Testcontainers로 MySQL 기반 통합 테스트 구성
- 동시성 테스트로 유니크 제약과 락 정책 검증

### 4-4. 운영 경험의 증거

현재 프로젝트에는 여러 기술이 있지만, “운영 중 어떤 실패가 발생했고 어떻게 탐지·복구·재발 방지했는가”의 증거는 더 필요하다.

준비해야 할 시나리오:

- Kafka 메시지 중복 발행·소비
- 소비자 실패 시 재시도와 DLQ
- 외부 시스템 타임아웃과 장애 전파
- 미디어 인코딩 콜백의 중복과 순서 변경
- 구조화된 로그와 request/correlation ID를 통한 요청 추적
- 메트릭, 대시보드, 알람
- 배포 실패 시 롤백
- 장애 재현 테스트와 재발 방지 문서

실제 운영 환경이 없다면 Docker Compose와 장애 주입 테스트를 통해 실패 상황을 의도적으로 만들어도 된다.

### 4-5. 네이밍보다 트레이드오프를 설명하는 능력

네이밍 컨벤션을 정리한 것은 좋지만, 면접과 실무에서는 이름보다 선택의 이유가 더 중요하다.

다음 질문에 무조건 한 줄 정답이 아니라 장단점과 대안을 포함해 답할 수 있어야 한다.

- 왜 `Movie`가 `MovieGenre` 추가를 책임지는가?
- 왜 Entity 중복 검사와 DB 유니크 제약이 모두 필요한가?
- 중복을 예외로 처리했을 때 API 사용성에 어떤 영향이 있는가?
- `PersonReadService`가 조회와 변경을 모두 담당하는 현재 구조는 적절한가?
- 트랜잭션 경계를 왜 그 위치에 두었는가?
- 다른 설계를 선택했을 때 어떤 장단점이 있는가?

“클린해 보여서”보다 무결성, 동시성, 실패 처리, 변경 비용 관점으로 설명한다.

## 5. 보완 우선순위

가장 효과가 큰 순서는 다음과 같다.

1. GitHub Actions에서 전체 빌드와 테스트를 자동 실행한다.
2. Flyway와 Testcontainers MySQL을 도입한다.
3. `PersonReadService` 같은 비대한 서비스의 Command/Query 책임을 분리한다.
4. `IllegalArgumentException`을 도메인 예외과 일관된 API 에러 코드로 정리한다.
5. Kafka 중복·재시도·장애 시나리오 테스트를 추가한다.
6. k6 결과를 `변경 전 → 원인 → 개선 → 변경 후` 수치로 정리한다.
7. Docker 기반 실행 환경과 로그·메트릭·알람을 구성한다.
8. 각 기술 선택을 2분 이내에 설명하는 면접 연습을 한다.

## 7. 면접 준비 체크리스트

다음 질문에 코드를 보지 않고도 자신의 선택을 설명할 수 있는지 확인한다.

### Java / Spring / JPA

- Entity 생성자를 제한하고 정적 팩토리를 사용한 이유는?
- `change`와 `apply`를 나눈 이유는?
- 양방향 연관관계에서 연관관계의 주인은 어느 쪽인가?
- `cascade = ALL` 과 `orphanRemoval = true`의 차이는?
- flush 시점에 예외이 발생하면 어떤 영향이 있는가?
- LAZY 연관관계에서 N+1을 어떻게 탐지하고 해결했는가?

### DB / 동시성

- Entity에서 중복을 검사해도 DB 유니크 제약이 필요한 이유는?
- 유니크 제약에 nullable 컬럼이 포함되면 어떤 문제가 생길 수 있는가?
- 낙관적 락과 비관적 락을 언제 선택하는가?
- 인덱스 컬럼 순서를 어떻게 결정하는가?
- H2 테스트가 MySQL 운영 환경을 완전히 대체할 수 없는 이유는?

### 인증 / 보안

- access token과 refresh token의 책임을 왜 나누었는가?
- refresh token rotation에서 기존 토큰 재사용을 어떻게 탐지하는가?
- HttpOnly, Secure, SameSite의 역할은?
- 쿠키 기반 인증에서 CSRF 보호가 필요한 이유는?

### Kafka / 운영

- Kafka consumer가 같은 메시지를 두 번 처리하면 어떻게 되는가?
- 메시지 처리와 DB 트랜잭션 사이의 일관성을 어떻게 보장할 것인가?
- 재시도 횟수와 DLQ 전환 기준은?
- 인코딩 콜백이 순서가 바뀌어 도착하면 어떻게 막을 것인가?
- 장애 발생 시 어떤 로그와 메트릭을 먼저 확인할 것인가?

## 8. 포트폴리오에 남겨야 할 증거

기술 이름을 나열하는 대신 각 주제를 다음 형식으로 정리한다.

```text
문제
→ 운영·비즈니스 영향
→ 원인
→ 검토한 대안
→ 최종 선택과 이유
→ 구현
→ 테스트 또는 측정 결과
→ 한계와 다음 개선 방향
```

추천 주제:

- refresh token 회전과 탈취 탐지
- 필모그래피 조회 N+1 및 인덱스 개선
- `MoviePerson` / `MovieGenre` 도메인 불변식 설계
- H2 ID 충돌과 DB 생성 전략 개선
- Kafka 미디어 인코딩의 실패·재시도·멱등성
- k6를 활용한 성능 개선 전후 비교

## 9. 최종 조언

현재 부족한 것은 코딩 재능이나 새로운 기술 스택의 개수가 아니다.

보완해야 할 핵심은 다음 한 문장으로 정리할 수 있다.

> 요구사항을 스스로 정의하고, 선택의 이유를 설명하고, 테스트와 운영까지 책임진 완결된 경험을 만들어야 한다.

Kafka, Redis, Kubernetes 같은 기술 이름을 하나 더 추가하는 것보다 Onfilm의 한 기능을 요구사항, DB, 동시성, 테스트, 배포, 장애 대응까지 끝내는 편이 3년차 역량을 훨씬 강하게 증명한다.
