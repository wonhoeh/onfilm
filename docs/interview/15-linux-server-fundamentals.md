# Linux와 서버 기본

- 작성일: 2026-09-14
- 관련 로드맵: [백엔드 서버·네트워크·인프라 학습 순서](14-backend-server-network-infrastructure-study-roadmap.md)
- 학습 목표: 서버에서 애플리케이션이 실행되는 구조와 CPU·메모리 사용 방식을 OnFilm 사례로 설명한다.

## 01. 서버란 무엇인가

서버는 특정 제품명이 아니라 다른 프로그램의 요청을 받아 처리하는 역할을 뜻한다. 문맥에 따라 다음 두 가지 의미로 사용한다.

- 서버 컴퓨터: 애플리케이션이 실행되는 컴퓨터
- 서버 프로그램: 요청을 받아 처리하는 프로그램

OnFilm에 적용하면 다음과 같다.

```text
EC2 인스턴스: 서버 컴퓨터
Ubuntu: 운영체제
JVM: Java 프로그램의 실행 환경
Spring Boot 애플리케이션: 서버 프로그램
Tomcat: HTTP 요청을 받아 Spring에 전달
MySQL: 데이터 요청을 처리하는 DB 서버
```

따라서 “API 서버가 종료됐다”는 말은 상황에 따라 EC2가 종료됐다는 뜻일 수도 있고, EC2는 실행 중이지만 Java 프로세스가 종료됐다는 뜻일 수도 있다. 장애를 설명할 때는 어느 쪽인지 구분해야 한다.

## 02. 프로그램과 프로세스

프로그램은 디스크에 저장된 실행 파일이고, 프로세스는 그 프로그램이 실제로 실행되고 있는 상태다.

```text
onfilm-api.jar
→ 디스크에 저장된 프로그램

java -jar onfilm-api.jar
→ 프로그램을 실행해 생성된 Java 프로세스
```

같은 JAR 파일을 여러 번 실행하면 프로그램 파일은 하나지만 프로세스는 여러 개 만들어질 수 있다. 운영체제는 각 프로세스에 PID라는 번호를 부여한다.

```text
java[6814]
```

여기서 `java`는 실행 중인 프로그램이고 `6814`는 프로세스 번호인 PID다.

## 03. 프로세스와 스레드

프로세스는 실행 중인 애플리케이션 전체이고, 스레드는 프로세스 내부에서 실제 작업을 수행하는 실행 단위다.

```text
OnFilm API Java 프로세스
├── main 스레드
├── Tomcat 요청 처리 스레드
├── Outbox 발행 스레드
└── 기타 스케줄러 스레드
```

하나의 프로세스에 속한 스레드는 Heap 메모리 등 프로세스의 자원을 공유한다. 각 스레드는 자신의 Stack을 가진다.

영상 인코딩을 API 프로세스 안에서 실행하면 인코딩 작업과 HTTP 요청 처리가 같은 CPU와 메모리를 두고 경쟁한다. OnFilm이 인코딩을 별도 Worker 프로세스로 분리한 이유도 여기에 있다.

```text
API 프로세스: 사용자 요청 처리
Worker 프로세스: CPU를 많이 사용하는 영상 변환
```

### 이해 확인

1. `onfilm-api.jar`는 무엇인가?
   - 실행 전 디스크에 저장된 프로그램이다.
2. `java[6814]`는 무엇인가?
   - PID가 6814인 Java 프로세스다.
3. Tomcat 요청을 동시에 처리하는 단위는 무엇인가?
   - Java 프로세스 안의 요청 처리 스레드다.
4. `8080` 포트를 사용하는 주체는 무엇인가?
   - Java 프로세스가 운영체제로부터 소켓을 열어 해당 포트를 사용한다.

## 04. CPU와 메모리

### CPU의 역할

CPU는 프로그램의 명령을 실제로 계산하고 실행한다. 프로세스의 스레드가 실행할 준비가 되면 운영체제의 스케줄러가 어느 CPU 코어에서 언제 실행할지 정한다.

CPU 코어가 하나인데 실행할 스레드가 여러 개라면 운영체제는 각 스레드를 매우 짧은 시간 동안 번갈아 실행한다. 이 교체를 Context Switching이라고 한다. 스레드를 무조건 많이 만든다고 처리 속도가 계속 빨라지지 않는 이유다.

```text
프로세스
  └── 실행할 스레드
          ↓
운영체제 스케줄러
          ↓
CPU 코어에서 명령 실행
```

### CPU 코어와 CPU 스레드

- CPU 코어: 명령을 실제로 계산하는 물리적인 처리 장치
- CPU 스레드: 운영체제가 CPU에 동시에 맡길 수 있는 작업 수

예를 들어 `6코어 12스레드`는 실제 계산 장치 6개가 운영체제에 작업 자리 12개를 제공한다는 뜻이다. 일반적으로 하나의 코어가 두 작업의 실행 상태를 관리하며, 운영체제는 이를 12개의 논리 CPU로 인식한다.

```text
물리 코어 1개
├── CPU 스레드 1
└── CPU 스레드 2
```

같은 코어에 속한 CPU 스레드는 일부 계산 자원을 공유한다. 따라서 `6코어 12스레드`는 `12코어`와 같은 성능을 의미하지 않는다.

### CPU 스레드와 프로세스 스레드의 관계

CPU 스레드는 하드웨어가 제공하는 작업 자리이고, 프로세스 스레드는 애플리케이션이 만든 소프트웨어 작업 단위다. 운영체제는 실행할 프로세스 스레드를 CPU 스레드에 배정한다.

```text
Java 프로세스 스레드
        ↓
운영체제 스케줄러
        ↓
CPU 스레드
        ↓
물리 코어에서 계산
```

예를 들어 CPU가 12스레드이고 Java 프로세스에 스레드가 200개 있어도 200개가 모두 동시에 CPU를 사용하는 것은 아니다. 실행 가능한 일부 스레드만 CPU에 배정되고, 나머지는 CPU나 DB·네트워크 응답 등을 기다린다. 또한 CPU는 다른 프로세스의 스레드도 함께 처리하므로 12개의 작업 자리를 Java 프로세스 하나가 항상 독점하는 것도 아니다.

일반 API 요청은 DB나 네트워크 응답을 기다리는 시간이 있어 Tomcat 스레드를 CPU 스레드보다 많이 둘 수 있다. 반면 FFmpeg처럼 CPU를 계속 사용하는 작업은 실행 수를 지나치게 늘리면 CPU 경쟁과 Context Switching이 증가할 수 있다.

한 문장으로 정리하면 다음과 같다.

> CPU 스레드는 운영체제가 CPU에 동시에 맡길 수 있는 작업 수를 의미한다.

### CPU-bound와 I/O-bound

- CPU-bound 작업: 계산량이 많아 CPU 사용 시간이 성능을 좌우한다.
- I/O-bound 작업: DB, 파일, 네트워크 응답을 기다리는 시간이 성능을 좌우한다.

OnFilm의 FFmpeg 영상 인코딩은 대표적인 CPU-bound 작업이다. 일반 API 요청은 로직 계산도 하지만 DB나 네트워크 응답을 기다리는 비중이 커 I/O-bound 성격이 강하다.

CPU-bound 작업을 API와 같은 서버에서 실행하면 다음 문제가 생길 수 있다.

1. 인코딩이 CPU 시간을 많이 사용한다.
2. Tomcat 요청 처리 스레드가 CPU를 제때 사용하지 못한다.
3. 일반 API의 응답 시간이 증가한다.
4. 요청이 계속 들어오면 대기 작업이 쌓일 수 있다.

따라서 OnFilm은 API와 Worker를 분리해 CPU 사용량이 큰 작업이 일반 요청에 미치는 영향을 줄였다. 이것은 작업을 비동기로 바꾼 것뿐 아니라 자원 경쟁과 장애 영향을 분리한 것이다.

### 메모리의 역할

메모리는 실행 중인 프로그램의 코드와 데이터를 보관한다. Java 프로세스에서는 다음 영역을 우선 구분한다.

- Heap: `new`로 생성한 객체처럼 여러 스레드가 공유하는 데이터를 저장한다.
- Stack: 메서드 호출 정보와 지역변수 등을 저장하며 스레드마다 따로 가진다.
- Metaspace: JVM이 클래스 정보를 저장한다.
- Native Memory: JVM, 스레드, 네트워크 버퍼 등이 Heap 밖에서 사용하는 메모리다.

```text
Java 프로세스 메모리
├── Heap: 객체 저장, 스레드 간 공유
├── Thread Stack: 메서드 호출과 지역변수, 스레드별 분리
├── Metaspace: 클래스 정보
└── Native Memory: JVM 및 운영체제 수준의 메모리
```

Garbage Collector는 더 이상 사용하지 않는 Heap 객체를 찾아 정리한다. Heap 사용량이 순간적으로 높다는 사실만으로 메모리 누수라고 판단하면 안 된다. GC 이후에도 사용량이 계속 증가하는지 장시간 추세를 확인해야 한다.

### 메모리가 부족하면 발생하는 일

- JVM Heap이 부족하면 `OutOfMemoryError`가 발생할 수 있다.
- 운영체제 전체 메모리가 부족하면 Swap을 사용하거나 프로세스를 강제 종료할 수 있다.
- Swap은 디스크를 메모리처럼 사용하므로 속도가 매우 느리다.
- 컨테이너나 `systemd`에 메모리 제한이 있다면 시스템 전체에 여유가 있어도 해당 프로세스가 종료될 수 있다.

### 확인 명령어

```bash
# 전체 CPU와 프로세스 상태
top

# 전체 메모리 상태
free -h

# CPU, 메모리, 실행 대기와 I/O 상태를 1초마다 확인
vmstat 1

# 특정 프로세스의 PID, CPU, 메모리, 실제 점유 메모리 확인
ps -o pid,ppid,%cpu,%mem,rss,cmd -p <PID>
```

`free -h`에서 `free` 값만 보고 메모리가 부족하다고 판단하지 않는다. Linux는 사용하지 않는 메모리를 파일 Cache로 활용하고 필요할 때 돌려주기 때문에 일반적으로 `available` 값을 함께 확인한다.

### OnFilm에서 확인할 주요 지표

- `process_cpu_usage`: Java 프로세스의 CPU 사용 비율
- `system_cpu_usage`: 서버 전체의 CPU 사용 비율
- `jvm_memory_used_bytes`: JVM이 사용하는 메모리
- `jvm_memory_max_bytes`: JVM이 사용할 수 있는 최대 메모리
- `jvm_gc_pause_seconds`: GC로 애플리케이션 실행이 멈춘 시간

### 이해 확인

1. FFmpeg 인코딩은 왜 CPU-bound 작업인가?
   - 영상 압축과 변환을 위해 많은 계산을 수행하기 때문이다.
2. 스레드를 많이 만들면 CPU-bound 작업이 계속 빨라지는가?
   - 아니다. 사용 가능한 CPU 코어보다 실행할 스레드가 지나치게 많으면 Context Switching 비용이 증가한다.
3. Java Heap 사용량이 높으면 바로 메모리 누수인가?
   - 아니다. GC 이후에도 사용량이 계속 증가하는지 추세를 확인해야 한다.
4. Linux의 `free` 메모리가 적으면 바로 메모리 부족인가?
   - 아니다. Cache로 사용 중인 메모리가 반환될 수 있으므로 `available`도 확인해야 한다.
5. API와 Worker 분리는 어떤 자원을 격리하는가?
   - CPU와 메모리 사용, 프로세스 장애의 영향을 분리한다. 별도 EC2에서 실행하면 운영체제와 하드웨어 자원까지 더 강하게 분리된다.
