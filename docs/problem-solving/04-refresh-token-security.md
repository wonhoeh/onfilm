# Refresh Token 회전과 재사용 방어

- 작업일: 2026-08-20
- 문서 작성일: 2026-08-24
- 관련 커밋: `44a635e`
- 상태: 완료. 현재 서비스 규모에 따라 사용자 단위 세션 폐기 정책 유지

## 문제

Refresh Token 회전 과정에는 동시에 같은 토큰을 사용하는 요청, 이미 폐기된 토큰의 재사용, 만료 접근 기록이 예외와 함께 롤백되는 문제가 있었다. 원문 토큰이나 해시를 로그에 남기면 보안 사고의 범위를 키울 수 있고, 여러 상태 변경 경로가 서로 다른 시간 기준을 사용하면 만료 판정도 일관되지 않는다.

## 원인

Refresh Token을 수명주기와 동시성을 가진 보안 자원이 아니라 단순 조회·삭제 데이터로 다뤘다. 실패 시 401을 던지는 트랜잭션 안에서 감사 상태까지 함께 저장해, 예외 롤백이 의도한 기록도 제거했다.

## 해결

- 원문 토큰 대신 SHA-256 해시만 저장하고 해시 UNIQUE 제약 적용
- `Clock`을 주입하여 발급·만료·폐기 시간 정책 통일
- 회전 시 기존 토큰을 폐기하고 새 토큰을 발급
- 낙관적 락으로 동시 회전 충돌 감지
- 폐기 토큰 재사용 시 해당 사용자의 모든 Refresh Token 삭제
- 재사용 감지 로그에는 사용자 ID와 이벤트만 WARN으로 기록
- 원문 토큰과 토큰 해시는 로그에서 제외
- 만료 토큰 접근은 별도 `REQUIRES_NEW` 트랜잭션에서 `lastUsedAt`, `revokedAt` 저장 후 401 반환
- 만료·폐기 토큰을 30일 보존한 뒤 스케줄러로 정리
- 잘못된 토큰, 만료, 락 충돌은 클라이언트에 공통 401로 응답

## 기술 선택과 트레이드오프

### 사용자 단위 전체 세션 폐기

폐기된 토큰 재사용은 탈취 가능성이 있는 보안 이벤트이므로 현재는 가장 단순하고 보수적인 사용자 전체 폐기를 선택했다. 다른 정상 기기의 로그인도 종료되는 비용이 있지만, 현재 서비스는 다기기 세션을 구분해야 할 요구가 크지 않다. 향후에는 `familyId`나 `sessionId`를 도입해 탈취된 토큰 계열만 폐기할 수 있다.

### `REQUIRES_NEW`로 만료 접근 기록 보존

401 예외로 외부 트랜잭션이 롤백되어도 보안 감사 정보를 남길 수 있다. 대신 별도 커밋 비용이 발생하고, 내부 메서드 호출로는 프록시가 적용되지 않으므로 별도 트랜잭션 컴포넌트 경계를 유지해야 한다.

### 낙관적 락

토큰 행 충돌은 일반 상황보다 예외 상황에 가깝기 때문에 지속적인 DB 잠금보다 낙관적 락을 선택했다. 충돌 시 재시도보다 공통 401을 반환해 이미 소비된 토큰을 다시 신뢰하지 않는다.

## 검증

- 발급·회전·폐기·만료 상태 테스트
- 같은 Refresh Token 동시 회전 테스트
- 재사용 감지 시 사용자 토큰 전체 제거 테스트
- 원문 대신 해시 저장 및 UNIQUE 제약 영속성 테스트
- 외부 트랜잭션 롤백 후에도 만료 접근 기록이 남는 테스트
- 정리 보존 기간과 스케줄러 테스트

## 결과

Refresh Token을 단순 저장 데이터가 아닌 수명주기와 보안 상태를 가진 엔티티로 정리했다. 동시 요청, 탈취 의심 재사용, 롤백되는 감사 기록까지 실패 시나리오를 명시적인 정책과 테스트로 관리하게 되었다.

## 포트폴리오 요약 후보

Refresh Token 회전에 낙관적 락과 재사용 감지를 적용하고, 탈취가 의심되면 사용자 세션 전체를 폐기하도록 설계했습니다. 401 예외로 사라지던 만료 접근 기록은 `REQUIRES_NEW` 트랜잭션으로 보존하고 민감 토큰 정보는 로그에서 제외했습니다.
