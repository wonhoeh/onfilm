# 엔티티와 Aggregate 경계 정비

- 작업일: 2026-08-17~2026-08-19
- 문서 작성일: 2026-08-24
- 관련 커밋: `df16ed6`, `9317f8d`, `9db497e`, `a3c0e03`, `6088cad`, `c5979f8`, `94d3807`, `93f17ff`, `1b1652f`
- 대상: `Movie`, `MoviePerson`, `MovieGenre`, `Genre`, `Person`, `PersonSns`, `ProfileTag`, `StoryboardProject`, `StoryboardScene`, `StoryboardCard`, `Trailer`

## 문제

엔티티마다 생성과 연관관계 관리 방식이 달랐다. 일부 자식은 팩토리에서 부모 연결까지 수행하고, 일부는 서비스가 `attach*`와 `getChildren().add()`를 직접 호출했다. Lombok getter로 실제 컬렉션이 노출되어 외부 코드가 중복 검증과 양방향 동기화를 우회할 수도 있었다.

이 구조에서는 다음 문제가 발생할 수 있었다.

- 부모가 없는 자식이나 한쪽만 연결된 연관관계 생성
- 다른 부모에 속한 자식의 조용한 재할당
- 삭제 후 자식이 이전 부모를 계속 참조
- 재정렬 요청의 중복·누락·존재하지 않는 ID를 정상 처리
- 생성과 수정 경로가 서로 다른 검증 적용
- 서비스가 JPA 컬렉션 구현과 연관관계 세부사항에 결합

## 원인

엔티티가 자신의 불변식을 지키는 객체보다 데이터 저장 구조로 사용되었고, Aggregate Root의 책임이 명확하지 않았다. 생성자, 팩토리, 서비스, 컬렉션 getter가 모두 상태 변경 통로가 되어 규칙을 우회할 수 있었다.

## 해결

다음 규칙으로 엔티티 스타일을 통일했다.

- JPA 기본 생성자는 `protected`, 비즈니스 생성자는 `private`
- Aggregate Root는 의미 있는 정적 팩토리로 생성
- 부모가 `add*`에서 자식을 생성하고 중복 검사와 양방향 연결까지 완료
- 자식 팩토리와 `attach*`·`detach*`는 package-private으로 제한
- 삭제는 부모의 `remove*`를 통해 컬렉션 제거와 양방향 해제를 함께 수행
- 컬렉션 getter는 `Collections.unmodifiableList`로 노출
- 생성과 변경이 같은 규칙을 쓰면 private `apply*`로 검증을 공유
- 컬럼 길이는 도메인 상수와 JPA 매핑에서 함께 사용
- 순서가 도메인 상태인 컬렉션은 `@OrderColumn`로 영속화
- 전체 재정렬 요청은 기존 원소의 정확한 순열일 때만 허용
- 전체 교체는 ID가 같은 기존 엔티티를 재사용하여 불필요한 delete/insert를 줄임
- `GenreName`과 태그 정규화 정책으로 공백·대소문자·유니코드 표현이 다른 논리적 중복 방지
- 표준 MovieGenre 연결 시 활성 Genre인지, 전달된 이름과 실제 Genre가 일치하는지 검증
- 장르 접두어 검색에서 `%`, `_`, escape 문자를 리터럴로 처리

예를 들어 Storyboard의 상태 변경은 다음 경계로 정리했다.

```text
Person.addStoryboardProject()
  └─ StoryboardProject.addScene()
       └─ StoryboardScene.add/replace/removeCard()
```

서비스는 더 이상 자식 생성과 부모 컬렉션 수정을 조립하지 않고 Aggregate Root의 공개 API만 호출한다.

## 기술 선택과 트레이드오프

### 부모가 자식 생성을 책임지는 방식

생성과 연결을 한 번에 완료해 불완전한 객체가 만들어질 경로를 줄였다. 반면 부모 클래스의 메서드가 늘어나고, 자식을 독립적으로 생성하는 테스트가 어려워진다. 이는 자식의 생명주기가 부모에 종속된 모델에서는 의도한 제약이다. `Genre`나 기존 `Person`처럼 독립 Aggregate인 객체는 새로 만들지 않고 인자로 받는다.

### 읽기 전용 컬렉션

변경 경로를 도메인 메서드로 제한하지만, 호출자가 정렬 결과를 직접 반영하던 코드는 모두 수정해야 한다. 또한 반환 view는 깊은 불변이 아니므로 자식 자체의 상태 변경은 여전히 자식의 공개 API 정책에 의존한다.

### `cascade = ALL`과 `orphanRemoval = true`

부모와 생명주기를 완전히 공유하는 Scene, Card, Trailer 등에만 적용했다. 삭제 구현은 단순해지지만 공유 엔티티에 잘못 사용하면 의도하지 않은 연쇄 삭제가 발생하므로 `Genre` 같은 독립 참조에는 적용하지 않았다.

### 원문과 정규화 값을 함께 보존

Genre와 ProfileTag는 사용자에게 보여줄 원문과 중복 비교·검색에 사용할 정규화 값을 구분했다. 표시 품질을 유지하면서 공백이나 대소문자 차이로 생기는 중복을 막을 수 있지만, 정규화 알고리즘이 바뀌면 기존 데이터 재계산과 마이그레이션이 필요하다. 검색어의 SQL 와일드카드는 자동완성 의도와 다르므로 escape 처리해 사용자가 입력한 문자 그대로 검색하도록 했다.

### 스크립트 정책 보류

`scriptHtml`의 허용 HTML, 크기, 보안 정제 정책이 확정되지 않은 상태에서 임의의 제약을 도메인 규칙으로 고정하지 않았다. 현재 확인 가능한 구조적 리팩토링만 완료하고 정책 수립 후 개선하도록 남겼다. 이는 불확실한 요구사항을 코드로 성급하게 확정하지 않은 선택이다.

## 검증

- 생성·변경 시 null, blank, 길이 경계 테스트
- 동일 자식 중복 추가와 다른 부모 재할당 거부 테스트
- 추가·삭제 시 양방향 연결/해제 테스트
- 외부 컬렉션 수정 불가 테스트
- 재정렬의 정상·중복·누락·존재하지 않는 ID 테스트
- orphanRemoval과 `sort_order` 영속성 테스트
- H2 기반 Aggregate 영속성 회귀 테스트
- Genre·ProfileTag 정규화 경계와 논리적 중복 테스트
- `%`, `_`, escape 문자가 포함된 장르 검색 테스트

## 결과

도메인 규칙이 서비스의 호출 순서가 아니라 엔티티 공개 API에 의해 보장되도록 변경했다. 새 엔티티를 추가할 때도 생성, 연결, 삭제, 컬렉션 공개 방식에 동일한 기준을 적용할 수 있도록 별도 컨벤션 문서로 일반화했다.

## 포트폴리오 요약 후보

JPA 엔티티별로 달랐던 생성과 양방향 연관관계 관리 방식을 Aggregate Root 중심으로 통일했습니다. 부모가 자식 생성·중복 검증·연결과 해제를 책임지게 하고 컬렉션 변경을 캡슐화했으며, orphanRemoval과 순서 영속성을 포함한 도메인·영속성 테스트로 불변식을 검증했습니다.
