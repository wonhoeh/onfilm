# DB 트랜잭션과 외부 I/O 경계 분리

- 작업일: 2026-08-25
- 문서 작성일: 2026-08-25
- 관련 커밋: `0a5e93a`, `aabe3dd`, `7b8cf7f`, `16bca90`, `827a860`, `e11eae9`, `5808bdb`
- 상태: 완료

## 문제

서비스 책임을 Command와 Query로 나눈 뒤 트랜잭션 annotation의 위치는 명확해졌지만, 일부 쓰기 서비스는 DB 변경과 외부 작업을 메서드 전체의 단일 트랜잭션으로 묶고 있었다.

- `MovieMediaService`가 Movie와 편집 권한을 조회한 뒤 ffmpeg 인코딩과 S3 저장이 끝날 때까지 트랜잭션 유지
- `PersonMediaService`가 Person을 조회한 뒤 프로필·필모그래피 파일 저장이 끝날 때까지 트랜잭션 유지
- 인코딩 완료 요청이 `MediaUploadRequest`를 비관적 잠금으로 조회한 상태에서 S3 `HeadObject` 실행
- Worker 완료 Callback이 Job을 조회한 트랜잭션 안에서 결과 파일의 S3 존재 여부 확인
- 회원가입과 로그인 트랜잭션 안에서 의도적으로 느린 BCrypt 인코딩·비교 수행
- 커밋 후 파일 삭제 Publisher를 트랜잭션 밖에서 호출하면 `@TransactionalEventListener`가 요청을 처리하지 않지만 호출자는 성공한 것처럼 진행할 가능성 존재

이 구조는 즉시 데이터 오류를 만들지는 않더라도 외부 시스템 지연과 CPU 연산 시간만큼 DB 커넥션과 영속성 컨텍스트를 오래 점유한다. 비관적 잠금 중 S3 응답이 늦어지면 같은 업로드 요청을 처리하는 다른 트랜잭션도 함께 대기한다.

또한 DB와 스토리지는 하나의 원자적 트랜잭션에 참여하지 않는다. DB 롤백과 파일 저장·삭제의 순서를 명시하지 않으면 DB가 존재하지 않는 파일을 가리키거나, 아직 DB에서 참조 중인 기존 파일을 먼저 삭제하는 문제가 발생할 수 있었다.

## 원인

초기 구현에서는 서비스 메서드 전체에 `@Transactional`을 적용하면 유스케이스가 안전해진다고 판단했다. 하지만 DB 트랜잭션의 원자성은 S3, 로컬 파일 시스템, ffmpeg, Kafka, BCrypt까지 확장되지 않는다.

트랜잭션의 실제 책임은 다음 두 종류가 섞이면서 모호해졌다.

- DB 상태를 함께 커밋하거나 함께 롤백해야 하는 작업
- DB와 독립적으로 실패하고 별도의 재시도·보상이 필요한 외부 작업

Spring의 프록시 방식도 고려해야 했다. 같은 Bean 내부에서 `@Transactional` 메서드를 호출하면 self-invocation으로 프록시를 통과하지 않으므로, annotation만 별도 메서드에 옮겨서는 의도한 경계가 만들어지지 않는다.

## 해결

먼저 [트랜잭션 경계 감사](../review/transaction/transaction-boundary-audit.md)를 수행해 현재 경계를 유지할 영역과 개선할 영역을 구분했다.

유지한 경계는 다음과 같다.

- 일반 Query 서비스의 `@Transactional(readOnly = true)`
- 일반 Command 서비스의 짧은 쓰기 트랜잭션
- Job과 Outbox를 함께 저장하는 단일 DB 트랜잭션
- Kafka 발행과 Outbox 발행 결과 기록의 분리
- 만료 Refresh Token 접근 기록과 재사용 대응의 별도 `REQUIRES_NEW`
- 기존 파일 삭제를 DB 커밋 이후 실행하는 `AFTER_COMMIT` 이벤트

외부 I/O가 포함된 경로는 공통적으로 다음 세 단계로 분리했다.

```text
짧은 읽기 트랜잭션
  → 트랜잭션 밖 외부 I/O 또는 CPU 연산
  → 짧은 쓰기 트랜잭션에서 상태·권한 재검증 후 반영
```

### 1. 커밋 후 파일 삭제 계약 강제

`StorageFileDeletionPublisher`가 활성 트랜잭션 안에서만 유효한 삭제 요청을 발행하도록 계약을 추가했다. 삭제 대상이 있는데 활성 트랜잭션이 없으면 즉시 `IllegalStateException`을 발생시킨다.

`fallbackExecution = true`로 트랜잭션 밖에서도 즉시 삭제하도록 만들지 않았다. 이 설정은 DB 변경이 롤백돼도 기존 파일이 삭제될 수 있어 커밋 후 삭제 정책을 약화하기 때문이다.

### 2. 업로드 원본 확인과 비관적 잠금 분리

인코딩 완료 요청은 다음 흐름으로 변경했다.

1. 잠금 없는 읽기 트랜잭션에서 요청 소유권, 만료, 입력값과 기존 Job 확인
2. 트랜잭션 밖에서 S3 원본 파일 존재 확인
3. 쓰기 트랜잭션에서 `MediaUploadRequest`를 비관적 잠금으로 재조회
4. 상태와 입력을 다시 검증하고 Job, Outbox, 업로드 완료 상태를 함께 저장

S3 확인 도중 다른 요청이 먼저 완료할 수 있으므로 마지막 잠금 구간의 재검증을 생략하지 않았다. 경쟁 요청이 이미 완료했다면 새 Job과 Outbox를 만들지 않고 기존 Job ID를 반환한다.

### 3. Worker 완료 Callback 경계 분리

Worker Callback도 읽기 검증, S3 결과 파일 확인, 최종 쓰기 반영으로 분리했다. 최종 쓰기 트랜잭션은 Job 상태와 Callback 출력 정보를 다시 검증한 뒤 Movie 결과 key 반영과 Job의 `DONE` 전환을 함께 처리한다.

이미 같은 Callback이 완료됐다면 멱등하게 종료하고, `FAILED` Job의 완료 전환은 거부한다. S3 확인 중 다른 Callback이 먼저 완료한 경우에도 최종 재조회에서 완료 상태를 발견해 Movie에 결과를 중복 반영하지 않는다.

### 4. Person·Movie 미디어 오케스트레이션 분리

`PersonMediaService`와 `MovieMediaService`는 트랜잭션을 소유하지 않는 오케스트레이터로 변경했다. 별도의 `PersonMediaTransactionService`와 `MovieMediaTransactionService`가 DB 조회·권한 재검증·엔티티 변경·기존 파일 삭제 이벤트 발행만 담당한다.

```text
권한·대상 ID 확인
  → 파일 검증·인코딩·신규 파일 저장·공개 URL 계산
  → 권한 재검증·엔티티 key 변경
  → DB 커밋 후 기존 파일 삭제
```

신규 파일 저장 후 URL 변환이나 DB 변경이 실패하면 신규 파일을 최선 노력으로 보상 삭제한다. 보상 삭제까지 실패하면 원래 예외를 유지하면서 storage key와 stack trace를 오류 로그로 남긴다.

공개 URL은 DB 변경 전에 계산한다. DB가 이미 커밋된 뒤 URL 변환이 실패해 신규 파일을 보상 삭제하면 DB가 삭제된 파일을 가리킬 수 있기 때문이다.

삭제 API는 외부 스토리지를 직접 호출하지 않는다. 짧은 쓰기 트랜잭션에서 엔티티 참조를 제거하고 삭제 이벤트를 발행하며, 실제 파일 삭제는 커밋 이후 수행한다.

### 5. BCrypt와 인증 DB 작업 분리

`AuthService.signup()`과 `login()`에서 메서드 전체 쓰기 트랜잭션을 제거하고 `AuthTransactionService`를 추가했다.

회원가입은 다음 순서를 사용한다.

1. 짧은 읽기 트랜잭션으로 알려진 이메일·사용자명 중복 확인
2. 트랜잭션 밖에서 BCrypt 인코딩
3. 쓰기 트랜잭션에서 중복을 다시 확인하고 User와 Person 저장
4. DB UNIQUE 제약 충돌을 도메인 중복 예외로 변환

로그인은 User 엔티티 대신 `userId`와 `encodedPassword`만 가진 불변 `LoginSnapshot`을 읽기 트랜잭션에서 반환한다. BCrypt 비교와 Access Token 생성은 트랜잭션 밖에서 수행하고, Refresh Token 발급은 기존 `RefreshTokenService`의 자체 쓰기 트랜잭션을 사용한다.

Refresh Token 회전은 기존 토큰 소비와 신규 토큰 저장이 함께 성공해야 하므로 분리하지 않았다.

## 기술 선택과 트레이드오프

### 선택한 방법

#### 비트랜잭션 오케스트레이터와 별도 Transaction Service

외부 작업의 순서를 조율하는 서비스와 DB 원자성을 보장하는 서비스를 별도 Bean으로 분리했다. Spring 프록시를 실제로 통과하므로 self-invocation 문제를 피하고, 메서드 이름만 봐도 외부 작업과 DB 커밋 경계를 구분할 수 있다.

최종 쓰기 단계에서 대상 상태와 소유권을 다시 검증한다. 읽기 검증과 외부 작업 사이에 상태가 달라질 수 있다는 TOCTOU 문제를 허용하지 않기 위해서다.

#### 신규 파일 보상 삭제와 기존 파일 AFTER_COMMIT 삭제

DB와 스토리지에 분산 트랜잭션을 적용하는 대신 파일의 역할에 따라 실패 순서를 다르게 처리했다.

- 신규 파일: 먼저 저장하고 DB 반영 실패 시 보상 삭제
- 기존 파일: DB 참조 제거가 커밋된 뒤 삭제

이 방식은 분산 트랜잭션 없이도 사용자에게 노출되는 참조 무결성을 우선 보장하며, 파일 삭제 실패는 로그와 후속 정리 대상으로 남긴다.

#### 잠금 밖 외부 확인과 잠금 안 재검증

비관적 잠금은 중복 Job 생성을 막는 짧은 임계 구역에만 유지했다. S3 `HeadObject`는 잠금 전에 실행하고, 잠금 획득 후 상태를 재검증해 동시 요청 안전성을 유지했다.

#### BCrypt 전후 중복 이중 확인

회원가입은 사전 확인과 저장 직전 확인을 모두 수행한다. 이미 존재하는 계정에는 비싼 BCrypt 연산을 피하고, BCrypt 실행 중 발생한 동시 가입은 최종 확인과 DB UNIQUE 제약으로 막는다.

### 검토한 대안

#### 서비스 메서드 전체 트랜잭션 유지

구현은 단순하고 하나의 영속성 컨텍스트에서 엔티티를 계속 사용할 수 있다. 하지만 S3와 ffmpeg 지연 동안 DB 커넥션과 잠금을 점유하므로 트래픽 증가 시 장애 범위가 커진다.

#### 같은 Bean의 내부 메서드에 `@Transactional` 추가

파일 변경량은 적지만 내부 호출은 Spring 프록시를 통과하지 않아 원하는 새 트랜잭션이 적용되지 않는다. 트랜잭션 전용 Bean을 분리했다.

#### S3 작업까지 XA 분산 트랜잭션으로 묶기

일반적인 S3 API와 ffmpeg는 DB XA 트랜잭션 참여자가 아니다. 구현·운영 복잡도에 비해 얻는 이점이 없으므로 명시적 보상과 커밋 후 이벤트를 선택했다.

#### 파일을 먼저 삭제한 뒤 DB 변경

DB 롤백 시 엔티티가 이미 삭제된 파일을 계속 참조하게 된다. 기존 파일은 커밋 전까지 유지하고 `AFTER_COMMIT`에 삭제하도록 했다.

#### S3 확인 결과만 믿고 최종 재검증 생략

외부 확인 중 다른 요청이 상태를 변경할 수 있어 중복 Job·Outbox가 만들어질 수 있다. 추가 DB 조회 비용을 감수하고 최종 잠금 구간에서 상태를 다시 검증했다.

#### 회원가입 중복 확인을 한 번만 수행

사전 확인만 하면 경쟁 조건에 취약하고, 저장 트랜잭션 확인만 하면 이미 존재하는 계정에도 BCrypt 비용이 발생한다. 조회가 중복되는 비용을 감수하고 사전 확인, 최종 확인, UNIQUE 제약의 세 단계로 방어했다.

### 감수한 비용

- 오케스트레이터와 Transaction Service가 분리되어 클래스와 테스트 수가 증가했다.
- 읽기 검증과 최종 쓰기 검증 때문에 일부 DB 조회가 두 번 실행된다.
- S3 존재 확인 직후 파일이 삭제되는 시간차까지 완전히 제거할 수는 없다.
- DB 커밋 결과를 알 수 없는 네트워크 장애에서는 신규 파일 보상 삭제 여부를 완벽하게 결정하기 어렵다.
- 보상 삭제가 계속 실패하면 참조되지 않는 파일이 남으므로 운영 정리 작업이 필요하다.
- 회원가입은 중복 방어를 위해 이메일·사용자명 조회를 사전과 최종 단계에서 반복한다.
- 서비스 흐름을 이해할 때 비트랜잭션 오케스트레이터와 실제 트랜잭션 Bean을 함께 살펴봐야 한다.

## 검증

실제 Spring 트랜잭션 프록시를 사용하는 경계 테스트에서 `TransactionSynchronizationManager.isActualTransactionActive()`로 각 호출 시점의 활성 여부를 검증했다.

- `MediaEncodeJobTransactionBoundaryTest`: 원본 S3 확인은 트랜잭션 밖, 1차 조회와 잠금 저장은 트랜잭션 안
- `MediaEncodeJobCompletionTransactionBoundaryTest`: 결과 파일 확인은 트랜잭션 밖, Job 조회와 Movie·Job 반영은 트랜잭션 안
- `PersonMediaTransactionBoundaryTest`: 파일 저장·URL 변환은 트랜잭션 밖, Person 변경과 삭제 이벤트 발행은 트랜잭션 안
- `MovieMediaTransactionBoundaryTest`: ffmpeg 인코딩·스토리지 저장은 트랜잭션 밖, 권한 검증과 Movie 변경은 트랜잭션 안
- `AuthTransactionBoundaryTest`: BCrypt·Access Token 생성은 트랜잭션 밖, 사용자 조회·저장과 Refresh Token 발급은 각각 자체 트랜잭션 안

실패와 경쟁 조건은 다음 테스트로 확인했다.

- 활성 트랜잭션 없는 파일 삭제 이벤트 발행 거부
- DB 롤백 시 기존 파일 미삭제, 커밋 이후에만 삭제
- 파일 하나의 삭제 실패 후 나머지 파일 삭제 계속 수행
- DB 변경 실패 시 신규 Person·Movie 파일 보상 삭제
- 공개 URL 변환 실패 시 신규 Person 파일 보상 삭제와 DB 미변경
- 원본 파일 부재 시 Job과 Outbox 미생성
- S3 확인 중 다른 요청이 먼저 완료한 경우 기존 Job 반환
- 결과 파일 부재 시 Movie와 Job 미변경
- 중복 Worker Callback 멱등 처리와 `FAILED → DONE` 전환 거부
- 회원가입 저장 직전 중복 재검증과 DB UNIQUE 경쟁 예외 변환
- 로그인 이메일 부재와 비밀번호 불일치에 동일한 인증 오류 반환
- Job과 Outbox의 동시 커밋·롤백, Refresh Token `REQUIRES_NEW` 관련 기존 영속성 테스트 유지

최종 `./gradlew test` 결과 269개 테스트가 통과했으며 실패, 오류와 건너뜀은 모두 0개였다. `git diff --check`도 통과했다.

감사 문서부터 인증 경계 분리까지 관련 커밋 범위는 27개 파일에서 2,251줄 추가, 435줄 삭제로 확인했다. 이는 성능 개선 수치가 아니라 트랜잭션 경계와 테스트가 인증, 스토리지, 영화, Kafka 영역에 적용된 변경 범위를 나타낸다. DB 커넥션 점유 시간이나 처리량은 별도 부하 테스트를 수행하지 않았으므로 개선 수치를 기록하지 않았다.

## 결과

변경 전에는 외부 파일 저장, S3 존재 확인, ffmpeg와 BCrypt 처리 시간이 DB 트랜잭션 수명에 포함됐다. 변경 후 DB 트랜잭션은 조회 스냅샷과 최종 상태 변경 구간으로 제한되고, 느리거나 독립적으로 실패하는 작업은 트랜잭션 밖에서 실행된다.

비관적 잠금은 중복 Job 생성을 막는 짧은 구간에만 사용하며, 외부 작업 이후 상태·소유권 재검증으로 동시성 안전성을 유지한다. DB와 스토리지의 정합성은 신규 파일 보상 삭제와 기존 파일 커밋 후 삭제라는 명시적인 정책으로 관리한다.

테스트는 단순히 annotation 존재 여부를 확인하지 않고 실제 Spring 프록시 환경에서 외부 호출 시점의 트랜잭션 활성 상태를 검증한다. 이후 서비스가 변경돼 외부 I/O가 다시 트랜잭션 안으로 들어오면 경계 테스트가 회귀를 탐지한다.

## 후속 과제

- 운영 환경에서 DB 커넥션 점유 시간, 트랜잭션 시간과 잠금 대기 시간을 계측해 변경 전후 성능을 비교한다.
- 보상 삭제 실패 파일과 Job으로 연결되지 않은 raw 업로드 파일을 주기적으로 정리하는 정책을 마련한다.
- S3 호출의 timeout, retry와 circuit breaker 정책을 장애 유형별로 정의한다.
- DB 커밋 성공 여부가 불명확한 장애에 대비해 파일 정합성 점검 작업을 검토한다.
- 회원가입의 사전·최종 중복 조회 비용이 실제 병목이 되면 정책을 측정하고 단순화 여부를 판단한다.
- 동시 Callback 충돌 빈도가 높아지면 Job 상태 전이의 비관적 잠금 또는 낙관적 락 충돌 변환 정책을 비교한다.

## 포트폴리오 요약 후보

S3 `HeadObject`, ffmpeg 인코딩, 파일 저장과 BCrypt가 DB 트랜잭션 및 비관적 잠금 안에서 실행되던 구조를 감사하고, 읽기 검증–외부 작업–최종 재검증·쓰기의 3단계 경계로 재설계했습니다. 신규 파일은 DB 실패 시 보상 삭제하고 기존 파일은 커밋 이후 삭제하도록 정합성 정책을 분리했으며, 실제 Spring 프록시 기반 경계 테스트와 전체 269개 테스트로 외부 I/O 시점과 동시 요청 멱등성을 검증했습니다.
