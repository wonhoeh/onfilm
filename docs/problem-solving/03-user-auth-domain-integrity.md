# User 인증 정책과 데이터 무결성

- 작업일: 2026-08-20
- 문서 작성일: 2026-08-24
- 관련 커밋: `59cfc1b`
- 상태: 완료

## 문제

이메일과 사용자명의 trim, 대소문자 처리, 형식 검증이 DTO·서비스·엔티티에 서로 다르게 구현되어 있었다. 비밀번호 필드가 `password`라는 이름으로 저장되어 원문인지 인코딩 결과인지 의미가 불명확했고, 애플리케이션의 사전 중복 확인만으로는 동시 가입 요청의 중복을 막을 수 없었다.

회원가입 시 생성한 Person을 프로필 초기화 과정에서 새 Person으로 교체할 가능성도 있어 User–Person 생명주기가 불안정했다.

## 원인

이메일·사용자명·비밀번호가 규칙을 가진 도메인 값이 아니라 일반 문자열로 취급되었고, 중복 방지를 애플리케이션 조회만으로 해결하려 했다. User와 Person 중 어느 쪽이 관계의 생명주기를 책임지는지도 명확하지 않았다.

## 해결

- `UserEmail`, `Username` 값 객체에 정규화와 검증 정책 통합
- 원본 사용자명과 비교용 `usernameNormalized` 분리
- 이메일 및 사용자명 정규화 값에 DB UNIQUE 제약 적용
- 비밀번호 필드를 `encodedPassword`로 명확히 하고 외부 노출 제한
- BCrypt의 72바이트 한계를 UTF-8 바이트 기준으로 가입 전에 검증
- `User.createPerson()`이 Person 생성과 양방향 연결을 책임지도록 변경
- 프로필 초기화는 기존 Person 객체를 수정하고 교체하지 않음
- 저장 시 `DataIntegrityViolationException`의 제약 이름을 도메인 중복 예외로 변환
- 로그인과 중복 확인도 동일한 값 객체 정책 재사용

## 기술 선택과 트레이드오프

### 값 객체로 정책 통합

모든 진입점이 같은 정규화 결과를 사용하고 테스트 범위가 명확해진다. 대신 JPA 필드와 DTO 사이 변환 코드가 추가된다. 이메일과 사용자명은 규칙과 의미가 충분히 강한 값이므로 단순 문자열보다 값 객체가 적합하다고 판단했다.

### 사전 조회와 DB UNIQUE를 함께 사용

사전 조회는 사용자에게 빠르고 구체적인 오류를 제공하지만 경쟁 조건을 막지 못한다. DB UNIQUE는 최종 무결성을 보장하지만 예외를 사용자 친화적인 오류로 변환해야 한다. 둘 중 하나를 제거하지 않고 서로 다른 목적의 방어선으로 유지했다.

### BCrypt 바이트 제한을 API 단계에서 검증

사용자가 입력한 문자 수만 검사하면 한글 같은 다바이트 문자열이 BCrypt 제한을 넘을 수 있다. UTF-8 바이트 길이를 검증해 조용한 잘림이나 환경별 오류를 막는 대신, 특정 해시 알고리즘의 제약이 입력 정책에 반영된다. 알고리즘 변경 시 정책도 함께 재검토해야 한다.

## 검증

- 이메일과 사용자명 trim·대소문자·길이·형식 테스트
- 대소문자가 다른 동시 중복 가입과 DB UNIQUE 예외 변환 테스트
- UTF-8 72바이트 경계 테스트
- 비밀번호 인코딩 값만 저장되는지 검증
- User–Person 생성과 양방향 연결 테스트
- 프로필 초기화가 기존 Person을 재사용하는 테스트

## 결과

인증 입력의 의미와 비교 기준을 한곳에 모으고, 애플리케이션 검증과 DB 제약을 함께 사용해 동시성 상황에서도 중복 계정을 방지했다. User가 Person 생명주기의 시작을 책임지게 하여 가입과 프로필 초기화 사이의 객체 교체 문제도 제거했다.

## 포트폴리오 요약 후보

이메일·사용자명 정규화를 값 객체로 통합하고 DB UNIQUE 제약과 예외 변환을 함께 적용해 동시 가입 경쟁 조건에서도 중복을 차단했습니다. BCrypt의 UTF-8 72바이트 제한과 User–Person 생명주기까지 도메인 규칙으로 정리해 인증 데이터의 의미와 무결성을 강화했습니다.
