# Storyboard 조회의 반복 DB 요청을 줄이고 AWS에서 성능 검증

- 작업일: 2026-03-28 구현, 2026-09-09 AWS 재측정
- 문서 작성일: 2026-09-09
- 관련 커밋: `b2d81c4` (Storyboard 조회 N+1 개선)
- 상태: 일부 완료 — 조회 개선·비교 측정·기존 버전 복구 완료, 준비 구간 지연 원인 분석 및 원본 백업 대조는 후속 과제

## 문제

Storyboard 프로젝트 목록에는 프로젝트 제목뿐 아니라 장면 수와 대본 미리보기가 필요하다. 프로젝트 목록을 가져온 뒤 각 프로젝트의 장면을 따로 조회하면 프로젝트 수에 비례해 DB 요청이 늘어난다.

[기존 SQL 분석 기록](../review/k6/result-storyboard.md)에서는 프로젝트 20개와 장면 200개를 조회할 때 요청당 SQL이 24회 발생했다. 장면 조회만 프로젝트별로 20회 반복됐고, 나머지는 소유권 확인과 사용자·프로젝트 조회였다.

Fetch Join으로 개선한 뒤에도 실제 AWS 환경에서 응답 시간과 자원 사용이 얼마나 달라지는지 확인할 필요가 있었다. 단순히 SQL 횟수가 줄었다는 사실만으로 처리 성능 전체가 좋아졌다고 결론 내리지 않고, 동일 데이터를 조회하는 비교용 N+1 버전과 개선 버전을 번갈아 실행했다.

## 원인

문제는 지연 로딩 자체가 아니라, 목록 응답을 만드는 과정에서 필요한 연관 데이터를 하나씩 불러오는 조회 구조였다. 프로젝트마다 장면 수를 확인하고 대본 미리보기를 만들면서 아직 읽지 않은 장면 목록을 반복 조회했다.

현재 `StoryboardQueryService.findProjectsByPublicId()`도 장면 수와 대본을 사용한다. 따라서 데이터를 사용하는 부분만 유지한 채 프로젝트와 장면을 미리 가져오지 않으면 DB 왕복이 늘어날 수 있다.

한편 AWS 재측정 중 발생한 수초 단위의 지연은 이 구조만으로 원인을 확정하지 않았다. 초기 N+1 실행에서 DB 연결 10개 사용, 연결 대기 최대 90개가 관측됐지만, Fetch Join 준비 실행에서도 지연과 일부 반복 누락이 있었다. 기동 직후 준비 작업, 캐시, SQL 로그 출력, DB 상태 등의 영향을 분리한 것은 아니다.

## 해결

프로젝트 목록에 필요한 Person·프로젝트·장면을 함께 가져오도록 조회 경로를 구성했다. 소유권 확인은 유지하고, 응답을 만들 때 필요한 장면을 프로젝트마다 추가 조회하지 않게 했다.

`PersonRepository.findByPublicIdWithStoryboards()`의 조회는 다음과 같다.

```java
SELECT DISTINCT p FROM Person p
LEFT JOIN FETCH p.storyboardProjects sp
LEFT JOIN FETCH sp.scenes
WHERE p.publicId = :publicId
```

이후 검증은 다음 순서로 진행했다.

1. 같은 사용자에게 프로젝트 20개·장면 200개가 존재하는지 확인했다.
2. API 서버에서 Fetch Join과 N+1 비교용 JAR를 번갈아 실행했다.
3. 준비 조건이 달랐던 1회차는 참고 결과로 분리했다.
4. 2·3회차는 기동 확인 후 최소 3분 대기, 초당 50회로 2분 준비 실행, 같은 조건으로 2분 본 측정 순서를 맞췄다.
5. 실행 시간과 k6 결과를 저장하고 해당 시간대의 CPU·Heap·DB 연결 지표를 확인했다.
6. 준비 구간의 지연과 실패도 보관하고, 측정 종료 후 Fetch Join JAR로 복구해 health `UP`을 확인했다.

## 기술 선택과 트레이드오프

### 선택한 방법

목록 응답에 실제로 필요한 프로젝트와 장면을 Fetch Join으로 함께 조회했다. 연관관계 전체의 로딩 정책을 바꾸는 대신 해당 조회에 필요한 데이터 범위를 명시할 수 있고, 기존 응답 생성 로직을 유지하면서 반복 DB 요청을 줄일 수 있다.

성능 검증에서는 응답 시간만 보지 않고 DB 연결 사용과 대기, 요청 오류, 실행하지 못한 반복 횟수도 확인했다. 요청이 느려져 일부 부하를 실행하지 못한 결과를 “오류 0건”만으로 정상 처리라고 해석하지 않기 위해서다.

### 검토한 대안

아래는 현재 설계와 비교할 수 있는 대안이며, 이번 실험에서 모두 구현하거나 성능을 측정한 것은 아니다.

- **연관 데이터를 항상 즉시 조회:** 다른 기능에서도 필요하지 않은 데이터를 읽을 수 있어, 이번 목록 조회만을 위한 변경 범위보다 넓다.
- **여러 프로젝트의 장면을 묶어서 조회:** 한 번에 모두 결합하기 부담스러운 경우의 대안이다. 다만 조회를 여러 번 나누고 결과를 조합하는 비용이 생긴다.
- **목록 전용 요약 조회:** 장면 수와 필요한 미리보기만 가져오면 장면 전체를 읽는 비용을 줄일 수 있다. 미리보기 선정 규칙과 장면 순서를 반영하는 별도 조회 설계가 필요하므로 후속 후보로 남겼다.
- **DB 연결 수 확대:** 대기를 줄일 가능성은 있지만 반복 SQL 자체를 줄이지는 않는다. 비교 조건을 유지하기 위해 풀 한도 10개를 변경하지 않았다.

### 감수한 비용

Fetch Join은 DB 왕복을 줄이는 대신 프로젝트와 장면을 한 번에 메모리에 올린다. 장면별 결과 행에 상위 데이터가 반복될 수 있어 SQL 횟수 감소가 DB 전송량 감소를 뜻하지는 않는다.

현재 목록은 페이지 단위 조회가 아니다. 데이터가 커지면 전체 장면 로딩 비용을 다시 평가해야 하며, 컬렉션을 함께 가져오는 조회에 단순히 페이징만 덧붙이지 않고 조회 범위를 나누는 설계가 필요하다.

## 검증

### 코드와 기존 근거

- [PersonRepository](../../src/main/java/com/onfilm/domain/movie/repository/PersonRepository.java): 프로젝트·장면 Fetch Join 확인
- [StoryboardQueryService](../../src/main/java/com/onfilm/domain/movie/service/StoryboardQueryService.java): 소유권 확인 후 목록 조회, 장면 수·대본 미리보기 생성 확인
- 기존 SQL 분석: 요청당 24회 → 3회. **2026-09-09 실행에서 SQL 횟수를 새로 계수한 결과는 아니다.**

### AWS 본 측정 2·3회차

API와 k6는 별도 EC2에서 실행하고 RDS MySQL을 사용했다. k6는 초당 50회, 2분, 사전 할당 및 최대 VU 100개로 설정했다. HTTP 200과 프로젝트 수 20개를 검증했다.

| 방식 | 회차 | 평균 | p95 | 최대 | 조회 수 | HTTP 오류 |
|---|---:|---:|---:|---:|---:|---:|
| Fetch Join | 2 | 21.22ms | 25.29ms | 405.65ms | 6,001 | 0 |
| N+1 | 2 | 55.89ms | 67.75ms | 502.28ms | 6,001 | 0 |
| Fetch Join | 3 | 21.80ms | 25.15ms | 480.56ms | 6,001 | 0 |
| N+1 | 3 | 60.44ms | 79.91ms | 943.20ms | 6,001 | 0 |

위 본 측정은 모두 응답 검증 100%, 종료 코드 0이며 미실행 반복 표시는 없었다. 로그인 1회를 포함한 전체 HTTP 요청은 실행당 6,002회이고, 표는 조회 API만의 지표다.

| 방식 | 회차 | CPU 관측 최대 | Heap 관측 최대 | DB 연결 관측 최대 | DB 연결 대기 관측 최대 |
|---|---:|---:|---:|---:|---:|
| Fetch Join | 2 | 24.30% | 147.39MiB | 1 | 0 |
| N+1 | 2 | 38.38% | 379.81MiB | 3 | 0 |
| Fetch Join | 3 | 25.90% | 241.34MiB | 1 | 0 |
| N+1 | 3 | 38.96% | 346.65MiB | 3 | 0 |

### 실패와 측정 한계

- N+1 준비 2회차 p95는 1.76초, 준비 3회차는 1.88초였다. 준비 3회차에는 반복 12회가 실행되지 못했다.
- Fetch Join 준비 3회차도 p95 490.90ms, 최대 3.24초, 미실행 반복 17회가 발생했다. 스크립트에 미실행 반복 임계값이 없어 종료 코드는 0이었다.
- N+1 준비 3회차의 첫 시도는 로그인 401로 조회 전에 종료됐다. 조회가 없던 결과를 성능 수치로 사용하지 않고 별도로 보관했다.
- 자원 지표는 Prometheus 표본 기준이다. 최댓값이 동시에 발생했다고 볼 수 없고, 대기 0도 표본 사이의 짧은 대기를 배제하지 않는다.
- Heap은 GC 시점에 영향을 받으므로 절감률로 단정하지 않았다.
- 수동 실행으로 대기 시간과 실행 간격이 완전히 같지는 않았다. CPU 크레딧, DB 캐시, 로그 처리 비용도 완전히 통제하지 않았다.
- 이 문서는 대화에서 확인한 실행 출력과 지표를 정리했다. 원본 백업 파일과의 대조는 아직 완료하지 않았다. 문서 작성 과정에서 애플리케이션 테스트를 새로 실행하지 않았다.

전체 실행 시간, JAR 식별 정보와 결과 파일명은 [AWS 성능 비교 상세 기록](../performance/storyboard-fetchjoin-aws-comparison-20260909.md)에 정리했다.

## 결과

준비 절차를 맞춘 두 번의 본 측정에서 Fetch Join의 평균 응답 시간은 21.22~21.80ms, p95는 25.15~25.29ms였다. N+1의 평균 55.89~60.44ms, p95 67.75~79.91ms보다 낮았으며, DB 연결 사용의 관측 최댓값도 3개에서 1개로 줄었다.

이는 단일 사용자·동일 데이터 반복 조회에서 확인한 결과다. 최대 처리량, 다중 사용자 성능 또는 모든 환경의 개선율로 확대하지 않는다. 위 범위는 실행별 요약값의 범위이며 전체 요청을 합쳐 계산한 p95가 아니다.

개선 효과뿐 아니라 준비 구간에서 발생한 지연과 미실행 요청도 기록해, 좋은 결과만 남기지 않고 측정 조건과 한계를 함께 설명할 근거를 마련했다. 최종적으로 API를 Fetch Join 버전으로 복구했다.

## 후속 과제

- 원본 결과·스크립트 백업의 존재와 해시를 확인하고, 공개 전 민감 정보를 검사한다.
- 비교 JAR의 소스 차이, 로그 수준 및 비밀값을 제외한 실행 설정을 대조한다.
- 준비 구간 지연이 발생한 시간대의 GC, CPU, DB 대기, SQL 로그 비용을 분석한다.
- RDS 사양·버전, CPU 크레딧 등 재현에 필요한 환경 정보를 보완한다.
- 후속 테스트에서는 미실행 반복도 실패 기준에 포함하고, 기존 결과와 실험 조건을 구분한다.
- 여러 사용자와 더 큰 데이터에서 재측정하고, 목록 전용 요약 조회 및 페이징 도입 여부를 검토한다.

## 포트폴리오 요약 후보

Storyboard 목록에서 프로젝트마다 장면을 따로 읽던 조회를 Fetch Join으로 개선했습니다. AWS에서 프로젝트 20개·장면 200개를 초당 50회씩 2분간 조회한 비교 측정에서, 준비 절차를 맞춘 각 방식의 본 측정 2회 기준 p95가 67.75~79.91ms에서 25.15~25.29ms로 감소했습니다. 본 측정의 요청 오류는 없었으며, 준비 구간의 지연과 일부 반복 누락도 별도로 기록했습니다.
