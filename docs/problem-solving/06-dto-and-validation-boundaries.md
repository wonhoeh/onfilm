# DTO와 계층별 검증 흐름 정비

> 현재 검증 위치를 결정하는 기준과 대표 사례는 [Domain Validation 위치 결정 가이드](../review/validation/domain-validation-location-guide.md)를 참고한다.

## 문제

요청·응답 DTO가 mutable class와 record로 혼재했고, `@NotNull` 같은 요청 형식 검증과 서비스의 수동 null 검사, 엔티티 검증, DB 제약의 역할이 불명확했다. 같은 검증이 여러 곳에 복사되거나 반대로 DTO 검증만 믿고 다른 호출 경로에서 잘못된 엔티티 상태를 만들 위험이 있었다.

컬렉션을 가진 record도 내부 List를 그대로 보관하면 record 자체의 불변 의도와 달리 외부에서 내용이 변경될 수 있었다.

## 원인

DTO를 단순 필드 묶음으로 보고 불변성 기준을 정하지 않았으며, 각 검증을 “중복 여부”로만 판단했다. 요청 형식, 유스케이스 조건, 도메인 불변식, 동시성 무결성이 서로 다른 실패 지점이라는 구분이 없었다.

## 해결

- Request, Response, Kafka Message, Application Event의 기본 형태를 record로 통일
- Bean Validation annotation을 record component에 선언
- 중첩 DTO에는 `@Valid`, 컬렉션 자체와 원소에는 각각 null·범위 검증 적용
- 응답·메시지·이벤트의 컬렉션은 `List.copyOf`로 방어적 복사
- 프로필 이미지 등 파일 입력 계약을 URL이 아닌 storage key로 통일
- 비밀번호 UTF-8 72바이트 custom constraint 적용
- 미사용 DTO와 레거시 콜백 계약 제거
- 검증 책임을 DTO → Service → Entity/Value Object → DB 흐름으로 문서화

계층별 기준은 다음과 같다.

| 계층 | 책임 |
|---|---|
| DTO | 요청의 null, blank, 길이, 범위, 중첩 구조 |
| Service | 현재 사용자, 권한, 존재, 소유권, 외부 파일 상태 |
| Entity/Value Object | 생성·변경 후 항상 지켜야 하는 불변식과 상태 전이 |
| DB | 동시성 상황까지 포함한 NOT NULL, FK, UNIQUE, lock |

## 기술 선택과 트레이드오프

### DTO 기본값으로 record

불변 전달 객체라는 의도가 코드에 드러나고 Lombok 생성자·getter가 줄어든다. 프레임워크가 setter와 기본 생성자를 요구하거나 단계적 조립이 반드시 필요한 경우에는 class를 예외로 허용한다. record가 참조하는 컬렉션은 자동으로 불변이 아니므로 별도 방어적 복사가 필요하다.

### 계층별 중복 검증 허용

DTO와 엔티티가 모두 제목 blank를 거부하는 것은 중복 코드처럼 보이지만 목적이 다르다. DTO는 클라이언트 오류를 빠르고 구조화해 반환하고, 엔티티는 메시지 Consumer나 테스트 등 HTTP 이외의 경로에서도 불변식을 지킨다. 서비스에는 동일 필드 검사를 다시 복사하지 않고 권한과 외부 상태처럼 서비스만 판단할 수 있는 검증을 둔다.

### DB를 최종 방어선으로 유지

사전 검증은 좋은 오류 메시지를 제공하지만 동시성 경쟁을 막지 못한다. UNIQUE와 FK를 유지하고 DB 예외를 도메인 오류로 변환하는 추가 비용을 감수했다.

## 검증

- Jakarta Validator 기반 DTO 단위 테스트
- null 컬렉션, null 원소, 중첩 DTO, 길이·숫자 경계 테스트
- 컨트롤러 validation 실패 시 422와 필드 오류 형식 테스트
- record 컬렉션 방어적 복사 테스트
- 엔티티 직접 호출 시에도 동일 불변식이 유지되는 테스트
- DB UNIQUE와 연관관계 영속성 테스트

## 결과

각 계층에서 “무엇을 왜 검증하는지”가 분명해졌고, API 계약과 도메인 불변식을 서로 대체하지 않는 다층 방어 구조를 만들었다. 새 DTO와 검증을 추가할 때 따를 수 있는 컨벤션도 함께 남겼다.

## 포트폴리오 요약 후보

혼재하던 DTO를 불변 record 중심으로 통일하고 DTO·서비스·엔티티·DB의 검증 책임을 분리했습니다. HTTP 요청 오류는 Bean Validation으로 빠르게 반환하면서도 엔티티 불변식과 DB 제약을 독립적인 방어선으로 유지해 다른 호출 경로와 동시성 상황까지 보호했습니다.
