# 스토리지 키와 트랜잭션 이후 파일 삭제

- 작업일: 2026-08-19, 후속 서비스 통합 2026-08-24
- 문서 작성일: 2026-08-24
- 관련 커밋: `b677dea`, `1b1652f`, `e1f3df3`
- 상태: 완료

## 문제

Trailer의 `url` 필드가 실제로는 내부 storage key를 저장하면서 완전한 URL도 허용했다. 파일 삭제 또한 DB 상태 변경과 같은 트랜잭션 흐름에서 즉시 실행되어, 이후 DB 트랜잭션이 롤백되면 DB는 파일을 참조하지만 실제 파일은 이미 사라지는 불일치가 발생할 수 있었다.

StoryboardCard는 클라이언트가 전달한 이미지 키를 그대로 받아 다른 Person의 파일이나 임의 경로를 연결·삭제할 가능성도 있었다. 컨트롤러마다 URL을 key로 바꾸고 저장 실패를 보상하는 코드가 반복되었다.

## 원인

영속 모델에서 “파일 식별자”와 “클라이언트 접근 주소”의 경계가 정의되지 않았고, DB 트랜잭션과 외부 스토리지를 하나의 성공 단위처럼 다뤘다. 파일 소유권과 삭제 시점도 각 서비스와 컨트롤러의 호출 순서에 의존했다.

## 해결

- 엔티티에는 공개 URL이 아닌 서버가 발급한 `storageKey`만 저장
- 공개 응답 경계에서 `StorageService.toPublicUrl()`로 URL 변환
- key의 경로 형식과 `personId` 또는 `movieId` 소유권 검증
- URL, 절대 경로, 역슬래시, 경로 탐색과 다른 Aggregate의 키 거부
- DB에서 참조를 제거한 뒤 `StorageFilesDeleteEvent` 발행
- 이벤트 리스너가 `AFTER_COMMIT` 시점에 실제 파일 삭제
- 여러 파일 중 하나의 삭제가 실패해도 경고 로그를 남기고 나머지 삭제 계속
- 신규 파일 저장 후 DB 변경이 실패하면 신규 파일을 최선 노력으로 보상 삭제
- 공통 삭제 발행 로직을 `StorageFileDeletionPublisher`로 통합
- 프로필과 Movie 파일 워크플로를 `PersonMediaService`, `MovieMediaService`로 이동

## 기술 선택과 트레이드오프

### URL 대신 storageKey

DB가 CDN 도메인과 배포 환경에 결합되지 않고 파일 소유권을 경로에서 검사할 수 있다. 대신 모든 공개 조회에서 URL 변환이 필요하며, YouTube 같은 외부 URL은 현재 모델에 직접 저장할 수 없다. 외부 영상 요구가 생기면 `STORAGE`와 `EXTERNAL` 출처를 명시적으로 모델링할 예정이다.

### 커밋 이후 이벤트 삭제

DB 롤백 시 기존 파일을 보존하는 것이 가장 중요한 선택 기준이었다. 반면 커밋 후 삭제 실패는 DB 트랜잭션으로 되돌릴 수 없으므로 고아 파일이 남을 수 있다. 현재는 경고 로그와 계속 처리 정책을 사용하며, 규모가 커지면 삭제 작업 테이블과 재시도 스케줄러를 검토한다.

### 보상 삭제

외부 스토리지와 DB를 하나의 ACID 트랜잭션으로 묶을 수 없으므로 신규 파일 저장 후 DB 실패 시 명시적인 보상 작업을 선택했다. 보상 삭제 자체도 실패할 수 있어 완전한 원자성을 제공하지는 않지만, 일반적인 실패에서 불필요한 파일 누적을 줄인다.

## 검증

- 정상 storage key와 URL·타 사용자·타 Movie key 거부 테스트
- Trailer key 단일 파일/HLS 형식 테스트
- DB 롤백 시 삭제 이벤트 미실행 테스트
- 커밋 후 삭제와 복수 파일 삭제 실패 격리 테스트
- 카드 교체 시 사용하지 않게 된 key만 삭제하는 테스트
- 미디어 서비스의 엔티티 참조 제거 및 삭제 이벤트 발행 테스트

## 결과

영속 데이터의 의미를 storage key 하나로 고정하고, 파일 소유권 검증과 공개 URL 생성을 명확한 경계로 분리했다. DB 상태와 파일 수명주기의 불일치 가능성을 줄였으며 컨트롤러에 흩어진 저장·삭제·보상 로직을 재사용 가능한 서비스로 모았다.

## 포트폴리오 요약 후보

DB에는 환경 의존적인 URL 대신 소유권 검증이 가능한 storage key만 저장하도록 미디어 정책을 통일했습니다. 파일 삭제를 트랜잭션 커밋 이후 이벤트로 옮기고 신규 파일 저장 실패에는 보상 삭제를 적용하여 DB 롤백과 외부 스토리지 사이의 불일치 위험을 줄였습니다.
