# OnFilm 로컬 데스크톱 개발 계획

작성일: 2026-09-22  
상태: 1단계 진행 중 / Electron 개발용 셸 구현·macOS 자동 스모크 검증 완료

## 1. 목표와 확정 사항

배우 한 명이 개인 PC에서 포트폴리오를 편집하고, 완성된 결과만 온라인에 게시하는 도구를 만든다.

- 개발 환경: macOS.
- 최종 실행 환경: Windows. 대상 Windows 버전·CPU 아키텍처는 착수 시 확인한다.
- UI: Electron 전용 창. 외부 브라우저에서 편집하는 방식은 사용하지 않는다.
- 기존 HTML·CSS·JavaScript 화면과 Java/Spring 기능을 가능한 범위에서 재사용한다.
- 실행 프로필: `local` 추가. 기존 `dev`, `prod`는 보존한다.
- 로컬에서 DB 저장·파일 관리·FFmpeg 인코딩을 수행한다.
- 온라인에서는 프로필 조회·영상 재생·공개 연락처 확인만 제공한다.
- 호스팅 업체는 공개 화면 결과물과 파일 용량을 확인한 뒤 선택한다.
- 사용자에게 개발 도구, 명령어, 클라우드 설정을 일상적으로 요구하지 않는다.
- 최초 설치·게시 연결은 개발자가 도울 수 있는 1인 사용 범위로 설계한다.

### 사용 흐름

```text
OnFilm 아이콘 실행 → 전용 창에서 편집 → 인코딩·미리보기
→ 게시하기 → 공유 링크 전달
→ 로컬 수정 → 게시 내용 업데이트 → 같은 링크에 새 버전 공개
```

읽기 전용 공개 화면은 게시 시점에 확정한 포트폴리오다. 이미지로 캡처한 화면이 아니라, 영상 재생과 화면 탐색이 가능한 웹페이지이며 편집 기능만 없다. 로컬 초안과 공개본을 구분한다. 게시해도 앱 실행 프로필은 `local`로 유지한다.

## 2. 범위와 미결정 사항

### 첫 버전에서 제외

- 다중 사용자 SaaS, 결제·요금제, 댓글 기능.
- 사용자별 AWS 전체 인프라 자동 생성·삭제.
- 기존 운영 구조 전체를 데스크톱 구조로 대체하는 작업.
- 중단된 인코딩을 정확히 중간 프레임부터 이어서 수행하는 기능.
- 자동 업데이트는 필수가 아니다. 먼저 수동 업데이트 시 데이터 보존을 보장한다.

### 구현 전에 결정할 항목

| 항목 | 현재 상태 | 결정 시점 |
|---|---|---|
| Windows 버전·아키텍처·검증 PC | 미확정 | 1단계 |
| Electron 소스 위치·빌드 도구·버전 | 미확정 | 1단계 |
| 최종 로컬 DB 배포 방식 | MySQL 재사용과 대안 비교 필요 | 1단계 |
| Kafka·Worker 실행 및 배포 방식 | 기존 계약 유지 기준으로 검토 | 1단계 |
| 최초 실행 계정·로컬 인증 방식 | 개발용 인증 우회는 사용하지 않음 | 2단계 |
| 게시 자격증명 보관·권한 범위 | 미확정 | 5단계 |
| 호스팅·도메인·예산·공개 기간 | 미확정 | 5단계 |
| 설치 파일 서명·배포 방법 | 비용·Windows 경고 포함 검토 | 7단계 |

개발 중에는 기존 MySQL·Kafka 환경을 사용할 수 있지만, 이를 일반 사용자용 최종 설치 방식으로 확정한 것은 아니다. Electron으로 감싼다고 DB와 Kafka 설치 문제가 해결되지는 않는다. 내장 DB나 작업 전달 방식 변경이 필요하면 별도 설계 검토·승인 후 진행한다.

## 4. 단계별 체크리스트

### 1단계. 의존성 조사와 Windows 최소 실행 실험

목적: 마지막에 Windows 설치 문제로 구조를 다시 바꾸지 않도록 핵심 위험을 먼저 확인한다.

- [ ] API·Worker·DB·Kafka·FFmpeg·파일 경로·외부 네트워크 의존성 목록 작성.
- [ ] 대상 Windows 버전·아키텍처와 실제 검증 환경 확보 여부 기록.
- [ ] Electron 최소 창에서 기존 로컬 화면 표시 실험.
  - [x] `desktop/`에 개발용 셸 추가. 기본 주소 `http://localhost:8080/`.
  - [x] 테스트용 HTTP 서버로 실패·재시도·성공·HTTP 오류·시작 시간 초과 검증.
  - [ ] 실제 API 로그인·프로필 편집·파일 선택·영상 재생 확인.
- [ ] Windows에서 Java 서버 시작과 FFmpeg 짧은 영상 변환 실험.
- [ ] 현재 HLS 영상의 Electron 재생 가능 여부 확인. 코덱·MIME·경로 차이 기록.
- [ ] MySQL·Kafka 재사용 시 설치 크기, 프로세스 수, 메모리, 시작·종료 방식 확인.
- [ ] 유지안과 경량화 대안의 변경 범위·복구 기능·배포 부담 비교.
- [ ] 최종 로컬 실행 구조와 Electron 소스 위치를 결정 문서로 확정.

완료 기준: macOS 개발 실험과 Windows 최소 실행 증거가 있으며, 사용자에게 필요한 설치 절차와 내부 실행 구성이 정해져 있다. Windows 검증이 불가능하면 이 단계는 부분 완료로 남긴다.

### 2단계. local 프로필과 데이터·보안 기반

- [ ] API와 Worker에 `local` 프로필 추가. `dev`, `prod` 회귀 확인.
- [ ] 사용자 데이터 경로를 운영체제별로 결정하고 맥 절대 경로 제거.
- [ ] 설치 파일 / DB / 원본 / 인코딩 결과 / 임시 파일 / 로그 / 게시 상태 구분.
- [ ] Java 런타임·FFmpeg·FFprobe 경로를 배포 환경에서 명시적으로 해석.
- [ ] 로컬 HTTP 접근을 loopback으로 제한하고 포트 선택 정책 정의.
- [ ] 최초 실행 계정과 비밀값 생성·영속 보관 설계. 개발용 고정 비밀값 사용 금지.
- [ ] 로컬 서버도 인증·Origin/CSRF 등 위조 요청 방어 유지. loopback만으로 안전하다고 가정하지 않음.
- [ ] DB 최초 초기화·마이그레이션·기존 데이터 보존 확인.
- [ ] 프로세스 재시작과 앱 업데이트 후 동일한 데이터 폴더 사용 확인.

완료 기준: 재실행해도 데이터와 설정이 남고, LAN에서 편집 API에 접근할 수 없으며, 개발용 보안 예외에 의존하지 않는다.

### 3단계. Electron 실행·종료 통합

- [ ] 앱 실행 → 의존 프로세스 실행 → 준비 상태 확인 → 편집 화면 표시.
- [ ] 시작 중·실패·재시도 화면 구현. 무한 대기 대신 시간 제한과 원인 안내.
- [ ] 중복 실행 방지와 기존 창 활성화.
- [ ] 포트 충돌 시 다른 프로그램을 종료하지 않고 안전하게 처리.
- [ ] 앱이 시작한 자식 프로세스만 추적·종료.
- [ ] 인코딩·게시 도중 종료하면 확인 안내. 강제 종료 후 복구 정책 연결.
- [ ] 렌더러의 Node 접근 차단, context isolation·sandbox·최소 IPC 권한 적용.
- [ ] 외부 URL·새 창·파일 접근·IPC 입력 검증. 공개 웹 콘텐츠에 로컬 권한 부여 금지.
- [ ] macOS와 Windows에서 실행·닫기·재실행 검증.

완료 기준: 사용자는 터미널과 외부 브라우저 없이 앱을 사용하고, 실패해도 빈 창만 남거나 내부 프로세스가 무분별하게 중복 실행되지 않는다.

### 4단계. 오프라인 편집·인코딩

- [ ] 네트워크 차단 상태에서 프로필·필모그래피 편집 및 저장.
- [ ] 사진·영상 파일 선택, 복사·관리, 앱 재시작 후 원본 참조 확인.
- [ ] 외부 CDN의 스크립트·폰트 등 오프라인 화면 의존성 제거 또는 대체.
- [ ] 인코딩 완료 후 HLS 재생·구간 이동·썸네일 표시.
- [ ] 작업 진행·실패 원인·재시도 UI.
- [ ] 인코딩 동시 실행 수·스레드 수 제한 및 편집 반응성 측정.
- [ ] 한글·공백 경로, 긴 경로, 권한 부족, 디스크 부족, 손상 파일 검증.
- [ ] 인코딩 도중 종료·재시작 후 상태 복구. 완료 단계 재사용과 재인코딩 범위 구분.

완료 기준: 인터넷 없이 편집부터 영상 재생까지 성공하며, 실패 작업을 설명하고 안전하게 재시도할 수 있다.

### 5단계. 공개 결과물 분리와 호스팅 선정

- [ ] 공개 전용 데이터 형식과 버전 정의: 프로필·필모그래피·연락처·미디어 참조.
- [ ] 계정·토큰·내부 작업 정보·로컬 경로가 포함되지 않는지 검증.
- [ ] 공개 연락처 선택·확인 UI.
- [ ] 로그인과 로컬 API 없이 실행되는 읽기 전용 화면 구성.
- [ ] Electron 미리보기와 실제 공개 화면이 같은 결과물을 사용하도록 구성.
- [ ] 다른 PC·모바일 브라우저에서 조회·HLS 재생 검증.
- [ ] 대표 포트폴리오의 용량·파일 수·예상 재생 요청 수 측정.
- [ ] 호스팅 후보의 비용·영상 제공 조건·업데이트·접근 중단 방법 비교.
- [ ] 사용자와 호스팅, 계정 소유자, 결제 주체, 예산, 공개 기간 확정.
- [ ] 게시 권한의 최소 범위·자격증명 저장 방식 결정. 저장소나 배포 파일에 관리자 키 포함 금지.

완료 기준: 독립적으로 열리는 공개용 결과물이 있고, 실측 규모에 근거해 호스팅을 선택했다. 실제 유료 리소스 생성은 별도 확인 후 수행한다.

### 6단계. 게시·업데이트·공개 중단

- [ ] 게시 버튼을 누른 시점의 내용과 파일 집합을 고정. 이후 편집과 분리.
- [ ] 게시 작업 ID·진행 단계·성공/실패·공개 버전을 영속 저장.
- [ ] 변경 파일만 전송할 수 있도록 파일 식별·해시 정책 구현.
- [ ] 새 버전 경로에 업로드 → 필수 파일 확인 → 공개 버전 전환.
- [ ] 게시 중 중복 클릭 제어, 네트워크 재시도·앱 재시작 복구.
- [ ] 전환 응답 유실 시 서버 상태를 확인해 성공 여부 조정.
- [ ] 기존 공유 링크 유지, 캐시 반영 정책과 기존 시청자 처리 정의.
- [ ] 이전 버전 보관·복귀 및 미완료 업로드 정리. 참조 중인 파일 삭제 금지.
- [ ] 공개 중단과 저장소 파일 정리 분리. 로컬 원본은 유지.
- [ ] 기간 제한을 제공한다면 PC가 꺼져 있어도 온라인에서 만료 적용.
- [ ] HLS 재생목록뿐 아니라 영상 조각에도 공개 정책 적용.
- [ ] 게시 완료·업데이트 실패·공개 중단을 사용자 언어로 안내.

완료 기준: 새 버전 게시 실패 시 기존 공개본을 유지하고, 성공 시 같은 링크에 새 내용이 반영된다. PC를 꺼도 공개본은 열리며, 약속한 공개 중단 범위가 검증돼 있다. 이미 다운로드된 파일 회수나 모든 캐시의 즉시 소멸은 보장하지 않는다.

### 7단계. Windows 설치·업데이트·백업·인수 검증

- [ ] Windows 빌드 환경에서 설치 패키지 생성·검증.
- [ ] 사용자에게 Java·Node·개발 도구 수동 설치를 요구하지 않도록 런타임 구성.
- [ ] FFmpeg·DB 등 동봉 구성요소의 라이선스·재배포 조건과 고지 검토.
- [ ] 코드 서명 비용과 미서명 설치 경고를 확인하고 배포 정책 결정.
- [ ] 일반 사용자 권한에서 설치·아이콘 실행·종료·재실행.
- [ ] 설치 경로·사용자 이름에 한글·공백이 있는 Windows에서 검증.
- [ ] 앱 업데이트 전 백업, 마이그레이션 실패 안내·복구 절차 검증.
- [ ] DB와 파일의 일관성을 보장하는 백업·복원 구현 및 다른 위치에서 복원 실험.
- [ ] 삭제 시 사용자 데이터 보존을 기본으로 하고 영구 삭제는 명시적 확인.

## 6. 기존 프로젝트 보호와 검증 원칙

- API와 Worker 저장소의 `AGENTS.md`를 따른다.
- API·Worker DB 간 직접 접근·조인·공유 트랜잭션을 도입하지 않는다.
- DB·작업 전달 구조를 바꿀 경우 기존 소유권 정책과 별도 결정 문서를 먼저 검토한다.
- Flyway를 스키마 기준으로 유지하고 `ddl-auto: validate`를 사용한다. 적용된 마이그레이션을 수정하지 않는다.
- MySQL 스키마 변경은 MySQL Testcontainers로 검증한다. H2 성공을 MySQL 검증으로 대체하지 않는다.
- 영향 범위의 단위·통합 테스트와 최종 `check` 결과를 기록한다.
- 실제 Windows 실행 검증과 테스트 자동화 결과를 구분한다.
- 기존 데이터 삭제·초기화, 클라우드 리소스 생성·유료 전환은 별도 확인 없이 실행하지 않는다.
- 사용자 기존 변경사항을 보존하며 각 단계의 변경 파일과 검증 결과를 기록한다.
