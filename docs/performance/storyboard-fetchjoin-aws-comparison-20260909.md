# Storyboard 조회: AWS에서 N+1과 Fetch Join 비교

- 측정일: 2026-09-09
- 정리 근거: 사용자가 공유한 k6 출력, Prometheus 조회 결과, 배포 경로 확인 결과
- 원본 백업 파일은 작성 환경의 안내된 경로에서 확인하지 못했다. 아래 수치는 대화에서 확인한 결과이며 원본 파일과의 대조는 별도로 필요하다.

## 1. 문제와 개선

Storyboard 프로젝트 목록을 조회할 때 관련 장면을 프로젝트마다 따로 가져오면 DB 요청이 반복된다. 비교용 N+1 버전과 관련 데이터를 함께 가져오는 Fetch Join 버전을 같은 API 서버에서 번갈아 실행해 응답 시간과 자원 사용량을 비교했다.

이번 실험은 **조회 방식 비교**이며 인덱스 적용 전후 실험이 아니다. 기존 SQL 횟수 분석은 [Storyboard 조회 개선 기록](../review/k6/result-storyboard.md), 인덱스 비교는 [MySQL 인덱스 성능 기록](mysql-index-before-after-comparison.md)을 참고한다. 이번 실행에서 요청당 SQL 횟수를 새로 계수하지는 않았다.

## 2. 측정 조건

| 항목 | 조건 |
|---|---|
| API | `GET /api/people/{publicId}/storyboard/projects` |
| 데이터 | 단일 사용자, 프로젝트 20개, 장면 200개 |
| 요청 방식 | k6 `constant-arrival-rate`, 초당 50회 |
| 본 측정 | 실행당 2분, 사전 할당 VU 100개, 최대 VU 100개 |
| 검증 | HTTP 200, 응답 프로젝트 수 20개 |
| 로그인 | setup에서 1회; 조회 지표는 `endpoint:storyboard-projects`로 분리 |
| 2·3회차 준비 절차 | 버전 전환 및 기동 확인 → 최소 3분 대기 → 2분 준비 실행 → 본 측정 |
| 인프라 | AWS EC2 API·k6 분리, RDS MySQL 사용 |
| API 자원 | 기존 구성 기록상 t3.medium, 출력에서 2 vCPU·메모리 약 3.7GiB 확인 |
| 실행 환경 | Ubuntu 26.04 LTS, Java 17, k6 `v2.2.0+dirty` |
| DB 연결 풀 | HikariCP 최대 10개 |

대기 및 준비 실행과 본 측정 사이 간격은 수동 진행으로 정확히 같지 않다. RDS의 정확한 인스턴스 사양·패치 버전, CPU 크레딧, 캐시 상태는 이번 기록에서 확정하지 않았다. 따라서 완전히 통제된 실험으로 표현하지 않는다.

## 3. 본 측정 결과

### 준비 절차를 맞춘 2·3회차

| 방식 | 회차 | 평균 | p95 | 최대 | 조회 수 | HTTP 오류 | 미실행 반복 |
|---|---:|---:|---:|---:|---:|---:|---|
| Fetch Join | 2 | 21.22ms | 25.29ms | 405.65ms | 6,001 | 0 | 출력에 없음 |
| N+1 | 2 | 55.89ms | 67.75ms | 502.28ms | 6,001 | 0 | 출력에 없음 |
| Fetch Join | 3 | 21.80ms | 25.15ms | 480.56ms | 6,001 | 0 | 출력에 없음 |
| N+1 | 3 | 60.44ms | 79.91ms | 943.20ms | 6,001 | 0 | 출력에 없음 |

모든 본 측정의 종료 코드는 0이고 응답 검증은 100% 통과했다. 전체 HTTP 요청은 로그인 1회를 포함해 실행당 6,002회다. `checks` 12,002건은 조회당 검증 두 개의 합이지 요청 수가 아니다.

이 조건에서 Fetch Join의 평균은 21.22~21.80ms, p95는 25.15~25.29ms로 N+1보다 낮았다. 범위는 **각 실행 요약값의 범위**이며 여러 실행을 합산한 p95가 아니다.

### 자원 사용량

| 방식 | 회차 | CPU 관측 최대 | Heap 관측 최대 | 사용 중 DB 연결 관측 최대 | DB 연결 대기 관측 최대 |
|---|---:|---:|---:|---:|---:|
| Fetch Join | 2 | 24.30% | 147.39MiB | 1 | 0 |
| N+1 | 2 | 38.38% | 379.81MiB | 3 | 0 |
| Fetch Join | 3 | 25.90% | 241.34MiB | 1 | 0 |
| N+1 | 3 | 38.96% | 346.65MiB | 3 | 0 |

Prometheus에서 실행 시작~종료 구간을 조회했다. CPU는 `process_cpu_usage`, Heap은 `jvm_memory_used_bytes{area="heap"}`를 시점별 합산해 MiB로 환산했다. DB 지표는 `hikaricp_connections_active`, `hikaricp_connections_pending`이다.

조회 step은 1초지만 실제 수집 간격이 1초라는 뜻은 아니다. 최댓값은 수집된 표본 기준이고 서로 같은 시점의 값이라고 볼 수 없다. 대기 0도 표본 사이의 짧은 대기를 배제하지 않는다. Heap은 GC 시점에 영향을 받으므로 메모리 절감률로 주장하지 않는다.

### 참고: 준비 조건이 달랐던 1회차

| 방식 | 평균 | p95 | 최대 | CPU 관측 최대 | Heap 관측 최대 | DB 사용 / 대기 최대 |
|---|---:|---:|---:|---:|---:|---|
| Fetch Join | 42.77ms | 39.03ms | 2.44초 | 31.86% | 275.44MiB | 1 / 0 |
| N+1 | 57.01ms | 77.84ms | 506.64ms | 34.46% | 390.56MiB | 3 / 0 |

각각 조회 6,001회, 오류 0건이다. N+1은 추가 진단 실행과 긴 대기 후 측정됐으므로 2·3회차와 묶어 동일 조건 3회 측정이라고 표현하지 않는다.

## 4. 준비 구간의 지연과 실패도 보관

| 준비 실행 | 조회 수 | p95 | 최대 | 미실행 반복 | 종료 코드 |
|---|---:|---:|---:|---:|---:|
| Fetch Join 2 | 6,001 | 110.95ms | 1.28초 | 출력에 없음 | 0 |
| N+1 2 | 6,001 | 1.76초 | 4.83초 | 출력에 없음 | 99 |
| Fetch Join 3 | 5,984 | 490.90ms | 3.24초 | 17 | 0 |
| N+1 3 | 5,989 | 1.88초 | 5.52초 | 12 | 99 |

- 처리된 조회의 HTTP 오류는 위 네 실행 모두 0건이다. 그러나 실행되지 못한 반복은 오류율에 포함되지 않는다.
- 기존 스크립트에는 `dropped_iterations` 임계값이 없다. 따라서 종료 코드 0도 목표 부하를 모두 실행했다는 뜻은 아니다.
- N+1 3회차의 최초 시도는 로그인 401로 setup에서 종료됐다(코드 107, 조회 0회). 실제 준비 실행과 구분해 보관한다. 이때 표시된 p95 0은 유효한 성능 수치가 아니다.
- 초기 N+1 1분 준비 실행에서도 p95 2.81초와 미실행 반복 161회가 관측됐다. 기동~진단 구간의 표본 최대는 DB 사용 10개, 대기 90개, CPU 약 94.8%였다. 각 최댓값의 동시 발생 여부와 정확한 부하 구간 일치는 확정하지 않았다.
- 이후 1분 진단에서는 p95 89.29ms, DB 사용 최대 3개·대기 0개·CPU 약 53.7%로 낮아졌다.

초기 부하에서 지연이 나타나고 이후 본 측정에서 완화되는 현상은 확인했지만, JIT·캐시·SQL 로그·DB 상태 중 무엇이 원인인지 분리 검증하지 않았다. 단순히 “워밍업 문제 해결” 또는 “N+1만의 장애”라고 결론 내리지 않는다.

## 6. 면접·포트폴리오 요약

> Storyboard 조회에서 반복되는 DB 요청을 줄이기 위해 Fetch Join을 적용했습니다. AWS에서 프로젝트 20개·장면 200개를 대상으로 초당 50회씩 2분간 비교했고, 준비 절차를 맞춘 각 방식의 본 측정 2회에서 p95가 N+1의 67.75~79.91ms에서 Fetch Join의 25.15~25.29ms로 감소했습니다. 각 실행은 조회 6,001회를 오류 없이 처리했습니다. 다만 단일 사용자·같은 데이터의 반복 조회 결과이며, 준비 구간의 지연과 일부 반복 누락도 별도로 기록했습니다.

실제 사용자 행동 지표, 최대 처리량, 다중 사용자 부하를 검증한 결과로 확대 해석하지 않는다. 준비 절차를 맞춰도 시간대와 실행 환경의 변동까지 제거한 것은 아니다.
